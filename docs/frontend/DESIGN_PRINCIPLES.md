# MuYun 前端设计原则

本文记录 MuYun 前端已经形成的设计哲学和稳定共识。它约束前端平台能力、业务页面、动态页面运行器和 UI adapter 的长期取舍。

## 核心定位

MuYun 前端不是单个业务后台，也不是 Ant Design Vue 的简单二次封装。它应逐步形成一组可被平台项目和业务项目共同消费的前端平台能力。

前端建设应以平台语义为中心。业务页面优先使用 MuYun 组件、MuYun client 和 MuYun runtime，不直接依赖底层 UI 库或裸 HTTP URL。静态业务页面和动态页面运行器应共享组件、字段、动作、错误、请求上下文和缓存语义。

## 螺旋迭代

MuYun 前端不采用先闭门建设完整组件库、再统一交付业务页面的方式，也不允许业务页面自由绕过平台能力形成事实标准。

组件和业务应螺旋迭代：

1. 先沉淀当前业务闭环必要的组件和 client。
2. 推进业务页面或动态页面运行器。
3. 从真实使用中发现组件、契约和非 UI 能力缺口。
4. 将稳定缺口上升到平台层，不稳定能力留在业务或示例中继续观察。

非 UI 能力和 UI 组件也应螺旋迭代。UI 组件可以随业务场景逐步加厚；HTTP、请求上下文、错误归一、权限、缓存、字典、引用和动作执行等非 UI 能力应尽早形成窄门面，避免业务项目重复封装。

## 业务闭环牵引

平台能力应由真实业务闭环牵引，而不是由抽象组件清单牵引。

每轮建设都应尽量围绕一个有代表性的页面、动作或动态运行链路展开，覆盖真实数据、真实动作、真实错误和真实刷新策略。这样沉淀出的契约更接近后端平台语义，也更容易被业务项目消费。

进入具体业务线前，应先固定平台主 UI 框架的承载形态。布局、菜单、菜单 tab、路由内容区、全局 loading、错误出口和上下文传递会影响后续所有页面，不应让业务页面各自形成实现。

## 能力上升

业务项目中的能力不自动进入平台层。能力上升应满足尽量多的条件：

1. 跨多个业务项目或多个模块复用。
2. 依赖平台标准语义，例如模块、字段、动作、字典、引用、附件、权限或审计。
3. 能通过稳定类型、props、事件、client 和文档交给下游团队使用。
4. 维护责任属于平台团队，或有明确共同维护机制。
5. 抽象后能明显降低业务项目代码量和风格分叉。

只服务单业务、语义未稳定或抽象收益不清楚的能力，应留在业务项目或示例中，不强行平台化。

## 垂直能力投入

垂直领域组件和能力可以在早期做深，但必须先判断场景是否足够清晰。

适合早期加深的能力通常具备：

1. 平台语义稳定。
2. 跨业务高频复用。
3. 后端能力边界清楚。
4. UI 形态变化空间有限。
5. 可通过类型、测试和示例稳定交付。

变化面大、业务面未看清或实现会明显扩张范围的能力，应控制投入并及时止损。

## 分层取舍

前端分层服务于长期演进，不服务于形式化拆目录。

| 层                     | 设计取舍                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| `web-contracts`        | 承载前后端共享的稳定语义、DTO、动作、字段、保存 envelope 和错误结构。                           |
| `web-core`             | 承载无 UI 的平台能力，例如 HTTP、请求上下文、错误、权限、Query 治理、字典、引用候选和动作执行。 |
| `vue-ui-antdv`         | 承载 Vue + Ant Design Vue adapter 和受控值归一，不承接平台数据获取和业务编排。                  |
| `platform-components`  | 承载跨业务复用、依赖平台标准能力、语义稳定的平台业务组件。                                      |
| `dynamic-page-runtime` | 将后端 descriptor、运行上下文、组件 registry 和平台 client 组合为动态页面能力。                 |
| `platform-workbench`   | 承载菜单、登录态、租户切换、全局错误出口和路由框架。                                            |

组件不应各自拼 URL、处理 token、解释权限、实现缓存失效或自定义错误展示。涉及这些能力时，应回到 `web-core`。

## UI adapter 复用与契约封口

UI adapter 的职责不是重写成熟 UI 库。下拉菜单、模态框、抽屉、通知、表格、表单和输入等已有成熟承载组件时，优先在 adapter 内部复用 Ant Design Vue；MuYun 只负责将它们收敛为稳定的业务或平台语义、视觉口径和受控交互，不在业务层复制浮层定位、焦点管理、键盘导航、遮罩或关闭生命周期。

对外导出的 MuYun 组件不能以“换了名称的 Ant Design Vue”形式存在：

1. 组件只声明平台认可的 props、事件与 slots，不透传完整 Ant Design Vue props，也不让未知 attribute 自动落到底层组件。
2. `class` 与 `style` 可作为外观挂点保留；HTML 标准能力如 `autocomplete`、无障碍标签等，只有在确有跨业务语义时才显式进入 MuYun 类型契约。
3. UI 库专有能力需要先判断是否应翻译为 MuYun 语义，例如密度、危险操作、确认动作、打开状态和选择结果；不能由业务层依赖 UI 库的私有字段或 DOM 结构。

当前 `UiDropdown` 是统一菜单浮层门面，内部复用 Ant Design Vue `Dropdown` 与 `Menu`；`UiModal` 是受控对话框门面，负责打开状态、标题、确认/取消和提交态；`UiSidePanel` 是非模态上下文侧栏门面，内部复用 Ant Design Vue `Drawer`。业务页面与平台组件不得直接组合 Ant Design Vue 的对应组件。

`UiSidePanel` 的承载范围必须显式表达：默认 `tab`，由 Workbench 为每个 tab 提供的 `UiSidePanelHost` 承载，只覆盖当前 tab 内容区；公开 Workbench 插槽具有默认 Host；内置缓存路由页在缓存单元内提供独立 Host，停用时隐藏抽屉而保留业务草稿，恢复时继续当前会话。Host 必须位于页面留白与滚动容器之外，确保抽屉边界贴合 tab 内容边界而非页内业务面板。只有跨 tab 的全局治理任务才能显式使用 `viewport`。业务页面不得用自身的 `position`、高度或 overflow 偶然决定抽屉覆盖浏览器还是 tab。

## 组件语义先于 UI 结构

平台组件的公开 props、events 和 slots 应表达调用方需要声明的业务意图，而非当前 DOM 结构或视觉位置。平台组件负责将这些意图安放到一致的视觉骨架中；调用方不应依赖 header、footer、sidebar、card 等实现词来控制布局。

1. 对外命名优先使用领域角色和行为，例如 `explorer`、`detail`、`operation`、`selection`、`scope`；`header`、`footer`、`sidebar`、`card` 等仅可作为组件内部结构或样式实现词。
2. 调用方只提供事实：数据、状态、允许的操作、权限结果和处理函数。位置、滚动、对齐、主次排序、窄屏换行、承载范围和浮层层级由平台组件统一负责。
3. 一个视觉区域在业务上有稳定职责时，应以职责命名并形成窄插槽，例如抽屉使用 `operation` 而非 `footer`；静态管理页使用 `explorer/detail` 而非 `sidebar/card`。
4. 不因追求抽象而删除必要的呈现能力。若业务确实需要选择承载范围或宽度，平台应通过受控、默认安全的语义属性提供，而不是让业务绕过组件访问底层 UI 库。
5. Review 时要追问：替换布局实现后，调用方的 API 是否仍成立？若答案是否定的，说明公开契约泄漏了 UI 结构，应优先重命名或收口。

记录与配置抽屉使用统一纵向骨架：header 只承载标题、状态和关闭；body 独立滚动；所有业务操作进入固定“操作区域”（`operation` 插槽），包括查看态的编辑、删除、刷新以及编辑态的取消、保存、确认。纯查看态可按页面语义允许点击外部关闭，编辑、创建和配置态默认不允许。

业务只在 `operation` 中声明操作事实；`DrawerOperationBar` 统一按钮对齐、主操作顺序和窄屏布局。`RecordDetailDrawer` 与 `RecordModeDrawer` 仅受控暴露 `width`、`scope`，默认分别为 `520` 与 `tab`；需要覆盖浏览器窗口时，业务必须显式声明 `scope="viewport"`。标准模块宿主根据可执行关联描述为含明细的记录选择 `extraWide`，普通表单保留 `standard`，查看与编辑使用同一宽度；显式定制抽屉仍按其宽度声明。标准业务入口和已发布业务预览共用此规则，实际宽度受工作区可用空间约束。

具备稳定对象身份的内容应声明为**工作视图**，而非“抽屉任务”或“Tab 页面”。工作视图定义唯一的类型、可序列化稳定输入、恢复校验和允许的承载方式；`drawer` 与 `tab` 只是同一视图实例的表现。平台注册表负责 URL、输入校验、按参数去重、激活页签和恢复，重复类型必须启动失败。`WorkspaceViewOutlet` 为两种承载提供统一宿主事实和关闭语义：URL 恢复 `drawer` 时，视图在当前 tab 的 `UiSidePanelHost` 中呈现；关闭后由宿主回到去除工作视图参数的普通路由。业务不得临时拼接路由，也不得把承载方式编码为另一套业务页面。

URL 只保存可恢复身份和承载声明，不保存草稿、加载态或局部交互。平台以“视图类型 + 稳定输入”建立会话槽位，并提供主机间 hand-off：目标 Tab 尚未挂载时消费待交接状态，已挂载时由目标主机接收状态。只有目标确认接收后，源抽屉才关闭；目标存在冲突草稿时必须拒绝交接，不能静默覆盖或丢弃。因而“固定为页签”不是搬运 DOM，也不应天然禁止未保存修改。提交中的视图仍不得切换承载；创建、批量配置、一次性授权、重置密码等没有稳定身份的事务性抽屉不得声明为工作视图。业务实现应将详情会话与内容组件从列表页抽出，供两个宿主共同承载，避免复制加载、保存和并发控制逻辑。

工作视图 URL 的恢复优先级高于同一路径的菜单匹配：带有已声明 `workspaceView` 的 URL 必须恢复为按稳定输入隔离的直接 Tab，不能退化为菜单 Tab。菜单页与工作视图可以复用同一路径和模块别名，但它们是不同的页面身份；刷新工作视图后，仍必须能从菜单打开其所属的管理页。

详情标题由平台组件统一承载为 `title`（主标题）和可选 `subtitle`（副标题）。业务只提供对象身份和上下文，不自行拼接 Header 布局；抽屉与工作区详情 Header 统一显示主标题和副标题，Tab 只显示主标题。主标题应能在并列 Tab 中识别对象，必要时包含稳定业务编号；副标题表达“详情”“编辑”等视图上下文，不参与 Tab 身份、URL 或去重。

详情骨架与表面也必须分离：工作区中的 `RecordDetailPanel` 使用卡片表面（边框、圆角）；标准抽屉内部使用同一详情骨架的抽屉表面（无内层边框和圆角），并以贯穿宽度的弱分割线界定 header 与内容。业务不选择表面样式或分割线，承载组件按自身语义决定，避免出现“抽屉内再嵌详情卡片”。

涉及模块动作、记录动作、表单提交、重试、取消或危险操作时，优先使用 `UiActionButton`。它使用 `emphasis` 表达主/次/弱操作，使用 `intent` 表达危险意图，使用 `density` 表达紧凑程度，避免业务和平台组件依赖底层按钮样式名。

## 平台反馈

全局反馈是 UI adapter 的平台能力，不由业务页面直接调用 Ant Design Vue 的 `notification`。业务侧通过 `showFeedback` 或语义快捷入口表达反馈事实，adapter 负责选择区域、堆叠、关闭周期和视觉状态。

当前反馈语义如下：

| 语义      | 承载组件       | 位置与队列             | 视觉口径                                         |
| --------- | -------------- | ---------------------- | ------------------------------------------------ |
| 错误/警告 | `notification` | 顶部居中、由 UI 库堆叠 | 紧凑、立即可见、使用错误色和 16px 状态图标。     |
| 成功回执  | `notification` | 右上角、由 UI 库堆叠   | 紧凑、非阻断、使用成功色和同样的 16px 状态图标。 |

图标和文字统一使用垂直居中、8px 间距的单行布局；不同承载组件不能因为默认 DOM 结构不同产生图标偏移。自动关闭反馈使用可见的上边缘时间条表达剩余时间。时间条使用与状态图标一致的语义色，向右流逝；鼠标进入气泡时回满并以短缓动展示，鼠标离开后重新开始完整倒计时。时间条只属于气泡卡片内部，不影响 UI 库管理的位置、堆叠或关闭生命周期。

当后续需要 `info`、`warning`、持久提醒、操作按钮或通知中心时，应先扩展 `UiFeedbackTone` 和 adapter 契约，再由业务接入；不要在业务页直接组合底层通知组件。

## 命名原则

包名表达 MuYun 归属，代码名表达职责。`@muyun/*` 保留品牌和发布边界；组件、类型、client 和函数不加 `Muyun` 前缀。基础 UI 组件使用 `Ui` 作为层级前缀并保持内外一致，例如 `UiForm`、`UiInput`、`UiSelect`、`UiTable`；平台语义组件直接使用职责名，例如 `ReferenceSelect`、`ActionBar`。`Dynamic`、`Platform`、`Admin` 等表达真实领域边界的前缀可以保留。

## Review 口径

前端 review 先看方向和边界，再看行为正确性，最后看组件细节。

重点判断：

1. 是否仍以平台语义和业务闭环为中心。
2. 是否避免业务页面绕过 MuYun client、MuYun 组件和 MuYun runtime。
3. 是否让静态业务页面和动态页面运行器共享字段、动作、错误、请求和组件语义。
4. 是否把稳定能力及时上升，把不稳定能力留在合适位置。
5. 是否为新增契约提供测试、边界检查或可运行示例。
