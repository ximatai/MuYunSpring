# 统一树与平铺拖拽组件专项治理

本文记录 MuYun 前端统一树/平铺展示组件的目标能力、交互契约、异步加载、结构动效和仓库治理边界。它先固定长期方向，不等同于当前实现已经全部完成。

## 治理目标

MuYun 当前同时存在树、平铺列表和页面编排三类节点交互：

| 场景         | 当前承载                                        | 主要问题                                 |
| ------------ | ----------------------------------------------- | ---------------------------------------- |
| 标准树资源   | `UiTree` / `TreeRecordExplorer`                 | 依赖 Ant Tree，拖拽事件需要 adapter 归一 |
| 标准平铺资源 | `RecordListExplorer` / `CrudRecordListExplorer` | 使用另一套原生列表拖拽协议               |
| 页面配置编排 | `PageCompositionTree`                           | 多个 Sortable 容器自行处理跨容器移动     |

这些组件的视觉表达相近，但选择、拖拽、跨组件投放、异步节点和状态变化没有统一公共契约。专项目标是形成一个可复用的基础交互能力，同时保留业务组件对领域规则和持久化的所有权。

## 核心原则

1. 公共组件统一节点身份、选择、复选、拖拽、异步状态和动效协议，不承载 CRUD 查询、业务权限、页面草稿或后端保存。
2. `tree` 和 `flat` 是同一套节点模型的两种展示适配器，不是两套互不兼容的组件 API。
3. 拖拽分为同实例排序、跨实例复制、跨实例移动和嵌套容器移动，不能用一个模糊的 `drop` 语义掩盖差异。
4. 异步数据既支持组件托管，也支持父页面受控；默认使用组件托管，复杂页面可以接管节点数据和缓存。
5. 动效主要跟踪节点结构变化；选中、展开、复选和加载状态使用各自的状态反馈，不冒充结构移动。
6. 业务事实在业务层产生，组件只发出规范化意图。排序、字段归属、页面草稿和发布仍由对应业务状态或平台 client 处理。
7. 所有节点必须有稳定且唯一的 `key`。节点的展示标题、标签和位置都不能替代身份。
8. 不以减少依赖数量或绝对去 vendor 为独立目标。只要底层库能显著提高可访问性、交互稳定性、动效质量或维护效率，且版本、许可证、性能和升级成本可接受，绑定底层库就是合理方案；是否做 adapter 按实际收益决定。

## 统一节点模型

公共组件继续使用来源无关的节点模型：

```ts
interface UiTreeNode {
  key: string;
  title: string;
  secondary?: string;
  tag?: string;
  muted?: boolean;
  disabled?: boolean;
  isLeaf?: boolean;
  children?: UiTreeNode[];
}
```

业务扩展字段不进入基础节点的固定语义；需要参与拖拽或投放时，通过拖拽 payload 或业务侧节点映射表达。

## 展示模式

### Tree 模式

Tree 模式支持：

- 多级父子结构；
- 展开/收起；
- 异步子节点加载；
- 同父级排序；
- 可选树形复选级联；
- 节点动作、选中和禁用状态。

树内拖拽是否允许改变父子关系由业务 `canDrop` 决定。默认不因为“拖到节点上”就隐式改变父子关系；需要结构移动的页面必须显式声明目标区域和规则。

### Flat 模式

Flat 模式消费有序的一维节点集合，保留与 Tree 模式一致的 item 视觉、选择、动作、复选和拖拽事件。

Flat 模式支持：

- 纵向排序；
- 跨组件复制或移动；
- 关键字过滤后的只读展示；
- 与 Tree 模式一致的节点 descriptor。

Flat 模式不解释 `children`，也不自行推导父子关系。需要树形语义时必须使用 Tree 模式。

## 选择与复选

复选框默认隐藏，由 `checkable` 显式开启。

### Tree 模式

支持两种复选语义：

- 级联模式：父节点、子节点和半选状态由树关系计算；
- 严格模式：节点之间独立选中，不因为父子关系联动。

复选值通过受控的 `checkedKeys` / `update:checkedKeys` 契约同步，组件同时发出包含当前节点、选中 key 和半选 key 的规范化 `check` 事件。

### Flat 模式

Flat 模式只有独立复选，不产生半选状态。复选框不应阻断节点选择、行内动作或拖拽手柄之外的正常点击语义。

节点 `disabled` 时，选择、复选和拖拽都必须遵守禁用规则；业务可以通过 `canDrag` 和 `canCheck` 做更细的权限限制。

## 拖拽协议

### 拖拽来源

组件提供统一的拖拽来源能力：

- `canDrag(node)` 判断节点是否可作为来源；
- `dragPayloadOf(node)` 生成来源无关 payload；
- `dragPayloadType` 标识 payload 类型；
- `drag-start` 暴露规范化节点和原生事件；
- 原生 `DataTransfer` 只承载可序列化的跨组件数据，不承载 Vue 实例或业务状态引用。

没有声明跨组件来源时，组件仍可以只提供同实例排序，不强制产生外部 payload。

### 投放类型

统一区分以下投放语义：

| 语义       | 典型场景                     | 组件输出                                     |
| ---------- | ---------------------------- | -------------------------------------------- |
| 同实例排序 | 同一树的同级节点、平铺列表   | `dragNode`、`dropNode`、相对位置             |
| 跨实例复制 | 可用字段 → 页面字段          | payload + 目标区域，来源保留                 |
| 跨实例移动 | 工作区之间转移同一节点       | payload + 目标区域，来源移除由业务决定       |
| 嵌套移动   | 表单字段 → 分组、分组 → 表单 | source container、target container、目标下标 |

`canDrop` 只负责判断投放是否成立；真正的复制、移动、排序和持久化由业务层执行。组件不根据节点标题或 DOM 位置猜测业务关系。

### 交互与视觉

拖拽过程至少需要统一：

- 来源节点拖拽态；
- 目标区域高亮；
- 上方/下方或容器内的投放指示；
- 不可投放时的反馈；
- 空容器可见的投放区域；
- 拖拽取消后的视觉恢复。

原生拖拽、指针拖拽和 Sortable adapter 可以是不同实现，但必须输出同一份平台事件，不能让业务页面分别理解 Ant Tree、HTML5 DragEvent 和 SortableEvent。

## 异步加载与懒加载

异步加载只对 Tree 模式有结构意义，Flat 模式不通过 `children` 做隐式懒加载。组件需要支持以下策略：

### 组件托管模式（默认）

组件在节点展开时调用 loader，loader 返回节点或加载结果；组件管理该节点的请求生命周期、最小 loading 时长、空分支处理和加载缓存。适合普通树资源和标准动态页面。

```text
expand -> loading -> replace/append children -> expanded
                 -> empty
                 -> error/retry
```

### 外部受控模式

组件只发出加载请求，父页面负责请求、缓存和更新 `nodes`。组件根据传入数据变化更新展示和动效，不直接拥有业务节点状态。适合页面编排、复杂权限或已有状态中心的场景。

### 数据合并模式

加载结果明确区分：

- `replace`：刷新或首次加载，替换当前子节点集合；
- `append`：分页、游标或“加载更多”，追加子节点。

加载协议还必须支持节点级刷新、请求去重、旧请求隔离、空结果和取消后的安全回收；失败重试统一通过 `refreshNode(key)` 重新发起。旧请求不得覆盖新的节点快照。

`UiTree` 对外提供 `refreshNode(key)` 与 `loadMore(key)` 命令，分别对应 `refresh` 和 `load-more` 请求原因；游标和 `replace` / `append` 的合并仍由组件协议统一处理，业务 loader 只负责返回节点结果或在受控模式下更新上游数据。

## 结构动效

动效以节点结构前后快照为基础，不依赖某一种拖拽库事件。组件或其 adapter 识别以下变化：

```text
enter     新增节点
leave     删除节点
move      同容器位置变化
reparent  父节点或目标容器变化
update    标题、标签等展示信息变化
```

默认动效策略：

1. 首次加载和整树刷新不播放移动动画。
2. 普通新增、删除、排序、跨容器移动和懒加载插入播放结构过渡。
3. 展开、收起、选择、复选和 loading 使用独立状态动画。
4. 搜索过滤和批量替换默认关闭位置移动动画，避免全列表跳动。
5. 默认时长保持在约 160～240ms，允许主题统一调整。
6. 遵守 `prefers-reduced-motion`，系统要求减少动效时降级为无位移动画。

Flat 模式可以使用标准 FLIP/TransitionGroup 实现同容器移动。Tree 模式按每个同级容器计算位置；跨父节点移动默认表现为旧位置离开、新位置进入，只有在渲染层具备稳定 FLIP 信息时才做连续位移动画。

## 分层边界

```text
UiTreeCore / UiTree
  -> 节点展示、选择、复选、展开、拖拽、异步状态、动效

TreeRecordExplorer / RecordListExplorer / PageCompositionTree
  -> 数据加载适配、过滤、领域规则、容器语义、页面状态

web-core / 业务状态 / service
  -> 权限、CRUD、排序、草稿、发布和持久化
```

`UiTree` 不应演变成带 CRUD 查询、HTTP、领域权限和保存按钮的业务容器。`TreeRecordExplorer`、`CrudRecordListExplorer` 和 `PageCompositionTree` 可以继续存在，但应逐步消费统一的基础交互协议。

## 实现依赖策略

依赖策略的目标是用可接受的维护成本获得稳定能力，而不是机械地删除依赖包或追求形式上的完全解耦。底层库绑定本身不是问题，无法控制业务语义、升级风险或测试成本时才是问题。

### 依赖决策规则

引入或保留底层库时，按以下顺序判断：

1. 能否直接满足 Tree/Flat、拖拽、复选、懒加载和动效等真实需求；
2. 复用它是否明显低于 MuYun 自己实现和长期维护的成本；
3. 版本稳定性、许可证、性能、浏览器兼容和升级风险是否可接受；
4. 底层 API 是否会迫使业务页面理解第三方内部事件或数据结构；
5. 是否需要 adapter，以及 adapter 的复杂度是否真的换来了稳定边界。

如果前 3 项收益明显、后 2 项风险可控，即使组件直接绑定 `ant-design-vue` 或 Sortable，也可以接受。adapter 不是必须存在的架构装饰；它只有在统一多个底层实现、隔离高频变化或显著降低业务接入成本时才值得保留。

### 允许保留和引入的依赖

以下依赖可以根据真实收益纳入实现：

- `ant-design-vue`：继续作为 MuYun 整体 UI 体系和部分基础控件的实现来源；
- `Ant Tree`：在过渡阶段作为 Tree renderer 或兼容 adapter，复用其成熟的展开、键盘、ARIA 和级联复选能力；
- `vue-draggable-plus` / Sortable：在需要可靠处理复杂嵌套容器时作为局部拖拽 adapter；
- Vue 原生 `TransitionGroup`、PointerEvent、DragEvent：用于 MuYun 自有的 Flat renderer、拖拽协议和结构动效。

是否使用某个依赖，以它是否减少重复实现、降低交互风险和提供可验证的浏览器行为为判断依据。不能为了追求“零依赖”而重新实现已经成熟且容易出错的可访问性或拖拽细节。

### 优先保持稳定的 MuYun 契约

无论底层使用 Ant Tree、Sortable 还是原生 DOM，以下内容属于 MuYun 的稳定交互语义，优先由 MuYun 定义。它们可以委托底层库实现，不要求全部重新实现：

- `UiTreeNode` 和节点身份规则；
- Tree/Flat 统一的选择、复选、异步和动效状态；
- 同实例排序、跨实例复制/移动和嵌套移动的拖拽语义；
- `canDrag`、`canDrop`、payload 类型和 drop zone 契约；
- loading、empty、error、retry、replace、append 的异步状态；
- `enter`、`leave`、`move`、`reparent`、`update` 的结构变化分类；
- 业务层接收的事件和值类型，以及必要时对第三方事件的归一化。

业务页面默认不直接消费 `AntTreeNode`、`SortableEvent` 或某个第三方组件的半选值结构。若直接绑定能显著降低复杂度，可以把绑定收敛在 `vue-ui-antdv` 公共组件内，并记录其版本和升级边界；不应让同一套第三方细节散落到多个业务页面。

### 推荐的演进方式

```text
MuYun public contract
  -> UiTreeCore / composables
  -> Tree renderer adapter
       -> 过渡期 Ant Tree
       -> 目标 MuYun renderer
  -> Flat renderer adapter
       -> Vue/native DOM
       -> 必要时局部 Sortable
```

目标不是立即移除 `ant-design-vue`，也不承诺未来一定替换底层 renderer。只要 Ant Tree 在目标场景下的能力、稳定性和维护成本仍然优于自有实现，就可以继续使用；只有在自有 renderer 的综合收益明确超过它时，才评估替换或减少 Ant Tree 的使用范围。

## 迁移路线

### 第一阶段：固定公共契约

- 在 `vue-ui-antdv` 统一节点、拖拽、复选和异步状态类型；
- `UiTree` 增加 Tree/Flat 展示能力，但保持现有 Tree 调用兼容；
- 先建立 renderer/adapter 边界，不因追求减少依赖而提前重写成熟的 Tree 基础行为；
- 提供组件托管 loader 和外部受控 loader 两种入口；
- 增加结构变化动效的默认策略和减少动效降级；
- 用组件测试锁住同树排序、跨组件 payload、懒加载并发隔离和复选语义。

### 第二阶段：迁移现有使用方

- `RecordListExplorer` 的平铺拖拽改为消费统一 flat adapter；
- `TreeRecordExplorer` 的树排序改为消费统一 Tree adapter；
- `PageCompositionTree` 保留页面领域命令，但消费统一跨容器 drop 事件；
- 左侧元数据树继续作为拖拽源，页面结构树继续作为领域投放目标。

### 第三阶段：完善平台体验

- 补齐键盘拖拽或可访问替代操作；
- 补齐浏览器级拖拽回归测试；
- 评估大数据量树的虚拟化，但不在基础组件尚未稳定前提前绑定虚拟化实现。

## GitHub 仓库治理判断

### 当前结论：跟随 MuYun 项目治理

现阶段不建议立即拆成独立 GitHub 项目，原因是组件仍与 MuYun 的以下平台契约紧密相关：

- `UiRecordExplorerItem` 和 MuYun 主题体系；
- `UiTreeNode`、平台动作和页面 explorer 视觉契约；
- 动态/静态统一页面运行器；
- `web-core` 的模块上下文和排序语义；
- MuYun 当前的构建、测试、发布和 consumer 校验链路。

现在拆仓库会提前引入独立版本、文档、CI、发布和兼容性成本，同时容易把平台组件做成与 MuYun 脱节的通用 UI 库。更合适的做法是在 MuYun 内部先把公共边界治理干净，让它成为一个清晰的可发布 package 边界，而不是复制出第二套实现。

### 未来可以独立拆分的条件

满足以下条件后再评估独立 GitHub 项目或独立 npm package：

1. 组件不再依赖 MuYun 业务类型、模块上下文和页面状态；
2. 主题、item renderer、拖拽 payload 和异步 loader 都有来源无关的公共契约；
3. 至少有两个非 MuYun 消费方或明确的外部使用需求；
4. 已具备独立的单元测试、浏览器拖拽测试、可访问性测试和视觉回归；
5. 有独立维护者、版本策略、变更日志和发布流程；
6. 拆分后 MuYun 仍可以通过稳定 adapter 消费，而不是直接反向依赖 MuYun 内部实现。

在此之前，建议采用“MuYun 单仓库内的平台 package 边界”治理：公共类型和组件保持在 `vue-ui-antdv`，业务适配器留在 `platform-components` / `views`，通过测试和文档维护边界。

仓库治理与依赖治理分开处理：即使未来保留 `ant-design-vue` 或局部 Sortable 依赖，仍然可以先把公共协议、adapter 和业务边界治理好；是否拆成独立项目不以依赖数量作为前置条件。

## 当前不纳入

- 不在基础组件中内置 CRUD、HTTP、权限和后端排序；
- 不把页面编排领域规则抽象成通用节点规则；
- 不强制所有树都支持改变父子关系；
- 不提前建设虚拟滚动、多人协作冲突合并或远程实时同步；
- 不为了独立开源而牺牲 MuYun 当前动静一体的平台契约。

## 验收口径

专项完成时，至少应满足：

1. 同一套节点和事件类型可以驱动 Tree 与 Flat 两种展示；
2. 普通同实例排序、跨组件复制、跨组件移动和嵌套移动可以明确区分；
3. 复选框默认隐藏，Tree 支持级联/严格模式，Flat 支持独立多选；
4. 懒加载支持组件托管、外部受控、replace、append、失败重试和旧请求隔离；
5. 节点结构变化可按 enter、leave、move、reparent、update 分类并触发动效；
6. 初次加载、批量刷新和减少动效环境不会出现不必要的位移动画；
7. 业务页面不需要理解 Ant Tree、原生 DragEvent 或 SortableEvent 的内部差异；
8. 现有应用管理、树管理和页面编排场景可以渐进迁移，不要求一次性重写。
