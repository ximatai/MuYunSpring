# 开发原则

本文记录已经确认的开发原则。它约束方向，不替代测试和代码实现。

## 核心路线

MuYunSpring 的目标是形成“动静一体”的平台：静态 Java 模型和动态元数据模型共享同一套能力、数据访问、生命周期和治理语义。

进入页面交付阶段后，“动静一体”不是要求建设两套静态/动态页面内核。动态 UI 配置和静态模块声明应先收敛为来源无关的 resolved descriptor，再复用同一套读投影、数据访问、能力语义、权限、审计、生命周期、租户和事务边界，不能因为配置化页面或静态页面声明拆出平行基础实现。

业务模块的理想形态是声明自己拥有哪些平台能力，而不是重复编写平台流程：

```java
@Service
public class OrganizationService implements
        CrudAbility<Organization>,
        SoftDeleteAbility<Organization>,
        TreeAbility<Organization>,
        ReferenceAbility<Organization> {
}
```

`TreeAbility` 已经包含同级排序语义。树形业务不需要再额外声明 `SortAbility`，避免把稳定业务层级误拆成可选 mixin。

## 公共业务接入与个性化治理

Service 和 Web Controller 都是公共业务接入平台的可插拔边界，不是把通用流程集中到某一层的理由。公共业务应通过模型、Ability、注解、标准 Web 投影、resolved descriptor 和贡献接口接入；静态与动态来源进入同一能力、权限、数据范围和页面交付链路。

模块只在自己的 Service 或 Web 声明中保留无法由平台推导的事实与意图：领域不变量、领域范围、特有动作编排、字段与页面表达。Controller 中的 DSL 是静态模块的交付声明，可以就地表达标签、字段顺序、导航组合和展示策略；它不得重写标准 CRUD、树、权限、租户、动作可用性或运行时流程。Service 也不得为了个别模块复制通用生命周期、数据权限、审计或能力实现。

发现某段代码需要被第二个公共业务以相同语义使用时，优先将事实产生在正确领域层，再通过小型、类型化的平台契约或 adapter 交付；不要把业务 Controller、某个 `*-web` 模块或前端页面变成其他模块的基础依赖。只有确属单一领域事实或单页表达时，才就地治理。抽象必须以减少接入成本和依赖方向混乱为目标，不为假设性的扩展预建框架。

## Service 构造契约

业务 Service 默认保留一个完整构造入口，Spring 装配和手工装配使用同一依赖契约。必需依赖在构造时校验，不得通过短构造方法传入 `null`，再在运行时静默跳过权限、引用、事件或关联清理。迁移旧的手工构造调用时，应补齐依赖；测试装配的便捷入口放在 `testFixtures`，不回流到生产 Service。

确实可选的扩展显式使用 `Optional`；需要延迟发现贡献者、打破初始化依赖的扩展保留 `ObjectProvider`，provider 本身不可缺失，也不得为压缩构造参数而提前求值。只有提供完整、等价默认行为的重载（例如默认时钟）才应保留。不以消除所有构造重载为目标，也不为缩短参数列表引入没有独立职责的依赖容器。

## 取舍原则

1. 保留能力组合、标准模型、标准 DAO、生命周期 hook、静态/动态统一运行时这些核心形态。
2. 避免含义不清的命名、冗余字段、隐式扩展 map 和过长的 service hook。
3. 普通业务接入应足够轻：模型、DAO、Ability、少量 hook、测试证明即可。
4. 平台基础设施可以多走一步，尤其是数据操作、建表、元数据、生命周期和能力组合边界。
5. 不为了拆分而拆分。只有当拆分能减少依赖混乱、复用成本或认知负担时才新增包或模块。
6. 进入业务线前先夯实能力层。基础能力要做到边界清晰、默认好用、动静一致，再承载平台标准业务。

## 长生命周期平台的改进原则

新业务、能力改进和 bug 修复都应以当前目标为切入口，同时审视存量设计和平台的中长期利益。交付既要解决当前问题，也要让平台更容易承接后续业务变化。

1. **往后看，反思存量。** 不把现有实现天然视为正确。追溯问题属于局部实现错误，还是暴露了封装不足、职责错位、重复事实源或已经失效的架构假设；结合实际使用和变更成本，判断哪些应保留、修正或淘汰。沿用既有架构和风格不意味着延续已确认的问题。
2. **往前看，面向长期。** 评估方案是否让公共契约更清晰、动静能力更一致、静态业务接入更自然，是否减少后续重复开发、维护和迁移成本。避免通过新增特例、复制流程或绕过分层换取眼前可用，也不为假想需求预建框架。
3. **按根因和影响确定范围。** 不以 bug 表面大小或最小 diff 限制必要的公共边界修正，也不借局部问题开展无关重构。当前目标内可完成的根因修正应一并推进；明显扩大范围或影响长期方向的调整，先说明收益、风险、兼容性与迁移成本，再与用户确认。
4. **明确取舍和后续责任。** 对发现的问题区分本次解决、后续治理和明确不做，并说明依据。必要的临时措施应说明尚未解决的根因、适用局限和后续处理条件；待治理问题按所属专题或技术债规则记录，不能把临时修补默认为最终设计。
5. **验证当前行为与长期契约。** 用与风险相称的测试覆盖当前场景和关键边界，修正公共根因时关注受影响的其他接入路径。收口时复核同类问题是否仍会迫使下一个业务重复补丁，并说明当前问题的解决结果、存量设计的改善和剩余风险。

## 推进方式

1. 按能力单元或业务单元推进，不追求过小步骤。
2. 一个能力单元应尽量包含公开契约、默认实现、测试证据和必要文档更新。
3. 文档写方向、边界、验收口径；细节行为优先由测试表达。
4. 发现实现别扭时，先判断是不是平台底座抽象不足，不急着在业务层硬编码补丁。
5. 每轮能力收口都要复盘：标准能力是否由平台完整承担、契约是否扎实、业务能否开箱即用并持续获得平台升级。代码量只作为结果观察，不以压缩代码替代职责判断；个性化业务规则和编排应保留在业务层。

## 测试策略

测试遵循“平台能力重测，业务装配轻测，能不 IT 尽量不 IT”。

1. 平台能力已覆盖的通用行为，不在每个业务中重复测试。
2. 身份根、权限、工作流、跨租户、审计、外部写入等特殊且敏感业务，应按风险专项测试。
3. 普通业务按需轻测，优先验证能力装配、业务字段、唯一约束和关键边界。
4. 能用单元测试或契约测试表达清楚的，不升级为 IT。
5. 只有需要验证真实数据库、Spring 装配、事务边界、跨层协议或外部集成时，才保留 IT。

## 非目标记录

非目标不按历史阶段长期保留。某项能力如果暂不进入当前任务，应记录在对应业务专题的边界说明中；如果它是跨专题的基础风险或待决策事项，再进入 [技术债记录](TECHNICAL_DEBT.md)。
