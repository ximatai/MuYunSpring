# 软删除、回收站与删除日志治理

本文定义平台对软删除、业务回收站、级联删除、恢复、唯一键冲突提示和删除运维审计的统一目标契约。

它服务于静态 Java 模型和动态模型的共同生命周期能力。业务模块只声明自己的删除影响范围和自身删除策略；平台负责标准删除入口、递归上下文、记录追溯、恢复编排、审计和交互契约。

本文描述的是目标治理边界，不表示下文所列能力均已实现。

## 生命周期边界

`enabled` 与 `deleted` 解决不同问题，不能互相替代：

| 状态 | 含义 | 常规查询与操作 | 是否可恢复 |
| --- | --- | --- | --- |
| 启用 | 正常业务实体 | 可见、可用 | 不适用 |
| 停用 | 实体仍存在，但暂停业务能力 | 可见；具体能力受限 | 可重新启用 |
| 软删除 | 实体从常规业务视图移出，处于保留期 | 不可见、不可用 | 可恢复 |
| 硬删除 / 最终清理 | 业务实体已物理移除 | 不可见、不可用 | 不可恢复 |

停用用于暂停、冻结、欠费或业务处置；删除用于结束当前数据生命周期。上游范围失效导致下游暂时不可访问，也不等同于删除下游资源。

## 总体原则

1. 平台统一删除入口、上下文、审计与恢复报告；业务模块保持自身数据生命周期主权。
2. 上游显式声明要删除的下游；不根据外键、`tenantId` 或表名自动推断级联。
3. 下游收到级联删除后，自行决定软删除、硬删除、拒绝、跳过，以及是否继续声明其下游删除。
4. 递归能力由标准删除上下文传导形成；平台不预先维护复杂的全局父子策略矩阵。
5. 平台不以数据库外键约束表达或推断删除关系。上游通过业务删除链显式声明下游，资源自身决定拒绝、跳过或继续清理；物理表不应依赖外键约束来决定级联顺序。
6. 只有软删除资源进入对应业务的回收站；硬删除仍进入删除日志，但不可恢复。
7. 恢复是沿删除链的尽力恢复，不跨越中间模块的生命周期决定。
8. 删除链、恢复结果和唯一键冲突必须可解释，不能将数据库异常或静默跳过暴露给操作者。

## 删除与级联契约

业务通过标准删除协调器执行删除。直接删除创建根节点；上游明确调用下游的标准删除入口时，平台传递同一个删除上下文：

```text
A.delete(a)
  -> A 声明删除 B
     -> B.delete(b, context)
        -> B 选择 SOFT 或 HARD，并可声明删除 C
           -> C.delete(c, context)
```

删除上下文至少包含：

- `operationId`：本次删除操作 ID；
- `rootResourceType`、`rootResourceId`：根资源；
- `parentEntryId`：当前级联直接来源；
- `chain`：资源路径，仅用于诊断与防环；

平台可在上下文中附着一次操作的轻量执行会话，用于汇总审计条目；它不承载权限、HTTP 请求、查询条件或业务策略，也不使用 `ThreadLocal` 重建递归关系。

平台必须保证：

1. 同一 `operationId` 内，同一资源至多执行一次，保证幂等。
2. 发现循环依赖时终止该分支并记录明确诊断。
3. 下游失败、拒绝或跳过须形成结构化结果，由上游汇总；事务策略由具体删除协调器按同库事务或跨模块补偿边界确定。
4. 业务模块不通过 `ThreadLocal`、隐式布尔标记或入口层特判识别父级级联，而是消费结构化删除上下文。

## 关系处理口径

是否级联删除由上游业务编码显式声明；下游是否支持软删除由下游自身决定。

| 关系 | 默认处理 | 示例 |
| --- | --- | --- |
| 生命周期从属 | 上游可声明级联删除 | 租户的应用开通配置、角色的授权明细 |
| 范围归属 | 默认不级联删除；上游失效时下游不可访问 | 租户范围内的用户、职员、部门、角色 |
| 普通引用、历史或审计关联 | 不级联删除，保留关联快照 | 操作日志、登录日志、审批历史 |

“范围归属”资源在上游删除后应被权限和租户范围过滤，恢复上游后重新可见；这不要求下游也启用软删除。

普通引用的写入完整性与目标生命周期实现分开处理：新增、恢复和引用值变更时，非空引用必须解析到当前租户范围内可用的目标；该校验不能由引用 title 或业务 service 的重复查询承担。`PRESERVE_HISTORY` 引用在普通更新中可原样保留记录既有的不可用目标，以维护历史事实，但不得新增、替换或重新激活不可用引用；`RESTRICT` 在存在活跃引用方时拒绝目标变为不可用，适用于当前业务关系；`CASCADE_DELETE` 将引用方纳入同一删除链，由引用方自身决定软删或硬删，适用于生命周期从属。策略对标准软删和直接硬删一致生效；最终清理仍按原删除链执行。级联必须显式声明，不从普通引用或数据库字段自动推断。

`@Children` / `@ChildOf` 与动态 `EntityRelationDefinition` 负责聚合载入、嵌套写入和归属字段。父删除始终以子项 FK 的引用完整性为准：仅 `CASCADE_DELETE` 清理子项，`RESTRICT` 阻断，`PRESERVE_HISTORY` 保留。静态模型通过 `@ReferenceTo.integrity` 声明，动态模型通过同一条 `EntityReferenceDefinition.integrity` 声明；关系定义不再拥有独立的级联删除开关。

静态注解原有的 `onTargetSoftDelete` 与 `ReferenceTargetDeletionPolicy` 保留为弃用兼容入口；其 `RESTRICT` 映射为新的 `onTargetUnavailable = RESTRICT`。新代码不得继续使用旧名称，动态元数据只使用新策略。

静态与动态记录引用都由 `@ReferenceTo` / `EntityReferenceDefinition` 编译为同一份 `ReferenceIntegrity` 策略和反向删除关系图。未被声明为引用的流程、审计、配置和快照 ID 继续按其各自业务边界处理，不因字段名以 `Id` 结尾而自动纳入引用治理。

## 回收站与恢复

回收站是业务域入口，不是把全部资源混在一起的全局业务页面：

- 租户管理提供租户回收站；
- 用户管理提供用户回收站；
- 只有启用软删除且有恢复价值的业务接入其回收站。

平台将回收站建模为可选的 `RecycleBinAbility`，它建立在独立可用的 `SoftDeleteAbility` 之上。业务服务只有明确需要向操作者开放已删除数据时才声明该能力，并提供范围与领域校验钩子；平台门面统一完成回收站查询、源删除链资格校验、恢复执行和结果模型。

回收站查询复用对应业务标准列表的字段投影、关联展示、过滤、排序、分页和展开内容；仅将主记录的数据范围切换为已删除记录，并追加删除时间及恢复、彻底删除等生命周期操作。业务不得为回收站维护一套字段缩水的平行列表。

每个接入回收站的软删除资源至少提供两个平台标准操作：

| 操作 | 含义 | 结果 |
| --- | --- | --- |
| 恢复 | 取消当前软删除状态，并沿本次删除链尽力恢复可恢复的下游 | 资源重新进入常规业务视图；返回恢复报告 |
| 彻底删除 | 终止保留期，物理清理当前软删除资源，并沿删除链处理可清理的下游 | 不可恢复；返回清理报告 |

两个操作的 HTTP 回执进入平台统一 `ActionResult`：结构化恢复或清理报告仍作为 `data` 返回，平台根据
根记录展示文本形成标准消息并报告数据变化事实。前端只消费消息和报告，不自行拼接模块级成功文案。

“彻底删除”不是业务页面直接调用 DAO 的物理删除。它必须进入标准 `PURGE` 协调器、创建删除操作日志，并接受独立权限、保留期、二次确认和领域依赖校验。批量彻底删除也必须逐资源产生可审计结果，不能以一条无明细的 SQL 取代。

资源默认不允许彻底删除。静态服务必须显式声明 `isRecycleBinPurgeEnabled()`，并在 `beforeRecycleBinPurge` 中执行资源自己的保留期、权限与依赖校验；动态实体只有在 `RECYCLE_BIN` 元数据能力和等价的 purge 策略同时具备时才可开放该操作。前端仅根据平台返回的 `purgeable` 事实展示操作，不得自行推断可清理性。

恢复根资源时，平台仅尝试恢复满足下列条件的直接下游：

1. 该下游由本次删除操作级联产生；
2. 当前仍处于软删除状态；
3. 未在后续被单独删除、再次删除或产生冲突；
4. 下游模块声明该资源可恢复。

若下游采用硬删除、恢复校验失败或发生唯一键冲突，平台跳过该分支；不会越过它直接恢复更深层子节点。恢复响应必须返回完整报告，至少区分已恢复、不可恢复、跳过和失败及其原因。

彻底删除遵循相同的链路归属约束：清理根资源时，只处理当前仍处于软删除状态、且由该删除链级联产生的下游；不得清理后来独立删除、再次删除、已恢复或仍处于活跃状态的资源。下游模块通过自身标准 `purge` 入口决定是否允许物理清理，并可继续向下传导。遇到不可清理节点时，平台返回清理报告；是否要求根清理整体失败，由该根资源的领域策略显式决定。

恢复和彻底删除允许针对同一个源删除操作续跑。前次尝试已经成功处理的节点视为该分支的已满足前置条件，只继续处理尚未成功的后代；后来发生的独立删除、恢复或其他生命周期变化仍按冲突处理，不能被重试覆盖。彻底删除先校验父节点策略，再按子到父顺序物理清理；只要后代未完成，祖先就继续保留在回收站，确保治理范围和重试入口仍然存在。

## 标准实体与删除日志模型

标准实体的软删除状态字段应保持稳定：

| 字段 | 语义 |
| --- | --- |
| `deleted` | 当前是否处于软删除状态 |
| `deleted_at` | 当前删除发生时间 |
| `deleted_by` | 当前删除执行人 |

`updated_by` 不是 `deleted_by` 的替代：前者表达最后更新人，后者表达删除这一生命周期事实。恢复时清空上述删除状态字段。

删除链和运维审计不应分散到每张业务表。平台建设以下两类事实：

### `platform_deletion_operation`

一条根级操作日志，记录一次 `DELETE`、`RESTORE` 或 `PURGE` 命令：

- `id`、`operation_type`、根资源类型和 ID；
- 操作者、原因、调用来源、租户上下文、发生时间；
- 总体执行状态、结果摘要和关联 trace ID；
- 与原删除操作或原删除条目的关联，适用于恢复和最终清理。

### `platform_deletion_entry`

一条受影响资源明细，记录一次操作波及的每个资源节点：

- `id`、`operation_id`、`parent_entry_id`；
- `resource_module_alias`、`resource_entity_alias`、`resource_record_id`、资源版本；
- `trigger_type`（`DIRECT` / `CASCADE`）；
- `delete_mode`（`SOFT` / `HARD`）；
- 执行状态、失败或跳过原因；
- 可选的脱敏展示快照，用于回收站与日志展示；
- 恢复关联与当前恢复状态。

建议索引：

- `platform_deletion_entry(operation_id, parent_entry_id)`；
- `platform_deletion_entry(resource_type, resource_id, status)`；
- `platform_deletion_operation(operation_type, occurred_at)`；
- 按业务回收站查询需要，可增加 `resource_type + status + occurred_at`。

删除操作日志与影响明细共同构成删除专项流水，不再另建重复的“删除日志表”。平台运行审计只保留动作入口、授权和 trace 线索；删除链负责解释删除影响、策略、恢复和最终清理。

## 恢复资源身份与解析

可恢复资源的稳定身份统一为 `moduleAlias + entityAlias + recordId`。模块 alias 只表达运行时业务边界，不足以在一个模块包含多个实体时定位恢复执行者；`entityAlias` 不是展示字段，也不得由表名或 Java 类名在恢复时临时推断。

静态资源只有实现 `DeletionRecoveryAbility` 后才进入恢复目录；默认从其稳定的 `ReferenceTarget` 推导 `entityAlias`，仅身份确有特殊映射时才覆盖该默认值。普通 `SoftDeleteAbility` 仍可独立使用，不因此承担回收站或恢复责任。动态实体由当前动态运行态提供同一身份，删除日志必须记录其动态实体 alias。级联链上的资源也按相同规则写入完整身份。

恢复解析遵循下列约束：

1. Resolver 必须先声明是否支持该完整资源身份，再返回对应的资源能力。
2. 零个 Resolver 命中时，该条目不可恢复并返回明确原因。
3. 恰好一个 Resolver 命中时，平台才执行资源自身的恢复原语。
4. 多个 Resolver 命中属于平台配置错误，必须中止该分支并报告冲突 Resolver；不得依赖 Spring Bean 注入顺序选择其一。

历史日志若缺少 `resource_entity_alias`，平台不得根据 `moduleAlias` 猜测目标资源；该记录仅保留审计可读性，并应在恢复报告中标记为不可恢复。任何需要治理历史数据的迁移必须显式补齐或确认资源身份，不能在普通恢复请求中隐式完成。

## 标准删除入口覆盖范围

所有通过平台标准删除协调器执行的领域资源删除均应写入删除操作与影响明细，包括无级联的直接删除。

| 场景 | 记录删除日志 | 进入业务回收站 | 可恢复 |
| --- | --- | --- | --- |
| 无级联软删除 | 是 | 是 | 是 |
| 软删除及递归级联 | 是 | 仅软删除资源 | 按删除链尽力恢复 |
| 无级联硬删除 | 是 | 否 | 否 |
| 级联链中的硬删除 | 是 | 否 | 否 |
| 已删除数据的最终清理 | 是，记录 `PURGE` | 否 | 否 |

数据库运维 SQL、缓存淘汰、日志归档、测试清理等非领域资源动作不自动进入此模型；如需留痕，应走对应运维审计或显式的系统清理入口。

## 唯一键冲突与新建提示

常规查询默认过滤软删除资源，新增前的重复校验不能只查询活跃数据。平台应统一执行“含已删除记录”的业务唯一键预检：

| 预检结果 | 响应 |
| --- | --- |
| 存在活跃记录 | 返回普通重复数据错误 |
| 仅存在已删除记录 | 返回 `RESOURCE_SOFT_DELETED_CONFLICT`，说明资源位于回收站并提供恢复定位信息 |
| 不存在记录 | 允许创建 |

禁止因发现软删除记录而自动恢复。新建代表新的生命周期，恢复代表继承原数据、配置和审计记录，必须由操作者明确选择。

租户 ID 是权限、数据隔离、路由和审计链路的重要标识：在保留期内不可复用，应引导操作者恢复原租户而非重新创建。
在平台尚未形成覆盖全部 tenant-scoped 数据的归档或清理治理前，租户根资源不得彻底删除；租户 alias 不能因物理清理而被重新分配给新的隔离边界。

## 权限、审计与安全

删除、回收站查询、恢复和最终清理分别具备独立动作权限。回收站查询开启独立数据权限，并定义当前操作者能够治理的根资源范围；恢复和最终清理只定义动作资格，执行时复用回收站查询的数据范围，不再形成两套相互漂移的治理边界。级联子节点继承根资源的治理结论，不单独扩大范围。前端按查询权限控制回收站入口，并按恢复、最终清理权限分别控制操作按钮。展示快照必须遵循字段保护和脱敏规则。

彻底删除默认应受资源保留期约束，并要求显式二次确认；涉及审计、流程、财务、外部引用或合规保留的数据，由领域模块拒绝清理或改为受控归档。平台不将“进入回收站”自动等价为“可以立即物理删除”。

删除操作与恢复操作保留独立的不可覆盖审计事实。删除影响明细不保存完整业务表单快照或敏感原文，只保存业务恢复、诊断和可识别展示所必需的摘要。

## 接入要求

业务模块启用软删除时，应完成以下接入：

1. 确认该资源自身采用软删除还是硬删除；仅在需要面向操作者治理已删除数据时声明 `RecycleBinAbility`。
2. 明确声明删除时需要调用的下游资源，不依赖数据库关系猜测。
3. 为新增与恢复提供业务唯一键冲突预检。
4. 定义回收站范围、恢复权限和恢复前领域校验；Controller 通过平台回收站 Web 适配暴露标准动作，不自行编排日志或恢复流程。
5. 为删除、级联、恢复、硬删分支、冲突和重复调用提供契约测试。
