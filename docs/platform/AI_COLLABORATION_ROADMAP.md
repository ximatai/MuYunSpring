# AI 应用建设与业务协作专项规划

## 定位与目标

MuYunSpring 是用于建设企业业务系统的动静一体平台。本专项围绕两条价值线推进：

- **AI 辅助建设应用**：帮助开发者、实施人员和业务配置人员理解已有定义，形成可审阅、可校验、可维护的配置变更。
- **应用支持人机协作**：让按平台规范接入的业务能力，同时服务页面、助手和按需建设的自动化执行。

长期目标是业务声明一次，平台从同一事实源形成可交互、可发现、可校验、可授权执行和可验证结果的能力。静态 Java 与动态元数据继续共享业务规则和运行链路；普通业务不因接入助手而重复实现 CRUD、权限、校验或专用助手流程。

本文同时规划业务能力与技术加固，记录建设目标、阶段顺序与验收边界，不代表后续能力已经交付，也不预设新的 Gradle 子项目、Agent 框架或执行引擎。

## 与现有专项的关系

[智能助手能力融合专项治理](AI_ASSISTANT_GOVERNANCE.md) 负责当前工作台助手的具体分层、Surface、能力调用、交互和场景验收。该文档中的三个实施阶段保持原义，与本文五个建设阶段不是同一编号体系。

本文是跨专题建设路线，当前助手专项是其中的已有基础。后续进入具体能力建设时，由所属专题补齐正式契约与验证，再由助手接入；本文不直接放开现有自动保存、配置发布、跨会话恢复或后台执行边界。

| 领域 | 继续拥有的职责 |
| --- | --- |
| Ability、模型与动态运行态 | 业务对象、关系、数据访问、字段约束、生命周期与动静一致性 |

| 后台执行与外部接入专题 | 真实需求触发后的执行身份、幂等、进度、恢复与接入协议 |

## 存量基础与能力边界

当前可复用的基础包括动静统一的能力链、已编译页面描述与执行计划、助手 Surface 与调用令牌、标准查询与草稿修改、元数据 change-set、工作流任务及动作结果机制。具体实现范围和验收状态以各专题及测试为准。

建设中必须保留以下区别：

1. 当前助手主要围绕浏览器页面协作，不是已具备持久任务的后台智能体。
2. 浏览器草稿、持久配置候选与已生效配置是不同状态；普通元数据保存可能影响 schema 和运行态，不能作为无副作用草稿入口。
3. 元数据 change-set 与页面修订各有治理边界，不代表整个模块具有统一原子发布能力。
4. 配置包归档与版本指针不等于实际配置发布、运行态切换或数据回滚，见[配置治理专题](topics/governance/OVERVIEW.md)。
5. 能力发现、模型建议和前端确认不产生业务权限；执行时继续由后端校验。

## 技术治理原则

平台尚未上线，按无需承担上线系统兼容与过渡成本的前提推进技术调整，以长期契约正确、职责清晰和业务接入轻量为优先，不以保留现状或最小 diff 为默认目标。需要修正公共抽象时，同步修改调用方和测试，删除失效实现；不为旧契约增加无必要的兼容构造、可选字段、静默 fallback 或平行运行链。

保留动静一体、模型网关、受控 Surface、统一业务入口和编译后运行的核心方向。重构围绕已出现的职责混合、事实重复与执行歧义展开，不以文件长度、追求形式统一或未来可能扩展为理由预建框架。

### 模型消息与工具回合

模型输入应具有供应商无关的结构化消息契约，明确区分用户消息、助手文本、助手工具调用、关联调用 ID 的工具结果，以及当前上下文快照。供应商 adapter 负责映射具体协议，不将业务执行语义压入模型网关。

第一阶段将能力结果从用户消息迁入原生工具回合，最新页面事实与历史结果分开组织。工具调用与结果必须保持配对，历史中的工具名称与内部能力身份保持稳定映射，不能依赖当前目录顺序重新解释。上下文与工具结果始终是受限数据，不因使用原生工具消息而成为授权事实或可信指令。

该契约是第一阶段的技术基础。模型回归分别记录目标完成情况与失败类别；尚无同模型、同场景的 token 或费用对照，不承诺仅改变消息格式即可消除模型偏航。

### 能力声明与参数契约

能力说明负责帮助模型理解，类型化执行契约负责帮助平台治理。优先为当前查询、导航、草稿修改和预检表达必要的效果类型、执行边界、结果类型及重试条件；正式业务写入按第三阶段扩展，不一次性设计全部能力分类。

这些事实来自可信的能力实现或受治理配置，不由模型指定。标准参数描述与输入解析应尽量由同一份类型定义产生；业务状态、权限及领域校验仍由正式执行入口承担。不能仅凭“可重试”标签推定幂等，也不要求业务模块重复声明平台已经知道的字段与动作事实。

### 执行事实与交互状态

执行结果必须将两个维度分开：

| 维度 | 需要表达的事实 |
| --- | --- |
| 能力执行 | 未执行、草稿已改变、持久化已提交、部分完成或结果未知 |
| 交互终止 | 正常结束、等待用户、取消、上下文失效、模型失败或达到步骤上限 |

具体类型在实施时按真实场景收敛，不以单个 `completed` 或异常同时代表两个维度。模型停止调用工具只表示本轮停止，业务目标完成须有独立证据。

页面效果已经发生后，即使取消、等待失败或结果过期，也要保留有界执行事实，并按原作用域隔离，不向新的身份或租户展示旧结果。停止后续执行、丢弃过期输出与撤销已发生操作是不同语义。

第一阶段先完善页面效果与回合结果。第三阶段开放持久化动作前，必须为选定动作补齐请求身份、服务端幂等与结果查询：断流不能推定未提交，模型总结失败不能丢失业务回执，浏览器成功调用去重不能替代服务端幂等。未知结果先核实，不盲目重试；不因此提前将所有只读或草稿能力持久化为后台任务。

### 会话控制、能力执行与展示分离

会话控制器负责输入、历史、澄清、运行、等待、取消及终止原因；能力运行时负责能力目录、调用令牌、执行和结果；面板只承担展示与用户操作。优先使用显式状态与转换函数，不预设引入状态机框架。

面板通过有限的结构化结果协议展示草稿差异、候选、预检和回执，不按具体能力编码解析业务输出。新增能力应贡献结果语义或受控展示适配，而不要求修改通用面板或助手主循环。沿用当前页面会话和过期调用控制，不为抽离职责复制第二套状态事实。

### 页面能力与领域能力分层

浏览器 Surface 继续负责导航、未保存草稿和页面交互，不整体迁移到后端。后续服务端工具承担授权后的业务查询与正式领域动作，不模拟打开页面，不依赖浏览器状态。

两类能力共享必要的业务身份与结果语义，但保留各自执行上下文。领域事实应位于正确的领域契约中，不能直接将含页面语义的 `ModuleExecutionPlan` 下沉为通用工具模型，也不能让领域模块反向依赖 Web 层。

当前浏览器提供能力目录只用于模型规划并交回原 Surface 执行。引入服务端工具时，必须从服务端可信目录解析执行目标，重新验证身份、参数、权限与作用域；不能把客户端能力描述变成服务端执行授权。以第一个真实服务端场景验证该边界，不预建统一工具大内核。

### 错误分类与模型接入治理

能力错误应具有稳定类别，区分非法参数、候选不唯一、缺少输入、上下文过期、授权或业务条件不满足、暂时不可用与执行结果未知。返回经过筛选的修正信息，避免原始异常泄露，也避免所有失败只剩下无法处理的通用文案。重试由运行时和能力执行策略约束，不让模型仅凭错误文本决定。

保留模型网关、凭据隔离和并发保护。逐步显式表达并验证工具调用、流式工具、参数与 Schema 支持范围、结束状态、使用量和取消行为；供应商不支持的能力应明确拒绝或按已定义策略降级，不能以提示词弥补协议差异。真实使用量不可用时保持未知，不将字符数冒充 token 或计费数据。

诊断沿用户目标、模型回合、能力调用与业务动作关联，记录耗时、失败类别及执行状态，不默认持久化完整业务正文。继续复用既有诊断事件与审计边界，按场景补齐证据，不另建重型观测平台。

## 建设阶段

阶段表示能力依赖与投入顺序，不是固定排期。第一、第二阶段的本期范围已完成，第三阶段尚未启动；后续阶段按完整场景逐项启动，不因列入路线而提前建设全部基础设施。

技术加固嵌入同一阶段路线，不另设与业务脱节的全面重构期：

| 技术推进顺序 | 对应阶段与门槛 |
| --- | --- |
| 先统一消息与工具结果协议、执行事实和错误分类 | 第一阶段优先完成，作为继续扩充能力的基础 |
| 收敛会话控制、能力契约与标准结果展示 | 随第一阶段完成，并支撑第二阶段配置协作 |
| 用一个正式业务动作验证确认、版本、幂等与结果核实 | 第三阶段开放持久化操作前必须通过 |
| 建设领域工具入口、后台执行和外部协议 | 由真实场景触发，支撑第四、第五阶段所需能力 |

| 阶段 | 建设目标 | 进入与推进依据 |
| --- | --- | --- |
| 一：共同基础 | 标准业务自然获得一致的助手能力 | 收口现有查询、草稿与元数据候选链路，补齐真实场景验收 |
| 二：辅助建设应用 | 自然语言形成可治理的应用配置变更 | 复用第一阶段能力，按配置专题逐块推进 |
| 三：受控业务操作 | 助手可靠地完成明确业务动作 | 选定动作具有正式执行、确认与结果契约 |
| 四：业务任务协作 | 人与助手共同推进并检查完整任务 | 由真实任务办理场景牵引，复用工作流与完成判定 |
| 五：后台与外部协作 | 同一业务能力服务页面外执行者 | 明确需要脱离页面、恢复执行或外部智能体接入 |

### 第一阶段：夯实共同基础

**目标**：新增普通业务模块时，基础助手能力随标准平台接入自然获得，静态与动态保持一致。

**建设思路**：

1. 从已有字段、关系、查询、动作、权限和页面状态推导助手可消费的受控描述；不维护另一套独立业务事实。
2. 标准能力自动投影，业务仅补充无法推导的含义、适用场景和特有结果语义。说明文本不替代领域规则，也不成为授权依据。
3. 收口当前导航、范围选择、查询、草稿填写和元数据字段候选的组合场景，保持正式入口、敏感字段裁剪和过期调用失效机制。
4. 同时建立确定性契约验证与少量真实模型场景回归，分别观察平台边界和实际目标完成质量。
5. 按技术治理原则先统一消息、能力结果和错误契约，再收敛会话控制与展示职责；同步更新调用方，不保留失效的双重协议。

**验收口径**：一个标准静态模块与一个动态模块无需修改助手主循环即可完成查询、引用选择和受支持字段的草稿填写；用户修改或切换上下文后旧调用不能覆盖新状态；未保存和失败状态必须如实呈现。

**状态：已完成。** 已交付原生工具消息及稳定身份、受控效果与安全错误、执行事实和终止原因分离、会话控制器及通用结果展示；同时修复了真实验收发现的流读取期限缺口和动态页面快捷搜索语义偏差。正式契约见[助手专项](AI_ASSISTANT_GOVERNANCE.md#共同基础的执行与消息契约)。

| 验收场景 | 已验证结果 |
| --- | --- |
| 标准静态职员模块 | 机构范围与姓名包含筛选匹配既有记录；姓名、编号及部门引用进入可见未保存草稿，取消后不保存 |
| 动态考试模块 | 名称包含筛选匹配数学测评；名称、日期、教学班及学科引用经同一标准 Surface 填入未保存草稿 |
| 元数据候选 | 普通可选字段进入真实候选编辑器，标准预检结果直接展示，取消后不产生物理列 |
| 故障与隔离 | 确定性测试覆盖工具配对、迟到结果、上下文变化、效果后的取消/异常、未知结果、只读越界和重复失败 |

上述业务样本已通过真实浏览器与已配置模型验证；完整后端验证、前端单元/组件/浏览器测试、类型检查、构建及发布包消费者验证通过。真实模型仍可能产生非中文进展或不理想说明，样本通过不等于跨模型稳定性保证；阶段一没有开放自动保存、配置生效或后台持久任务。

本阶段不建设通用服务端工具目录或企业知识图谱。未来服务端能力需要共享事实时，应在正确领域提炼窄契约，不反向依赖含页面语义的 Web 执行计划。

### 第二阶段：让 AI 辅助建设应用

**目标**：开发者与配置人员用自然语言辅助搭建和修改应用，产物可审阅、可验证并可持续维护。

**建设思路**：

1. 采用“需求—候选—差异与影响—校验预览—确认生效”的链路，优先完成既有动态模块的元数据变更，再进入受模板约束的页面配置。
2. 规则与动作配置按各自专题后续扩展；每类配置先具备正式候选、校验、生效和失败契约，再接入助手。
3. 用户可以直接修改或取消候选。预览结果必须对应实际候选与基线版本，候选或基线变化后重新校验。
4. 配置声明由平台编译并执行；模型不直接修改生效配置、执行任意 DDL 或绕过治理入口。

**验收口径**：选定配置场景中，用户能看到具体变化、依赖和真实影响，修改与取消均符合草稿语义；过期候选不能生效；失败不能报告发布成功。

跨字段、页面和规则的组合变更先明确依赖、顺序及部分失败处理，不承诺跨专题原子发布与自动回滚。Java 业务代码继续经过代码审查、编译和测试，不并入在线配置执行。

**状态：本期范围已完成（元数据候选与已有字段页面编排）。** 已有动态模块的单字段候选支持差异读取、普通字段连续修订、手工修改后的重新预检，以及人工确认前后的候选保护；正式 change-set 继续负责指纹、版本与事务验证。保存后生效状态查询或页面刷新失败不会抹去已保存事实。契约见[元数据候选协作与人工生效](AI_ASSISTANT_GOVERNANCE.md#元数据候选协作与人工生效)。

当前支持已有动态模块、同一元数据节点下的多字段新增方案（每批 1–12 项），可组合普通字段、模块引用和字典绑定；全部解析通过后一次进入现有编辑会话，逐项修改或移除，统一预检并人工确认。方案不包含批量修改存量字段、跨节点依赖编排或删除操作。页面配置已接入受模板约束的候选协作：读取当前模板与字段目录，调整已有字段的列表、表单及独立详情根投放与展示属性，配置快速查询；保留分组、关联、动作和未指定配置，复用只读预览与人工发布。第二阶段以元数据和已有字段页面编排两个闭环收口；规则与动作配置留在所属专题后续建设，不作为进入第三阶段的前置条件。不承诺跨专题自动建应用或原子发布。

已通过确定性测试覆盖手工编辑投影、原候选改名、确认期间变更和提交后刷新失败；真实 PostgreSQL 路径验证旧指纹/旧基线拒绝及重新预检后的物理列生效。真实模型与浏览器已验证候选生成、保留手工名称后修改索引及预检回执。模型仍可能多余澄清或在候选生成后说明失败；页面保留真实候选与执行事实，不能由样本通过推定自主完成质量稳定。

连续场景已通过真实模型、浏览器和 PostgreSQL 验收：多字段候选经人工确认落地后，返回保留草稿的页面配置，最新字段可被助手投放至列表、表单和快速查询，原有人工展示标题与子表保持；页面再次人工确认生效后，正式业务列表与表单消费新配置。目录加载失败及忙碌期间返回页签的恢复、旧调用拒绝、字段只读策略保留和发布失败后的候选保留由确定性回归覆盖。两个确认点分别承担本专题生效责任，页面候选放弃或发布失败不撤销已提交元数据。

### 第三阶段：让助手完成受控业务操作

**目标**：在明确的动作范围内，从辅助填写推进到正式业务执行，保持与手工操作相同的规则。

**建设思路**：

1. 从少量完整业务动作切入，形成“识别动作—补齐参数—具体提议—必要确认—执行校验—正式执行—真实回执”的闭环。
2. 区分参数检查、动作可用性、领域影响预览与正式执行。仅在领域明确支持时提供影响预览，不以执行后回滚模拟通用试运行。
3. 动作按钮和助手消费相同业务动作事实；模型负责理解和提出候选，确定性程序负责约束与执行。
4. 确认对应具体对象、参数和适用版本；执行前重新检查权限、租户、数据范围和业务状态。复用动作结果与数据变化事实表达结果。
5. 为选定持久化动作落实服务端幂等与结果核实，明确取消、断流和超时后的提交状态；前端去重与确认卡片不能承担这两个职责。

**验收口径**：手工与助手执行遵守相同领域规则；过期或变更后的提议不能沿用旧确认；取消、失败和重复调用具有明确处理；模型总结失败不能掩盖真实执行结果。

本阶段先沿现有页面运行器推进。正式能力交付前，当前“助手不自动保存”的边界保持不变；面向业务的执行确认与工作流审批不能相互替代。具体结果契约见[动作结果与数据变更契约](ACTION_RESULT_AND_DATA_CHANGE.md)。

### 第四阶段：围绕业务任务组织人机协作

**目标**：人和助手围绕业务任务持续协作，减少用户逐步指挥，并能验证任务是否完成。

**建设思路**：

1. 复用模块任务的完成检查与工作流的办理、审批和流转能力，为助手提供未完成项、合法处理入口和当前办理上下文。
2. 助手解释缺失项、定位数据并准备处理结果；需要人工判断时交接，处理后由领域重新检查完成条件。
3. 复用变更对比、候选选择、动作提议、完成检查和执行回执等有限交互组件，不开放任意生成式业务页面。

**验收口径**：一个完整任务能由人与助手交接处理，完成结论来自领域事实或明确的人工决定；助手不能自行越过办理权、审批或流转条件。

助手交互状态、业务任务状态和后台执行状态分别归所属领域，不以一张通用 Task 表替代。模块完成项也不升级为具有办理人和委托语义的审批待办。边界见[工作流与任务专题](topics/workflow-task/OVERVIEW.md)和[页面交互概览](topics/page/interaction/OVERVIEW.md)。

### 第五阶段：按需扩展后台与外部协作

**目标**：让已形成的业务能力在明确授权下服务后台自动化和外部智能体。

**触发条件与思路**：真实场景需要关闭页面后继续执行、跨会话恢复、长耗时处理或外部调用时，再按专题补齐执行身份、授权、幂等、进度、重试、恢复、取消及结果检查。需要互操作时再评估 MCP 等协议，协议适配继续调用正式业务能力。

**验收口径**：选定场景脱离浏览器后仍具有明确责任主体和执行状态；失败可定位、重复执行可控、恢复不绕过现行权限与业务约束。

本阶段只保留建设方向，不预选执行引擎，不自动将所有 API 暴露为工具，不建设自主多智能体系统。具体设计由[后台任务与异步批次边界](BACKGROUND_JOB_AND_BATCH_BOUNDARY.md)和[外部写入接入边界](EXTERNAL_WRITE_BOUNDARY.md)约束。

## 验证与阶段收口

每阶段围绕一个完整目标交付公开契约、默认实现、必要测试与专题文档。共用以下判断：

- 平台是否减少了下一个业务的接入代码与重复声明，且保留静态 Java 接入的直观性。
- 静态与动态是否使用同一能力语义；短期单侧限制是否明确记录。
- 人工与助手是否经过相同正式业务链路，模型失败是否有真实可理解的反馈。
- 成功是否由实际草稿、配置生效、业务状态或执行结果证明，而不是由模型文本证明。

确定性契约测试覆盖权限、范围、字段保护、版本、取消和结果语义；涉及真实数据、配置生效或事务边界时补真实路径测试。模型场景回归记录目标完成情况、调用次数、耗时和失败分类，不能以测试替身通过推定真实模型体验达标。

技术加固优先验证故障与并发交界：工具调用及结果配对、效果发生后的取消或断流、用户修改草稿后的迟到响应、动态配置更新后的旧能力调用，以及非法参数和重复调用。进入持久化动作时增加真实提交后响应丢失、相同请求重试与未知结果核实的契约；不以正常链路成功替代这些门槛。

近期优先复用[教学管理演示](../architecture/EDUCATION_DEMO_SCENARIO.md)验证静态主数据与动态测评的共同接入，以及既有动态模块的字段候选治理。演示仅承担平台验收，不为展示路线一次性扩成完整业务套件。

各阶段完成后将稳定契约归入所属专题，本文维护阶段状态、依赖与未完成边界，不记录执行流水。新增框架、发布机制或跨专题执行能力，应在进入相应阶段时重新评估收益、维护成本和验证范围。
