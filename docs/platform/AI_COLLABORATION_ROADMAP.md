# AI 应用建设与业务协作专项规划

## 定位与目标

MuYunSpring 是用于建设企业业务系统的动静一体平台。本专项围绕两条价值线推进：

- **AI 辅助建设应用**：帮助业务人员、实施人员和开发者从业务目标逐步澄清范围、形成建设方案，再落为可审阅、可校验、可维护的配置变更。字段与页面候选是执行能力，不是要求普通用户掌握的需求表达方式。
- **应用支持人机协作**：让按平台规范接入的业务能力，同时服务页面、助手和按需建设的自动化执行。用户应能在对话中审阅、确认、执行和检查结果，页面承担可选的详细查看与编辑，不要求用户为每个步骤离开对话。

长期目标是业务声明一次，平台从同一事实源形成可交互、可发现、可校验、可授权执行和可验证结果的能力。静态 Java 与动态元数据继续共享业务规则和运行链路；普通业务不因接入助手而重复实现 CRUD、权限、校验或专用助手流程。

本文同时规划业务能力与技术加固，记录建设目标、阶段顺序与验收边界，不代表后续能力已经交付，也不预设新的 Gradle 子项目、Agent 框架或执行引擎。

## 与现有专项的关系

[智能助手能力融合专项治理](AI_ASSISTANT_GOVERNANCE.md) 负责当前工作台助手的具体分层、Surface、能力调用、交互和场景验收。该文档中的三个实施阶段保持原义，与本文五个建设阶段不是同一编号体系。

本文是跨专题建设路线，当前助手专项是其中的已有基础。后续进入具体能力建设时，由所属专题补齐正式契约与验证，再由助手接入；本文区分现有交付与规划能力：对话内确认执行、建设方案保存与恢复须补齐各自契约后开放；不因规划完成而直接放开现有自动保存、配置发布或后台执行边界。

| 领域 | 继续拥有的职责 |
| --- | --- |
| Ability、模型与动态运行态 | 业务对象、关系、数据访问、字段约束、生命周期与动静一致性 |
| 页面交付与交互 | descriptor、查询、表单草稿、候选选择和正式页面操作 |
| 助手 | 目标理解、必要澄清、能力组合、受控交互与回合衔接 |
| 配置与治理 | 配置候选、校验、影响预览、生效及失败处理 |
| 动作、身份权限与审计 | 动作语义、执行授权、租户与数据范围、执行事实 |
| 工作流与业务任务 | 办理权、业务完成判定、审批与流程流转 |
| 后台执行与外部接入专题 | 真实需求触发后的执行身份、幂等、进度、恢复与接入协议 |

## 存量基础与能力边界

当前可复用的基础包括动静统一的能力链、已编译页面描述与执行计划、助手 Surface 与调用令牌、标准查询与草稿修改、元数据 change-set、工作流任务及动作结果机制。具体实现范围和验收状态以各专题及测试为准。

建设中必须保留以下区别：

1. 当前助手主要围绕浏览器页面协作，不是已具备持久任务的后台智能体。
2. 浏览器草稿、持久配置候选与已生效配置是不同状态；普通元数据保存可能影响 schema 和运行态，不能作为无副作用草稿入口。
3. 元数据 change-set 与页面修订各有治理边界，不代表整个模块具有统一原子发布能力。
4. 配置包归档与版本指针不等于实际配置发布、运行态切换或数据回滚，见[配置治理专题](topics/governance/OVERVIEW.md)。
5. 能力发现、模型建议和前端确认不产生业务权限；执行时继续由后端校验。

## 技术治理原则

平台尚未上线，按无需承担上线系统兼容与过渡成本的前提推进技术调整，以长期契约正确、职责清晰和业务接入轻量为优先，不以保留现状或最小 diff 为默认目标。需要修正公共抽象时，同步修改调用方和测试，删除失效实现；不为旧契约增加无必要的兼容构造、可选字段、静默 fallback 或平行运行链。

保留动静一体、模型网关、受控 Surface、统一业务入口和编译后运行的核心方向。重构围绕已出现的职责混合、事实重复与执行歧义展开，不以文件长度、追求形式统一或未来可能扩展为理由预建框架。

### 模型消息与工具回合

模型输入应具有供应商无关的结构化消息契约，明确区分用户消息、助手文本、助手工具调用、关联调用 ID 的工具结果，以及当前上下文快照。供应商 adapter 负责映射具体协议，不将业务执行语义压入模型网关。

第一阶段将能力结果从用户消息迁入原生工具回合，最新页面事实与历史结果分开组织。工具调用与结果必须保持配对，历史中的工具名称与内部能力身份保持稳定映射，不能依赖当前目录顺序重新解释。上下文与工具结果始终是受限数据，不因使用原生工具消息而成为授权事实或可信指令。

该契约是第一阶段的技术基础。模型回归分别记录目标完成情况与失败类别；尚无同模型、同场景的 token 或费用对照，不承诺仅改变消息格式即可消除模型偏航。

### 能力声明与参数契约

能力说明负责帮助模型理解，类型化执行契约负责帮助平台治理。优先为当前查询、导航、草稿修改和预检表达必要的效果类型、执行边界、结果类型及重试条件；正式业务写入按第三阶段扩展，不一次性设计全部能力分类。

这些事实来自可信的能力实现或受治理配置，不由模型指定。标准参数描述与输入解析应尽量由同一份类型定义产生；业务状态、权限及领域校验仍由正式执行入口承担。不能仅凭“可重试”标签推定幂等，也不要求业务模块重复声明平台已经知道的字段与动作事实。

### 执行事实与交互状态

执行结果必须将两个维度分开：

| 维度 | 需要表达的事实 |
| --- | --- |
| 能力执行 | 未执行、草稿已改变、持久化已提交、部分完成或结果未知 |
| 交互终止 | 正常结束、等待用户、取消、上下文失效、模型失败或达到步骤上限 |

具体类型在实施时按真实场景收敛，不以单个 `completed` 或异常同时代表两个维度。模型停止调用工具只表示本轮停止，业务目标完成须有独立证据。

页面效果已经发生后，即使取消、等待失败或结果过期，也要保留有界执行事实，并按原作用域隔离，不向新的身份或租户展示旧结果。停止后续执行、丢弃过期输出与撤销已发生操作是不同语义。

第一阶段先完善页面效果与回合结果。第三阶段开放持久化动作前，必须为选定动作补齐请求身份、服务端幂等与结果查询：断流不能推定未提交，模型总结失败不能丢失业务回执，浏览器成功调用去重不能替代服务端幂等。未知结果先核实，不盲目重试；不因此提前将所有只读或草稿能力持久化为后台任务。

### 会话控制、能力执行与展示分离

会话控制器负责输入、历史、澄清、运行、等待、取消及终止原因；能力运行时负责能力目录、调用令牌、执行和结果；面板只承担展示与用户操作。优先使用显式状态与转换函数，不预设引入状态机框架。

面板通过有限的结构化结果协议展示草稿差异、候选、预检和回执，不按具体能力编码解析业务输出。新增能力应贡献结果语义或受控展示适配，而不要求修改通用面板或助手主循环。沿用当前页面会话和过期调用控制，不为抽离职责复制第二套状态事实。

### 页面能力与领域能力分层

浏览器 Surface 继续负责导航、未保存草稿和页面交互，不整体迁移到后端。后续服务端工具承担授权后的业务查询与正式领域动作，不模拟打开页面，不依赖浏览器状态。

两类能力共享必要的业务身份与结果语义，但保留各自执行上下文。领域事实应位于正确的领域契约中，不能直接将含页面语义的 `ModuleExecutionPlan` 下沉为通用工具模型，也不能让领域模块反向依赖 Web 层。

当前浏览器提供能力目录只用于模型规划并交回原 Surface 执行。引入服务端工具时，必须从服务端可信目录解析执行目标，重新验证身份、参数、权限与作用域；不能把客户端能力描述变成服务端执行授权。以第一个真实服务端场景验证该边界，不预建统一工具大内核。

### 错误分类与模型接入治理

能力错误应具有稳定类别，区分非法参数、候选不唯一、缺少输入、上下文过期、授权或业务条件不满足、暂时不可用与执行结果未知。返回经过筛选的修正信息，避免原始异常泄露，也避免所有失败只剩下无法处理的通用文案。重试由运行时和能力执行策略约束，不让模型仅凭错误文本决定。

保留模型网关、凭据隔离和并发保护。逐步显式表达并验证工具调用、流式工具、参数与 Schema 支持范围、结束状态、使用量和取消行为；供应商不支持的能力应明确拒绝或按已定义策略降级，不能以提示词弥补协议差异。真实使用量不可用时保持未知，不将字符数冒充 token 或计费数据。

诊断沿用户目标、模型回合、能力调用与业务动作关联，记录耗时、失败类别及执行状态，不默认持久化完整业务正文。继续复用既有诊断事件与审计边界，按场景补齐证据，不另建重型观测平台。

## 建设阶段

阶段表示能力依赖与投入顺序，不是固定排期。第一、第二阶段的本期范围已完成；第三阶段的简单应用工程链路已形成，面向非 IT 用户的使用体验尚未收口；后续阶段按完整场景逐项启动，不因列入路线而提前建设全部基础设施。

技术加固嵌入同一阶段路线，不另设与业务脱节的全面重构期：

| 技术推进顺序 | 对应阶段与门槛 |
| --- | --- |
| 先统一消息与工具结果协议、执行事实和错误分类 | 第一阶段优先完成，作为继续扩充能力的基础 |
| 收敛会话控制、能力契约与标准结果展示 | 随第一阶段完成，并支撑第二阶段配置协作 |
| 用一次表单保存验证对话内确认、版本、幂等与结果核实 | 第三阶段开放持久化操作前必须通过，随后复用于配置生效 |
| 建设可修订业务方案与受治理的逐步落地链路 | 第三阶段以简单应用建设牵引，不等待所有业务动作开放 |
| 建设领域工具入口、后台执行和外部协议 | 由真实场景触发，支撑第四、第五阶段所需能力 |

| 阶段 | 建设目标 | 进入与推进依据 |
| --- | --- | --- |
| 一：共同基础 | 标准业务自然获得一致的助手能力 | 收口现有查询、草稿与元数据候选链路，补齐真实场景验收 |
| 二：辅助建设应用 | 自然语言形成可治理的应用配置变更 | 复用第一阶段能力，按配置专题逐块推进 |
| 三：对话内受控执行与应用建设 | 用户在对话中确认执行，并从业务目标逐步建成可用模块 | 先完成可靠保存，再贯通业务方案、配置候选与正式生效 |
| 四：业务任务协作 | 人与助手共同推进并检查完整任务 | 由真实任务办理场景牵引，复用工作流与完成判定 |
| 五：后台与外部协作 | 同一业务能力服务页面外执行者 | 明确需要脱离页面、恢复执行或外部智能体接入 |

### 第一阶段：夯实共同基础

**目标**：新增普通业务模块时，基础助手能力随标准平台接入自然获得，静态与动态保持一致。

**建设思路**：

1. 从已有字段、关系、查询、动作、权限和页面状态推导助手可消费的受控描述；不维护另一套独立业务事实。
2. 标准能力自动投影，业务仅补充无法推导的含义、适用场景和特有结果语义。说明文本不替代领域规则，也不成为授权依据。
3. 收口当前导航、范围选择、查询、草稿填写和元数据字段候选的组合场景，保持正式入口、敏感字段裁剪和过期调用失效机制。
4. 同时建立确定性契约验证与少量真实模型场景回归，分别观察平台边界和实际目标完成质量。
5. 按技术治理原则先统一消息、能力结果和错误契约，再收敛会话控制与展示职责；同步更新调用方，不保留失效的双重协议。

**验收口径**：一个标准静态模块与一个动态模块无需修改助手主循环即可完成查询、引用选择和受支持字段的草稿填写；用户修改或切换上下文后旧调用不能覆盖新状态；未保存和失败状态必须如实呈现。

**状态：已完成。** 已交付原生工具消息及稳定身份、受控效果与安全错误、执行事实和终止原因分离、会话控制器及通用结果展示；同时修复了真实验收发现的流读取期限缺口和动态页面快捷搜索语义偏差。正式契约见[助手专项](AI_ASSISTANT_GOVERNANCE.md#共同基础的执行与消息契约)。

| 验收场景 | 已验证结果 |
| --- | --- |
| 标准静态职员模块 | 机构范围与姓名包含筛选匹配既有记录；姓名、编号及部门引用进入可见未保存草稿，取消后不保存 |
| 动态考试模块 | 名称包含筛选匹配数学测评；名称、日期、教学班及学科引用经同一标准 Surface 填入未保存草稿 |
| 元数据候选 | 普通可选字段进入真实候选编辑器，标准预检结果直接展示，取消后不产生物理列 |
| 故障与隔离 | 确定性测试覆盖工具配对、迟到结果、上下文变化、效果后的取消/异常、未知结果、只读越界和重复失败 |

上述业务样本已通过真实浏览器与已配置模型验证；完整后端验证、前端单元/组件/浏览器测试、类型检查、构建及发布包消费者验证通过。真实模型仍可能产生非中文进展或不理想说明，样本通过不等于跨模型稳定性保证；阶段一没有开放自动保存、配置生效或后台持久任务。

本阶段不建设通用服务端工具目录或企业知识图谱。未来服务端能力需要共享事实时，应在正确领域提炼窄契约，不反向依赖含页面语义的 Web 执行计划。

### 第二阶段：让 AI 辅助建设应用

**目标**：开发者与配置人员用自然语言辅助搭建和修改应用，产物可审阅、可验证并可持续维护。

**建设思路**：

1. 采用“需求—候选—差异与影响—校验预览—确认生效”的链路，优先完成既有动态模块的元数据变更，再进入受模板约束的页面配置。
2. 规则与动作配置按各自专题后续扩展；每类配置先具备正式候选、校验、生效和失败契约，再接入助手。
3. 用户可以直接修改或取消候选。预览结果必须对应实际候选与基线版本，候选或基线变化后重新校验。
4. 配置声明由平台编译并执行；模型不直接修改生效配置、执行任意 DDL 或绕过治理入口。

**验收口径**：选定配置场景中，用户能看到具体变化、依赖和真实影响，修改与取消均符合草稿语义；过期候选不能生效；失败不能报告发布成功。

跨字段、页面和规则的组合变更先明确依赖、顺序及部分失败处理，不承诺跨专题原子发布与自动回滚。Java 业务代码继续经过代码审查、编译和测试，不并入在线配置执行。

**状态：本期范围已完成（元数据候选与已有字段页面编排）。** 已有动态模块的单字段候选支持差异读取、普通字段连续修订、手工修改后的重新预检，以及人工确认前后的候选保护；正式 change-set 继续负责指纹、版本与事务验证。保存后生效状态查询或页面刷新失败不会抹去已保存事实。契约见[元数据候选协作与人工生效](AI_ASSISTANT_GOVERNANCE.md#元数据候选协作与人工生效)。

当前支持已有动态模块、同一元数据节点下的多字段新增方案（每批 1–12 项），可组合普通字段、模块引用和字典绑定；全部解析通过后一次进入现有编辑会话，逐项修改或移除，统一预检并人工确认。方案不包含批量修改存量字段、跨节点依赖编排或删除操作。页面配置已接入受模板约束的候选协作：读取当前模板与字段目录，调整已有字段的列表、表单及独立详情根投放与展示属性，配置快速查询；保留分组、关联、动作和未指定配置，复用只读预览与人工发布。第二阶段以元数据和已有字段页面编排两个闭环收口；规则与动作配置留在所属专题后续建设，不作为进入第三阶段的前置条件。不承诺跨专题自动建应用或原子发布。

已通过确定性测试覆盖手工编辑投影、原候选改名、确认期间变更和提交后刷新失败；真实 PostgreSQL 路径验证旧指纹/旧基线拒绝及重新预检后的物理列生效。真实模型与浏览器已验证候选生成、保留手工名称后修改索引及预检回执。模型仍可能多余澄清或在候选生成后说明失败；页面保留真实候选与执行事实，不能由样本通过推定自主完成质量稳定。

连续场景已通过真实模型、浏览器和 PostgreSQL 验收：多字段候选经人工确认落地后，返回保留草稿的页面配置，最新字段可被助手投放至列表、表单和快速查询，原有人工展示标题与子表保持；页面再次人工确认生效后，正式业务列表与表单消费新配置。目录加载失败及忙碌期间返回页签的恢复、旧调用拒绝、字段只读策略保留和发布失败后的候选保留由确定性回归覆盖。两个确认点分别承担本专题生效责任，页面候选放弃或发布失败不撤销已提交元数据。

### 第三阶段：对话内受控执行与应用建设

**目标**：用户围绕业务目标持续与助手协作，在对话中完成必要澄清、方案审阅、执行确认和结果检查；既能闭环一次表单保存，也能将商定的业务范围逐步建设成可用应用。普通用户不必先将需求翻译为模块、字段或页面配置命令。

**状态：工程链路已形成，非 IT 用户体验验收未通过，第三阶段继续收口。3A 标准记录保存、3B 需求方案确认与版本恢复、3C 简单动态登记应用建设与验收已有技术验证，不等同于普通用户可独立完成业务目标。** 第二阶段的已交付能力与验收结论保留；方案已能关联真实模块、主实体和初始化回执；普通字段可以在对话内单独确认落地；页面和入口各自独立确认，业务验收由人工核对后单独记录；复杂关系与业务规则仍按专题后续扩展。

#### 当前推进顺序

1. 先稳定对话确认与失败恢复：明确拒绝允许显式重试，未知结果先核实；验证实际运行服务与浏览器链路，而非仅凭测试通过判断可用。
2. 收敛方案一致性：人工修改使旧确认失效，相关问题、假设和规则重新核对后才能确认；模型负责语义调和，平台负责版本和确认门禁。展示聚焦本轮变化、待决定事项和实际完成状态。
3. 串起简单订单登记的字段、基础规则、页面与访问入口，复用正式配置治理能力，从失败节点继续。交付以实际录入和查询为准。
4. 完成上述闭环后，通过不依赖源码的用户体验与跨层契约验证收口，再扩展新的建设节点。

#### 面向非 IT 用户的收口条件

技术节点已有验证不替代业务目标验收。以不了解平台结构的用户自然表达需求为入口，不要求用户提供字段英文名、模块身份、发布指令或工具参数，也不由测试者用实现知识补齐操作路径。当前优先解决：

- 保存事实一致：区分未保存候选、已保存需求、已建设应用和已保存业务单据。助手说明不能把候选更新解释为持久化成功；结果区以可信回执明确当前成果和下一步。
- 业务范围可兑现：在确认建设范围前说明当前可实现、需简化及暂不支持的业务行为，以业务后果帮助用户取舍，不先承诺完整流程再在建设时静默省略。
- 确认可理解：主视图说明本次会创建或改变什么、确认后能做什么及仍缺什么；技术身份、存储细节和完整规则按需展开，关键决定与确认按钮不被长篇方案淹没。
- 追问可继续：审阅期间询问含义或影响，应保留待审阅内容；只有影响执行的候选、权限或作用域变化才使原确认失效，不能把普通解释性追问一律当作取消。
- 失败可恢复：模型输出过大、参数错误等应说明本次实际完成与未完成的事项，提供明确的继续路径；面向模型的参数修正信息与面向用户的提示分开，不让用户承担技术排错。

当前实现约束：

- 需求上下文显式提供未保存、需求已保存和保存结果未知三类事实；折叠方案标题保留保存状态，模型后续对话携带可信操作回执。需求确认不等于应用可用或业务单据已保存。
- 解释性追问保留待确认卡，提交时仍校验原候选与作用域；确认摘要展示业务影响，完整方案、验收清单和存储细节可展开审阅。新消息跟随到最新位置，向上阅读历史时提供返回最新回复入口。日期时间沿用平台本地时区展示，列表、详情、草稿变化与保存确认保持一致，执行参数仍使用规范化时间值。
- 当前对话建设只兑现独立登记表。已确认方案仍包含对象关联时，服务端拒绝初始化，须先商定并确认分期范围；不把关联需求静默转换为普通文本。自然语言规则的完整可实现性仍须逐项核对，不视为平台已经自动证明。
- 已知业务校验错误向模型提供有界修正原因，系统异常不暴露内部细节；模型回复中断可带回原请求进行补充，恢复入口不自动重放写入；未知保存结果继续通过原请求身份查询。流式传输开销与有效输出分别限制，事件、工具参数和总内容的上限仍然保留。

已补齐需求兑现映射与基于实际配置的任务续接，后续收口重点是普通用户端到端试用、需求映射的业务准确性，以及数据范围切换和相对日期的低门槛提示。固定状态选项、自动计算等未被配置能力兑现时，不得仅凭普通文本字段或人工验收按钮视为已交付。复杂需求的取舍说明不能替代对首版中每条已承诺规则的核对。

已确认方案为本期范围、规则和关系逐项记录兑现方式：实际字段、必填、唯一约束、明确的人工事项或暂不支持项。未对应或不支持项阻止对象建设；发布页面、入口和确认验收还须核对声明的字段约束已实际存在；建设页面的表单须包含本期字段兑现项，包括选填字段，已有页面缺少这些字段时重新核对交付。旧方案可以读取，但不会因已有页面或旧验收记录自动通过新检查。映射是经用户审阅的预期，不是另一套模型定义；当前只自动核对字段存在、必填与唯一，不证明自然语言规则完整正确，也不以普通字段证明固定选项、计算或流程能力。人工事项须明确说明业务后果，不能静默替代已承诺的自动化。

建设任务按已确认需求、现有配置和正式回执推导下一步，不保存第二套完成状态。刷新后可重新读取任务；确认成功且方案、会话仍有效时，助手自动核实进度并准备下一项确认。结果未知、用户正在输入、范围取舍和业务验收时停止自动续接。续接不代替用户授权，不自动执行下一次写入，也不扩大为跨节点事务或通用工作流引擎。

收口须验证从业务目标到首笔实际业务记录，并覆盖中途追问、能力取舍、失败继续及刷新恢复。能保存方案、能返回工具成功或由熟悉实现的人完成操作，均不足以判定该体验通过。

#### 复杂关系场景验收

单表闭环不能代表已有主子表与模块引用页面已通过助手验收。第三阶段须覆盖以下正式演示场景，操作已有页面与从零建设关系配置分别判断，不因建设器暂不支持关系而否定业务运行态已有能力。

| 场景 | 代表性演示 | 验收要求 |
| --- | --- | --- |
| 静态主子表 | 班级与班级成员 | 理解主表和成员明细的归属；保留添加学生的完整目标，不误称页面没有成员区块 |
| 动态主子表 | 考试与参考学生 | 读取、审阅主表和多条明细；增改明细后旧确认失效；保存后重新读取并核对学生、成绩与参加状态 |
| 跨模块引用 | 班级选班主任；考试选班级、学科；明细选学生 | 使用正式候选、按名称审阅；查询候选不等于授权选定，不能以原始 ID 替代可理解的名称；上下文和保存结果一致 |
| 从零建设复杂应用 | 进货单、货品明细与独立供应商 | 明确当前建设器的支持边界，保留完整需求；拆成独立表或改为手填须经用户选择，不视作关系能力已经兑现 |

助手已能读取嵌入式明细的行数、逐行业务内容和移除项；保存确认复用同一展示投影，列出整单明细并沿用聚合保存。明细修改仍由正式页面承担，助手不得宣称已具备明细增改能力，复杂关系协作尚未整体通过验收。必须区分“正式页面存在该能力”“助手能读取该区块”“助手能修改该区块”三个事实；未开放操作也应明确告知边界，不能由字段列表缺项推断明细不存在。保存确认须覆盖实际提交的聚合内容，包含明细数量、逐行业务信息及引用名称。主表成功不能替代整张单据成功，模型总结不能推翻真实页面草稿和回执。

关系协作优先复用现有关系描述、聚合草稿、引用选择和标准保存链路，不另建主子表运行态。引用详情的页面上下文切换与登录身份、业务租户变化须分开表达；查看关联记录应保留原单据目标及返回路径，不误报身份变化而让用户重新描述业务。明细的必填提示、字典与引用选择标题使用业务名称；状态选项应符合演示业务阶段，未考试的名单不能被迫标记为已参加或缺考。助手无法完成时须保留草稿并清楚交接，避免反复读取相同主表直至耗尽回合。

#### 3A：对话内完成一次可靠保存

首个切片选择标准页面的单条记录保存，复用现有演示验证静态与动态接入。用户描述需求，助手准备草稿，在对话中显示对象、关键值、变化及校验结论，用户选择“确认保存”“继续修改”或“取消”；确认后直接进入正式保存链路并返回真实回执，无需再到页面点击保存。

- 待执行提议由可信能力根据实际草稿产生，绑定操作身份、对象或新建意图、参数快照、用户与租户作用域、适用版本及失效条件。聊天中的肯定文本或模型生成的选项不单独构成执行凭据。
- 用户确认后，由受控执行器提交已审阅的提议；模型可以解释结果和提出后续步骤，不能在确认与执行之间重写参数或替换对象。草稿、范围或相关版本变化后须重新校验，影响本次提议时旧确认失效。
- 页面按钮与助手共用正式保存、字段编码、校验及领域规则。需要抽取控制器内部逻辑时，在已有运行器或领域门面提供窄的准备/提交契约，不模拟点击、不复制保存流程、不在聊天面板拼接业务 API。
- 选定写操作必须同时具备服务端幂等与受授权的结果查询。相同请求、相同内容重试返回同一执行事实；复用请求身份但更改内容应拒绝。响应丢失先核实结果，不能依据模型文案或前端点击去重认定成功或安全重试。
- 同步草稿效果与异步持久化执行分别表达。不能把网络写入塞进当前同步 `applyEffect` 回调；提交、取消等待、传输中断和最终业务结果分别由相应执行契约负责。保存与提交审批也不得隐式合并。

**完成门槛**：一项静态与一项动态标准表单均可在对话内确认保存，落地结果与页面手工保存一致；双击、旧确认、权限变化、提交后响应丢失和模型总结失败均有确定性验证，未知结果可查询。首批不开放删除、批量写入或权限配置。

3A 当前通过可信 `form.prepare-save` 提议进入对话确认，确认句柄不注册为模型工具。普通业务的标准主记录新增、修改共用页面运行器；首批不开放 `platform`、`iam` 管理域和切换子资源的树页面。回执与正式保存共享事务，绑定调用用户、请求租户和请求内容；重复请求不重复写入，回执查询重新检查记录访问权限。校验或权限的明确拒绝与传输中断的未知结果分别展示，查询到已提交结果后仅在原草稿仍未变化时恢复已保存页面。

确定性验证覆盖动静两种页面宿主、对话确认、旧草稿拒绝和响应丢失恢复；真实 PostgreSQL 覆盖并发去重、事务回滚、身份隔离，真实 HTTP 覆盖静态学生与动态考试模块的重复保存和回执查询。该能力不承诺关闭页面后的任务恢复，也不把配置发布或审批纳入标准保存。

#### 3B：围绕业务目标形成可修订建设方案

建设方案交互可与 3A 的底层实现并行设计，但执行生效依赖 3A 的确认与结果契约。以“我要管理订单”等自然语言目标为入口，先了解使用者、业务起止、关键对象与第一版成果，再细化必要字段、关系和页面；只追问会影响当前边界或执行正确性的缺口，不一次抛出全套配置问卷。不要求完整业务一次设计完毕：一个可独立验收的小范围确认后，即可进入 3C 准备候选并逐步落地，其余问题继续保持未决。

方案由平台 application 领域保存，表达业务目标与验收例子、本期纳入/排除范围、对象与关系、关键规则、未决问题和建议假设、需求与建议来源。确认版本构成需求共识，不生成第二套运行态模型定义。未执行初始化时状态为“尚未建设”；3C 初始化后，方案保留业务对象、确认版本、模块、主实体与关系身份的绑定，明确表达“已初始化，后续建设未完成”。

- 助手依据平台当前能力和既有配置提出有理由的边界推荐，并区分用户明确要求、用户已确认的建议与尚待决定的假设。推荐不自动扩张为已承诺范围。
- 用户先审阅可理解的业务范围与例子，字段、页面和技术差异按需展开；可以在对话内改需求，也可以打开正式编辑器调整，调整后重新对齐方案和候选。
- 确认业务范围、接受设计方案与批准实际生效是不同决定。“第一版只做订单登记”不能授权未来所有配置发布；常规命名与可逆候选生成也不要求逐字段确认。
- 每次实质修订形成方案版本，并标出受影响候选、已生效配置与尚未完成项。已完成步骤不因重新讨论而自动重跑；变更已经生效的内容须形成新的受治理候选。
- 建设目标和已确认决策独立于活动页面上下文；切换元数据、页面或预览时可以继续同一目标，但各步骤仍重新发现能力并校验当前作用域。恢复保存的方案时重新校验权限、依赖和基线，不复活旧执行确认。方案保存与恢复不等于后台继续执行，也不要求默认持久化全部聊天正文。

**3B 交付契约**：工作台通过 `construction.*` 能力整理本地候选、读取个人方案和恢复讨论；可信确认卡片展示完整业务内容、本版变化与需求来源，用户在对话内点击“确认本期方案”才形成持久版本。工作台同时提供目标、范围与验收例子的人工修订入口。目标、范围或验收条件改变且存在关联问题、假设、规则或决策时，候选标记待核对；旧内容保留但不能直接确认，由助手基于最新人工修改重新整理，不能靠字符串匹配静默删除问题或推定同意。该门禁不等于确定性语义冲突检测。未确认候选保留在当前工作台会话，刷新后恢复已确认版本，不默认存储全部聊天正文。

方案归当前登录用户及其登录租户的个人配置工作区所有，不随活动业务页的租户选择转移。服务端检查所有权、预期版本与请求内容指纹；方案头与不可变历史同事务提交，重复确认可定位原结果，即使已存在后续版本。读取入口最多返回最近 30 个方案或历史版本。身份变化清空本地状态；活动页面变化保留目标，但旧页面的执行授权不复活。响应丢失时可从方案卡查询原确认结果，不自动再次提交。

结果未知时保留原方案标识、请求标识、内容与预期版本，先查询原确认回执；不能通过重新准备确认绕过未知结果门禁，也不允许替换候选。查询未找到回执仍保持未知，不推定原请求未执行；跨会话未提交请求的持久恢复暂不属于当前契约。

**完成门槛**：普通用户可从业务目标逐步明确本期范围、未决问题和验收例子；能审阅、人工修改、确认版本并恢复讨论，不要求知道字段类型、模块别名或发布接口。已落地配置与待落地步骤的展示、范围变化对正式候选的追溯更新由 3C 完成。

#### 3C：将方案逐步建设为可用模块

**已交付节点：受治理模块初始化。** 对已确认方案中的一个业务对象，助手可以准备“应用 + 新动态模块 + 主实体”的只读预检；应用可以新建，也可以使用启用且非平台托管的业务应用。确认卡展示实际应用归属、模块身份、存储变化和未完成事项。首批限系统配置身份，并重新检查应用创建、模块创建和主实体创建权限；租户业务用户仍可梳理个人方案，不因此取得全局配置写入权。

用户单独确认初始化后，配置领域复用标准应用、模块和主实体服务，在同一事务中创建配置、建表并保存不可变回执；运行态走既有提交后激活链路。预检绑定方案版本、业务对象和应用版本，拒绝接管已有模块、实体或物理表。按方案串行化确认与需求修订；应用范围锁和应用行锁防止同一应用的并发初始化漂移。相同请求返回原回执，同一业务对象不能因修改方案、刷新页面或换请求标识而再次初始化。

`construction.initialization-status` 查询真实回执与运行态状态。首个提交响应不提前承诺运行态已激活；恢复方案后能看到已有初始化记录和所属需求版本。已提交配置不因后续需求修改而自动撤销或重建。此节点不自动编排业务字段、关系、发布页面或菜单，也不把标准字段可用判为业务验收完成。

**已交付节点：对话内普通字段新增。** 已初始化对象可读取真实字段及启用规格目录，一次预检 1–12 个新增字段，再由用户单独确认。当前支持实际规格、标题、必填、唯一和索引，复用正式元数据变更集的校验、物理结构及提交后运行态刷新。普通新增不隐式承诺金额范围、复杂业务规则、引用、字典或页面能力。

预检绑定需求版本、初始化对象与元数据基线；服务端验证个人方案所有权、系统配置身份和正式元数据预检/发布权限。字段变更与不可变回执在同一事务中提交，相同请求重试定位原结果，换内容复用请求标识会拒绝；需求修订不会重做已提交字段。方案恢复包含字段提交记录，运行态通过结果查询核实，不以提交响应代替激活成功。继续遵循平台运行模式的 schema migration 策略，不绕过生产严格迁移约束。字段回执只证明该节点提交；页面、入口与人工验收由下述独立节点承接。

**已交付节点：页面、工作台入口及人工验收。** 页面节点依据实际字段生成受 management 模板约束的列表、表单、共用详情与快速查询，沿用模块标准新建、编辑和保存动作；预检复用正式页面编译器，确认复用不可变修订及发布服务。字段基线、已有页面修订和需求版本变化使预检失效；独立维护或已被其他修订替换的页面不能被助手自动接管。页面可以在原建设对象下重新预检并发布新修订，不重复创建模块。

入口节点在页面发布后独立确认，创建当前系统配置工作台的可见菜单；不自动授予租户用户或角色权限。前端消费提交回执刷新入口，刷新失败保留已提交事实。建设进度从正式页面、菜单和运行态核实，保存的回执不代替实时状态。

人工验收展示当前需求规则及验收例子，用户应先在选定业务租户中实际验证录入、查询与详情，再明确确认。验收记录绑定需求、字段、页面及菜单基线，存在未决问题、运行态未就绪或基线变化时不能确认；后续变更使旧验收不再代表当前版本通过。人工验收不冒充自动化测试证明，也不将模型的完成声明作为验收事实。

当前闭环限定系统配置身份建设简单动态登记模块；普通字段支持必填、唯一和索引，页面支持已有字段的基础投放与查询。跨对象关系、任意规则、自动角色授权和复杂布局不在本期闭环范围，需求中涉及这些能力时必须明确留待后续或重新确认本期范围。

将 3B 的方案接到第二阶段已形成的元数据与页面候选，再接入 3A 的对话内执行确认。优先完成一个最小应用建设闭环，不先扩展全部正式业务动作。

首个验收场景为简单“订单登记”：在方案明确范围后，从空白建设一个可录入、查询和查看详情的动态模块，按实际需求选择必要关联；支付、库存、财务、审批等不因“订单”名称自动纳入。样例承担平台能力验收，不成为完整订单产品或助手主循环中的业务特判。

- 先盘点方案所需的正式能力。已有对象可复用，缺少的应用/模块初始化、主元数据或关系创建必须由配置领域补齐候选、校验、生效和失败契约，再向助手开放；不能把现有普通保存包装成隔离草稿，也不能宣称现有字段候选已支持从空白建应用。
- 建设计划按已确认范围和配置依赖确定步骤：准备候选、审阅影响、确认生效、核实运行态、生成依赖下一步的候选、预览及验收。步骤指向正式配置对象、基线和结果回执，由确定性执行逻辑约束，模型负责提出与修订建议。
- 对话内确认按有意义的建设节点组织。能准确预览的一组变更可在同一确认中展示；依赖上一步实际结果才能确定的变化，在得到结果后再展示确认。不让用户逐个批准技术调用，也不把一次范围确认解释为无限执行授权。
- 元数据生效后，页面候选使用实际配置身份与最新目录。页面发布失败时清楚表达“字段已生效、页面未完成”，保留可修正候选，从失败点继续；取消后续建设不撤销已提交步骤，不承诺跨专题原子发布或自动回滚。
- 完成判定来自正式配置、运行态和用户验收例子。回执区分“配置已保存”“运行态已生效”“页面可用”与尚未支持的业务规则，不能以最后一条模型总结或全部工具调用返回成功代替应用验收。

**完成门槛**：用户从描述一个简单业务目标开始，在同一对话中确认范围、审阅方案并分步批准生效，最终取得实际可用的模块。覆盖人工中途修改、方案范围调整、步骤部分失败、重复确认及恢复后基线变化；不会丢失已确认需求或重复创建已完成对象。能力不支持的需求明确留待后续，不静默省略。

#### 架构归属与投入边界

| 层次 | 新增或收敛的责任 | 继续复用的基础 |
| --- | --- | --- |
| 对话展示与会话控制 | 业务方案摘要、待确认提议、修改/拒绝/确认及执行回执；保留建设目标 | 现有助手消息、受控选择交互与会话控制器 |
| 能力适配与执行 | 可信操作提议、失效检查、确认后确定性调度、异步结果核实 | Surface、调用令牌、标准页面运行器与能力契约 |
| 配置建设领域 | 建设方案版本、配置依赖、候选引用与分步执行事实 | 元数据 change-set、页面修订及配置治理门面 |
| 业务与持久化领域 | 权限、租户、版本、幂等、正式执行和可查询结果 | 统一 Ability、领域 Service、事务、动作结果与审计 |

方案状态、对话状态、业务单据状态和执行回执保持各自归属，不用一个通用任务状态替代。共用确认展示与执行纪律，不强行把 CRUD 保存、元数据 DDL 与页面发布合并为同一事务或执行引擎。平台尚未上线，可按上述边界直接收敛已有控制器和接口，不维持双重保存实现；不预建通用工作流、任意脚本执行或多智能体框架。

当前普通业务标准保存允许用户在对话内确认后由平台执行；方案关联的普通字段新增已可对话内确认；其他元数据变更继续由正式治理页面人工生效；方案关联页面和入口已经接入独立对话确认。未确认的自动保存仍不开放。工作流审批继续拥有独立的办理权和业务含义。正式结果契约见[动作结果与数据变更契约](ACTION_RESULT_AND_DATA_CHANGE.md)。

### 第四阶段：围绕业务任务组织人机协作

**目标**：人和助手围绕业务任务持续协作，减少用户逐步指挥，并能验证任务是否完成。

**建设思路**：

1. 复用模块任务的完成检查与工作流的办理、审批和流转能力，为助手提供未完成项、合法处理入口和当前办理上下文。
2. 助手解释缺失项、定位数据并准备处理结果；需要人工判断时交接，处理后由领域重新检查完成条件。
3. 复用变更对比、候选选择、动作提议、完成检查和执行回执等有限交互组件，不开放任意生成式业务页面。

**验收口径**：一个完整任务能由人与助手交接处理，完成结论来自领域事实或明确的人工决定；助手不能自行越过办理权、审批或流转条件。

助手交互状态、业务任务状态和后台执行状态分别归所属领域，不以一张通用 Task 表替代。模块完成项也不升级为具有办理人和委托语义的审批待办。边界见[工作流与任务专题](topics/workflow-task/OVERVIEW.md)和[页面交互概览](topics/page/interaction/OVERVIEW.md)。

### 第五阶段：按需扩展后台与外部协作

**目标**：让已形成的业务能力在明确授权下服务后台自动化和外部智能体。

**触发条件与思路**：真实场景需要关闭页面后继续执行、跨会话恢复、长耗时处理或外部调用时，再按专题补齐执行身份、授权、幂等、进度、重试、恢复、取消及结果检查。需要互操作时再评估 MCP 等协议，协议适配继续调用正式业务能力。

**验收口径**：选定场景脱离浏览器后仍具有明确责任主体和执行状态；失败可定位、重复执行可控、恢复不绕过现行权限与业务约束。

本阶段只保留建设方向，不预选执行引擎，不自动将所有 API 暴露为工具，不建设自主多智能体系统。具体设计由[后台任务与异步批次边界](BACKGROUND_JOB_AND_BATCH_BOUNDARY.md)和[外部写入接入边界](EXTERNAL_WRITE_BOUNDARY.md)约束。

## 验证与阶段收口

每阶段围绕一个完整目标交付公开契约、默认实现、必要测试与专题文档。共用以下判断：

- 平台是否减少了下一个业务的接入代码与重复声明，且保留静态 Java 接入的直观性。
- 静态与动态是否使用同一能力语义；短期单侧限制是否明确记录。
- 人工与助手是否经过相同正式业务链路，模型失败是否有真实可理解的反馈。
- 成功是否由实际草稿、配置生效、业务状态或执行结果证明，而不是由模型文本证明。

确定性契约测试覆盖权限、范围、字段保护、版本、取消和结果语义；涉及真实数据、配置生效或事务边界时补真实路径测试。模型场景回归记录目标完成情况、调用次数、耗时和失败分类，不能以测试替身通过推定真实模型体验达标。 多步读取已提供同一有效基线内的有界结果连续利用；模型反复查询的收敛风险仍须以真实场景回归持续检查，后续扩展节点应同时验证建设进度的连续利用。分步确认链路可用不等于普通用户的一次目标描述已能稳定完成建设。

技术加固优先验证故障与并发交界：工具调用及结果配对、效果发生后的取消或断流、用户修改草稿后的迟到响应、动态配置更新后的旧能力调用，以及非法参数和重复调用。进入持久化动作时增加真实提交后响应丢失、相同请求重试与未知结果核实的契约；不以正常链路成功替代这些门槛。

近期优先复用[教学管理演示](../architecture/EDUCATION_DEMO_SCENARIO.md)验证静态主数据与动态测评的共同接入，以及既有动态模块的字段候选治理。演示仅承担平台验收，不为展示路线一次性扩成完整业务套件。

各阶段完成后将稳定契约归入所属专题，本文维护阶段状态、依赖与未完成边界，不记录执行流水。新增框架、发布机制或跨专题执行能力，应在进入相应阶段时重新评估收益、维护成本和验证范围。
