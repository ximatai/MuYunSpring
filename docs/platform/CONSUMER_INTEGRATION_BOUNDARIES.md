# 消费者接入边界

本文记录公共接入约束、能力裁决和后续建设条件。消费反馈基线为 Java／Web 0.26.21、
Spring Boot 4.1.1、JDK 21；下述源码边界以 0.26.23-SNAPSHOT 为准，新增导出须随正式版本发布后消费。
不据历史故障推断旧版或新版的全部行为，也不包含具体应用协议和业务流程。

## 裁决总览

| 场景 | 归类与决定 | 平台承接边界 |
| --- | --- | --- |
| 默认 JSON 转换器 | 明确已有配置的接入约束，补齐契约测试 | 明确 Jackson 2 HTTP 配置，验证实际 MVC 往返；不要求消费者复制依赖排除 |
| 超级管理员专用模块 | 公共能力候选；优先后续评估 | 模块访问约束需同时收敛菜单、描述与动作；现有系统作用域不能替代授权 |
| 非 UI 读取会话 | 已补齐公开导出边界 | 增加公开 `record-read` 子路径，验证真实 tarball 在 Node 中消费；不公开全部内部实现 |
| 旧页面延迟分包失败 | 部署责任与应用壳恢复分别处理 | 明确资源契约；公共壳错误展示与恢复列为后续候选，不自动重载 |
| 系统单例配置 | 先沿用显式领域实现；暂不新增能力 | 复用系统写入门禁、标准 CRUD 版本和生命周期；领域保留单例规则与生效语义 |
| 通知恢复 | 公共生命周期候选；后续评估 | 可承接恢复源生命周期与隔离；待处理事实和动作有效性仍由领域判定 |
| 授权范围关联分页 | 已有引用依赖策略部分覆盖；优先评估静态与通用接入缺口 | 优先复用 `referenceDependency` 子查询执行链；不能以摘要投影替代关联授权 |
| 提交与缓存可见性 | 契约澄清；继续观察 | 明确本节点、事务和失效边界；无当前最小复现不修改缓存机制 |

候选不等于已交付 API，也不要求消费应用在新版本发布前移除必要适配。

## JSON 转换器

平台的 `CodeTitleEnum`、动态记录和内容语言模块目前使用 Jackson 2。
仅引入 `spring-boot-jackson2` 不保证 MVC 优先使用它；Spring Boot 4.1.1 在两代 Jackson
自动配置均存在时默认选择 Jackson 3，合法的业务枚举 code 因而可能无法解码。

推荐消费应用显式设置 `spring.http.converters.preferred-json-mapper=jackson2`。
这是 HTTP 接入约束，替代各子模块重复排除 Jackson 3 的规避，不声称已完成 Jackson 3 迁移。
手动构造或替换 ObjectMapper、MVC 转换器的应用仍须验证平台模块是否被采用。

`JacksonMvcConsumerContractTest` 保留两代 Jackson 自动配置，检查实际
`RequestMappingHandlerAdapter` 选中的转换器，并通过 MockMvc 验证枚举 code 的请求、响应、非法值、
内容语言写入意图与动态记录协议。
该测试不替代消费应用的自定义装配验证，也不证明 0.26.21 的原始应用已复现或已修复。

## 系统作用域与模块访问

`SystemScope`、`SystemManagedAbility` 和 `StaticModuleTenantScopePolicy` 管理数据执行作用域，
不表达“仅平台超级管理员”。`CurrentUser.system()` 也不是超级管理员的唯一身份判据：
当前无租户账号均可投影为 system user，菜单策略与动作策略对 system user 均有直接放行分支。
因此仅检测 system、隐藏菜单或关闭活动租户要求，都不足以实现反馈中的限制。

静态平台模块可通过 `@PlatformStaticModule(tenantAccessible = true)` 声明无需开通所属应用的
租户入口，默认关闭。该事实经静态模块目录交付给应用可用性目录，菜单、动作执行、角色
授权和租户管理员隐式授权复用同一判断；所属应用停用仍会拒绝。它只表达租户入口可用性，
不授予动作权限、不改变数据作用域，也不表示模块仅供超级管理员使用。

当前没有可直接推荐的统一模块限制声明。应用的显式后端授权和菜单限制应暂时保留；
不能仅凭使用 `@Primary` 就判定应用用法错误，也不把替换全局菜单策略推荐为长期接入方式。

后续若建设，应由模块声明产生同一访问约束，由菜单、页面描述／入口、动作执行及相关发现接口消费；
限制应在系统用户直接放行、租户管理员隐式授权之前生效，不能靠配置授权扩大。
平台负责定义超级管理员身份与可信后台执行的边界，业务不复制用户 ID 判断。
验收至少覆盖超级管理员、普通系统用户、租户管理员、普通租户用户以及绕过菜单的直接请求。
这是授权公共契约变更，需单独完成设计与验证后交付。

## 非 UI SDK 消费

推荐通过 `@ximatai/muyun-web-app/record-read` 获取记录读取会话和具名入口解析；
根入口继续交付工作台与 UI 注册。原有根入口导出保持兼容，子路径及其声明属于正式消费面。
Node 测试、Vue effect scope 释放与身份隔离的接法见[前端消费者接入](../frontend/LOCAL_CONSUMER.md)。

应用应在包含该导出的正式版本发布后移除包片段扫描与 VM 执行适配。
新增子路径只解决公开读取逻辑的加载边界，不将所有内部函数开放，也不移除包的 UI peer dependencies。

## 发布资源与加载恢复

部署方负责入口文档、静态资源与版本切换的一致性：

- HTML 应可重新验证，哈希资源可长期缓存且内容不可原地替换。
- 版本切换应原子化；保留旧资源或提供等价的版本资源路由，覆盖约定支持的旧会话周期。
- 资源保留期应依据会话周期和发布频率约定，不能假设一次发布后所有浏览器立即刷新。
- 缺失 JS／CSS 返回正确的资源错误，不回退到 SPA HTML；工作台路由的 HTML 回退单独配置。

资源历史可用性无法由 SDK 单独保证。平台标准壳目前没有统一的旧分包加载失败恢复契约，
接入业务自己宿主的路由失败也不能由内置 router 自动接管。
公共壳候选应提供明确错误展示和用户主动恢复入口，区分网络失败与版本资源失效，保留其他已挂载页。
恢复必须尊重未保存状态与现有关闭门禁，不自动无限刷新，也不清空草稿。
验收应包含旧 HTML 加载新版本、旧分包 404、离线、连续失败和未保存表单。

## 系统单例配置

优先使用独立类型化配置模型、DAO、`SystemStandardBusinessService` 和正常领域读写门面。
单例身份由服务端固定，领域拒绝任意 ID 或第二条记录；数据库主键／唯一约束作为并发兜底。
首次创建与更新应有明确协议：并发创建冲突不能静默转为覆盖更新，编辑保存必须携带读取到的 version。
标准 CRUD 已提供乐观锁、生命周期、事务与缓存失效，无需再建设一套配置写入链路。

系统作用域与操作者授权仍分别校验，读取也不能因固定 ID 而隐式放开。
普通配置不自动使用平台托管初始数据，不默认组合租户覆盖、软删除或缓存；是否需要全局读取显式决定。
页面请求状态可沿用既有操作反馈与保存门禁，字段校验及何时生效留在领域。
当前缺少足以证明统一单例基类收益的稳定生命周期样例，暂不新增配置中心、通用锁或自动迁移能力。

## 通知恢复

`connectAppRealtime` 的连接状态回调和通知回调可用于应用适配；连接会恢复订阅，
但不查询离线期间的待处理事实。`BusinessNotificationPanel` 接收通知列表并处理展示与动作交互，
不提供恢复源注册、跨来源快照合并或账号切换后的恢复请求隔离。
持续可见仅是展示策略，见[实时业务提醒接入](BUSINESS_NOTIFICATION_BACKEND_INTEGRATION.md)。

应用目前可在首次连接和重连后查询领域的授权待处理项，并向同一面板投影；退出与切换身份时
释放旧连接、清理旧通知、取消旧请求，并用身份代次拒绝无法取消的迟到响应。
各来源只维护自身通知，不能用一个来源的恢复结果覆盖全部列表；实时增量与恢复快照的竞争也需显式处理。

后续只评估恢复源注册、请求合并、来源／身份隔离与释放契约。有效性、到期、接收权限和命令执行成功
仍以领域服务为准；不预设持久消息中心、离线事件重放或统一业务台账。
建设前需提供无敏感数据的双来源、重连、退出、切换身份及迟到响应样例。

## 授权范围关联分页

`DataScopeAbility.readScope` 可解析当前实体的动作数据范围，`pageQueryForAction` 可在该实体上执行分页。
`RelationProjectionReadService` 负责关联字段投影，不是来源实体授权范围转为目标列表过滤的门面。
引用摘要在来源记录可见后可不再套用目标业务数据范围；不能反过来把这条展示规则当成关联授权。
`readScopeByPolicy(moduleAlias, ...)` 也不能直接替代跨实体映射：其字段映射仍属于当前 Service。

已有 `DataScopePolicy.REFERENCE_DEPENDENCY`：列表实体通过引用字段依赖被引用实体的动作数据范围，
`RoleDataScopeCriteriaService` 将其编译为带参数的 `IN (SELECT ...)`，包含被引用实体的租户与软删过滤；
没有有效 resolver 时拒绝范围。内置 `DynamicReferenceDependencyScopeResolver` 从动态运行态目录
解析两侧实体与字段，角色授权候选当前使用目标 `VIEW`；它不能据此证明普通静态实体已有同等声明接入。
已有测试覆盖子查询生成、跨租户范围收敛与无法解析时拒绝，但不等于已验证反馈应用的完整分页路径。

若样例是已发布动态实体的直接引用，并且业务需要的正是这类可配置授权继承，优先评估现有策略，
继续走标准动作鉴权与 `pageQueryForAction`；确认字段候选、动作语义和多角色范围合并符合需求后再替换适配。
业务不可放宽的强制关联约束不能直接改写为可被其他角色授权取并集的数据范围策略。

强制关联读使用 `AuthorizedAssociationQuery`。静态 Service 与动态实体操作入口均可作为参与方，
每次执行分别校验各方动作与数据范围，静态字段映射取自对应 Service；关联约束始终取交集，
跨租户授权只作用于取得该授权的参与方，外层临时 bypass 不替代授权。

```java
var visibleFiles = queries.from(fileService, PlatformAction.VIEW);
var page = queries.from(publicationService, PlatformAction.QUERY)
        .where(Criteria.of().eq("status", status))
        .whereRelated("fileId", visibleFiles)
        .page(PageRequest.of(pageNumber, 20), Sort.desc("updatedAt"), Sort.asc("id"));
```

`requiring(policy)` 增加必须同时满足的动作范围；`whereRelated(localField, relatedQuery, relatedField, records)`
支持反向关联、嵌套关联和显式 `INCLUDING_DELETED` 的关联来源。历史读取只跳过该来源的 active 条件，
仍执行其 `tenantCriteria`、动作与数据范围；应由领域决定哪些历史事实可参与查询。
根分页与计数按 `from` 声明的动作执行，并保留目标 Service 的读取与输出链路；动态入口也不额外叠加 QUERY 范围。
条件在数据库内编译成参数化半连接，分页与计数使用同一组约束，
无需加载完整 ID 集合；重复关联不会扩增目标记录。

参与方必须使用同一宿主数据库。查询要求登录身份，非全局实体在没有跨租户授权时要求当前租户；
不支持跨数据库关联，也不把该门面当作授权结果缓存。现有角色配置的引用依赖策略保持原有边界。
真实 PostgreSQL 契约覆盖静静、静动、动静、动动关联、独立跨租户授权、历史来源、空范围、
拒绝动作、自定义字段映射、身份变化、元数据刷新、受保护字段下的空范围、不同动作范围、
反向重复关联与 records／count 一致性。

## 事务与缓存可见性

`CacheAbility` 在实际 Spring 事务内绕过共享缓存，读取受当前连接与数据库隔离级别约束。
普通非事务读取可使用本进程缓存；标准写入在提交后失效，回滚保留原缓存。
失效代次可阻止跨越失效的旧读取重新填充缓存，但不会撤回已交付调用方的旧结果。

数据库提交可见和本节点 after-commit 失效完成存在先后关系：与提交回调并发的独立读取
不能据此获得线性一致保证。通过 Spring 事务代理或 `TransactionTemplate` 实际创建并提交事务的
同步调用成功返回，可作为该事务提交回调已执行的边界；仅加入外层事务的 Service 返回仍可能处于
未提交事务中，不能据此通知其他线程读取新值。`REQUIRES_NEW` 按其独立事务边界判断。
异步业务应等待实际事务与任务完成，不能把“已受理”当成提交完成。需要绕过缓存的读取可使用
普通 Criteria 查询或显式事务，并明确投影、生命周期和数据库隔离语义，不把 RAW 读取当成通用补救。
跨实例缓存不自动失效，相关后续边界见 [TD-005／TD-006](../TECHNICAL_DEBT.md)。

观察项不升级为缓存重构。若仍有偏差，最小复现应标明版本、节点、事务边界、读取入口、
数据库隔离级别、提交回调与任务完成时序；使用可控同步点，不以任意 sleep 代替完成条件。

## HTTP 流错误边界

流接口在进入流响应前被拒绝时，使用标准 JSON 错误体和原始 HTTP 状态码；即使消费者只声明
`Accept: text/event-stream`，平台异常处理也明确返回 `application/json`。前端流客户端默认接受
SSE 与 JSON，沿用普通请求的错误解析和登录恢复规则，允许调用方显式覆盖 Accept。

流响应已经提交后，不能再通过 JSON 错误体或修改 HTTP 状态报告失败；由所属流协议处理。
助手流使用 SSE `error` 事件，消费者需要同时处理建流失败与流内错误。
助手客户端收到 `error` 事件即以该错误结束本轮并取消响应体读取，不等待连接关闭；
读取期间的取消与断连保留原始异常，并释放 reader。
容器 ERROR 分派不重新校验菜单入口，并清理菜单入口上下文；正常请求、转发与异步恢复仍执行校验。
该豁免只服务错误渲染，不替代业务动作权限、租户和数据范围校验。
