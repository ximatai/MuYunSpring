# 平台配置专题

## 能力定位

平台配置专题覆盖 MuYunSpring 自身配置态的基础对象和运行态刷新链路，目标是让应用、模块、元数据、字段、数据字典和菜单等配置按平台能力维护，并能同步为动态运行态。

这条链路服务于“动静一体”：动态模块通过元数据声明能力，运行态刷新后进入与静态模型一致的数据访问、能力语义、生命周期、权限、审计、租户和事务边界。专题文档只梳理配置对象和业务线索，不展开 Java 底层实现。

Web 维护面按“独立配置根 + 模块聚合子资源”组织：应用、模块、元数据保留平台模块 alias 根路径；模块动作、模块-元数据关系、模块字段配置从 `/platform.module/{moduleAlias}` 进入。动态运行态刷新也挂在模块配置域下，表达把当前配置同步到 `DynamicRecordRuntime`。配置包版本归档、导入导出、指针切换和健康检查仍归属配置治理，不混入普通维护接口。

## 主要对象

| 对象               | 作用                                             | 关键边界                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 应用               | 平台业务空间的上层归属                           | `applicationAlias` 全局唯一，使用单段小写标识                                                                                                                                                    |
| 模块               | 运行时业务边界                                   | 统一使用 `moduleAlias`，格式为 `<applicationAlias>.<moduleName>`；不使用 `moduleId` 表达同一件事                                                                                                 |
| 元数据             | 动态实体的配置态定义                             | `Metadata.id` 是平台稳定 ID；`metadataAlias` 在应用内唯一；物理定位使用 `schemaName + tableName`                                                                                                 |
| 字段               | 元数据的字段事实和轻量行为                       | 表达字段名、列名、类型、约束、字典绑定、引用、保护和公式等运行态必须知道的信息                                                                                                                   |
| 字段类型与 UI 类型 | 字段配置的基础目录                               | 字段类型定义运行态形态和查询能力；UI 类型属性和字段映射定义页面控件配置线索                                                                                                                      |
| 模块-元数据关系    | 模块与主/子元数据的绑定关系                      | 一个模块最多一个主元数据；动态模块必须有主元数据；子关系的外键必须是子实体物理字段，并以单值引用回指其父实体                                                                                     |
| 元数据视图         | 模块关系下的配置态视图                           | 是模块定义运行态编译前的视图真相源；页面布局和端侧差异仍归 UI 配置                                                                                                                               |
| 数据字典           | 字段选项和值域约束                               | 类目按应用维护，alias 在应用内唯一；项目按类目维护，code 在类目内唯一；业务数据保存字典项目 `code`                                                                                               |
| 计量单位           | 数值字段的单位目录、基础换算事实和业务硬换算规则 | 以共享单位库为主，`tenantId` 为空表示平台全局公开，`tenantId` 有值表示租户公开；单位按分类维护，业务数据保存单位 `code`；基础目录承诺同分类线性换算，硬换算规则按租户/全局、模块和记录上下文生效 |
| 币种与汇率         | 金额字段和跨系统金额口径的基础资料               | 币种使用 ISO 4217 alpha-3 code；租户可设置本位币；汇率按币种对、汇率类型和生效日期维护，支持按业务日期取最近有效汇率                                                                             |
| 菜单方案与菜单     | 基础入口组织                                     | 菜单不归属应用；一个菜单只属于一个方案；模块可被多个菜单节点挂载                                                                                                                                 |
| 租户应用开通       | 租户可使用的应用范围                             | 以独立关联维护，不写入租户核心模型；已开通应用是租户角色可授权模块的前置条件，角色授权继续细分模块与动作                                                                                         |

## 核心业务链路

1. 创建应用，确定 `applicationAlias`。
2. 创建模块，确定稳定 `moduleAlias`，并声明静态或动态接入方式。
3. 为动态模块维护元数据、字段、关系、视图和字典绑定。
4. 通过模块-元数据关系绑定主元数据和子元数据，并维护关系下的模块字段、元数据视图和字段行为。模块入口能力不另设一套开关，而由 MAIN 的元数据与字段事实编译；子元数据不继承数据范围、树、排序（含排序分区）、启停或审批等模块增强能力，主子聚合和删除语义由关系及其外键引用事实承接。同一子字段若在不同模块关系中回指不同父实体，引用配置必须按关系分别维护，不能使用全局默认引用。跨模块引用也必须按来源关系维护，目标只能是目标动态模块的 MAIN 元数据；跨模块展示投影暂不开放。
5. 配置菜单方案和菜单节点，将模块挂载为运行入口。
6. 为租户开通应用；租户角色只能在已开通应用内授予模块与动作。平台与租户共用能力应通过应用边界治理，不在模块上叠加租户开放策略。
7. 元数据或字段保存后，平台在事务提交后按单个 metadata 编译动态 `EntityDefinition` 并执行 schema ensure；无事务时立即执行。
8. 刷新运行态，把当前模块配置编译为动态 `ModuleDefinition`、`EntityDefinition`、`FieldDefinition` 等运行态定义。
9. 运行态刷新链路必要时再次执行模块级 schema ensure，并刷新动态运行态 registry。
10. 运行态通过动态记录入口按 `moduleAlias + metadataAlias` 执行描述读取、CRUD、查询和引用等能力。

最小闭环是：

```text
应用 -> 模块 -> 元数据 -> 字段 -> schema ensure -> 关系/菜单/字典 -> runtime refresh -> DynamicRecordService -> CRUD/query
```

## 边界说明

1. 配置专题聚焦应用、模块、元数据、字段、数据字典、计量单位、币种汇率、菜单基础配置和刷新到运行态。
2. 静态模块可以没有元数据；动态模块必须有一个主元数据。
3. 字段定义只承载运行态必须知道的轻量字段事实和行为；引用过滤、引用回填、字段保护和公式规则属于配置态字段行为，按元数据字段或模块字段归属聚合。
4. 菜单模型只表达入口树和模块挂载；权限剪枝属于权限专题，不能反向污染菜单配置。
5. 运行态 URL、权限、审计和 OpenAPI 统一围绕 `moduleAlias`，不暴露内部实体定位作为业务入口。
6. 元数据结构保存即生效：元数据和元数据字段新增、更新后，平台会在事务提交后执行单 metadata schema ensure；无事务时立即执行。该链路只承诺安全加法和当前 `DynamicSchemaService.ensureTable` 的默认治理口径，不把字段删除、破坏性类型变更或复杂迁移策略作为普通保存副作用。字段保护、字典绑定等轻量字段事实可进入结构编译；模块字段消费配置、UI/query 配置和模块动作不参与单 metadata schema ensure。
7. Runtime refresh 是配置态到运行态契约的同步边界，负责把模块关系、模块字段消费配置、视图、动作等编译进动态运行态；结构 ensure 是物理结构层，两者职责不同。影响 `ModuleDefinition` 编译结果的配置保存后，平台会在事务提交后自动刷新受影响模块；无事务时立即刷新。自动刷新覆盖模块-元数据关系、模块字段消费配置、引用过滤/带出、公式规则、元数据视图、模块动作，以及元数据字段变更后引用该 metadata 的动态模块。手动 refresh 仍保留为运维入口，并沿用当前运行模式下的 schema migration 默认策略；preview refresh 始终 dry-run。模块级配置包归档偏治理版本定稿和跨环境迁移，不是业务运行的硬前置；UI 配置和查询模板 publish 仍表达用户可见生效，不触发 runtime refresh 或 schema ensure。
8. 本专题不复盘推进过程，不记录测试流水；稳定契约优先由代码和 contract 测试支撑。

## 静态选项字段

静态模型通过 `@OptionField` 或其字典专用声明 `@DictionaryField` 声明字段的选项来源，和动态字段编译后的 option binding 复用同一套前端 schema、保存校验和 title 输出语义。`@DictionaryField` 只改善字典绑定与 baseline 的声明体验，运行时仍编译为同一个 dictionary `OptionBinding`；两者不能标注在同一个字段。通用 `@OptionField` 保持来源无关，避免 common 层依赖字典持久化或启动机制。

当前稳定来源包括：

1. `DICTIONARY`：静态字段使用 `@DictionaryField(source = "applicationAlias.categoryAlias")`；字段需要交付最小字典值域时在同一注解声明 `title` 和 `initialItems`。业务字段保存字典项目 `code`。租户上下文读取字典选项时，租户字典优先；租户下不存在对应类目时，允许回退读取平台全局字典。
2. `ENUM`：字段类型或 `enumType` 必须实现 `CodeTitleEnum`，业务字段保存 enum code。集合或数组字段必须显式声明 `selectionMode = MULTIPLE`。

## 判别字段

当一个字段的值语义由同记录的选项字段决定时，使用判别字段契约，而不是把值当作无约束字符串，也不以表单公式决定数据语义。首期只支持三类分支：`FIXED` 固定值、`FIELD` 取同记录字段、`REFERENCE` 使用一个标准单值引用；不支持任意表达式、脚本或动态执行函数。

静态模型将声明放在被判别字段上：`@DiscriminatedValue` 指定判别字段、其 `CodeTitleEnum` 类型和每个 enum code 的分支。动态模块以 `EntityDiscriminatedValueDefinition` 提供同构定义，并使用已发布选项的 code 集合；其取值来源和候选依赖可以使用动态业务字段或当前支持的标准字段 `tenantId`，但被写入的判别值字段和判别字段必须是模块自身的可写字段。两侧都编译为同一个 `DiscriminatedValuePlan`，由服务端负责固定值/字段值归一和引用完整性、候选依赖校验；页面公式只消费该事实来控制显隐或必填，不决定引用目标。

判别字段适合“同一个持久化值由不同分支产生”的模型；它不把所有“scope”模型强行统一。计量换算、编码规则等具有不同的字段组合和业务选择逻辑，只有满足上述判别值语义时才接入。

`tenantId` 是平台标准作用域引用：当静态模块在页面中显式声明该字段时，UI 会将其渲染为 `iam.tenant` 的单值记录选择器；它不是每个模型重复声明的业务 `@ReferenceTo`。`MenuScheme` 是明确字段建模：系统范围不填写作用域对象；租户范围由 `tenantId` 表达；机构范围同时填写 `tenantId` 和带候选依赖的标准引用 `organizationId`。页面公式只据 `scopeType` 控制显隐和必填，不再生成或归一化伪造的 scope 值。

静态查询 schema 会在 `QueryAbility.querySchema()` 中按模型同名字段自动合并 `@OptionField` 或 `@DictionaryField` 元数据；静态页面字段选项应在模块 UI descriptor 编译链中合并，不再以 service `FormAbility.formSchema()` 作为目标来源。业务 service 的 `QueryDescriptor` 只声明查询语义；模块 UI 声明只表达页面意图。读模型字段通过 `@OptionLoad(source = "...")` 声明从已绑定选项中提取的 `OptionItem` 属性，默认读取 `title`；`field` 可显式选择 `code`、`enabled`、`sortOrder` 或 `parentCode`。动态元数据在输出虚拟字段上使用同构声明：`FieldDefinition.string("subjectTitle", "学科").virtual().optionLoad("subjectCode")`。因此选项值字段只声明候选与校验，投影字段自行声明读取来源；当存在 `field = "title"` 的投影时，schema 或 descriptor 暴露对应的 `optionTitleField`。枚举来源在静态对象或 SQL 投影中出现 Java 枚举常量名时，会先按声明的 `CodeTitleEnum` 精确归一为业务 code；字典来源始终按持久化 code 精确匹配，不做大小写模糊兼容。

## 计量单位边界

计量单位用于给动态字段和静态字段提供稳定单位目录。单位分类表达长度、重量、面积、体积、数量、时间等单位组；单位项目表达分类下的业务保存值、展示符号、默认精度和到分类基准值的线性换算参数。

基础换算只处理同分类内 `baseValue = value * factorToBase + offsetToBase` 这类上下文无关事实，例如 `kg/g`、`m/cm`、`L/ml`。

单位主数据按共享单位库维护。平台全局公开单位作为所有租户的兜底事实；租户公开单位优先于平台全局单位，供同一租户下多个应用共同消费。应用路径保留为兼容和应用视角消费入口，不作为默认隔离模型。

`1箱=12瓶`、`1托=48箱`、`1卷=30米` 这类依赖模块、物料、规格或记录上下文的硬换算规则不写进单位目录本身，而由计量单位换算规则表达。规则保存 from/to 的单位分类和单位 code，可按租户/全局、模块或记录上下文生效，运行时支持链式解析和反向换算。它仍是平台换算配置能力，不替代库存包装、BOM、供应商规格或批次差异等业务模型。

计量单位被元数据消费时，配置入口在模块字段配置上。主业务字段必须是数值字段，并声明 `unitCategoryAlias`、`baseUnitCode`、单位输入模式、默认单位、换算模式等契约。可选单位字段使用伴生字段表达，字段角色为 `MEASURE_UNIT`，归属于主业务字段；标准值字段使用影子字段表达，字段角色为 `MEASURE_BASE_VALUE`，由平台管理，归属于主业务字段。

典型字段形态是 `quantity`、`quantityUnit`、`quantityBase`：`quantity` 是业务输入值，`quantityUnit` 保存业务单位 code，`quantityBase` 保存按基准单位归一后的数值。模块字段配置保存后，平台会按需要自动创建或复用伴生/影子字段，并在运行态刷新后由动态 `FieldDefinition.measureUnit` 暴露单位分类、固定/可选模式、伴生字段名、影子字段名、基准单位分类、基准单位、换算模式和单位必填约束，供动态运行态、页面配置和静态字段契约统一消费。计量单位字段能力不提供独立 prepare 入口，统一走模块字段配置保存。

动态记录保存和更新时，平台按 `FieldDefinition.measureUnit` 自动计算影子标准值字段。线性换算使用单位目录；业务硬换算使用计量单位换算规则，并可按模块和记录上下文字段选择规则。更新主数值或单位任一字段时都会重新计算标准值；只更新主数值时沿用记录已有单位。旧记录缺少单位且配置了默认单位时，保存链路会补写默认单位；单位必填时，显式清空单位但仍有数量会被拒绝；单位可选时，缺少单位不执行标准值归一并写空标准值。记录上下文字段在换算规则中使用 code 风格命名，例如字段 `skuId` 对应 `contextObjectType=sku_id`。

静态模型通过 `@MeasureUnitField` 声明同一套字段定义契约，平台编译时把注解转换为 `FieldDefinition.measureUnit`，用于 describe、校验和治理消费。静态声明仍要求业务模型显式提供单位伴生字段和标准值字段。当前注解不拦截静态 `CrudAbility` 的 insert/update；静态业务如果需要自动计算标准值，应显式调用后续平台归一门面，避免在业务 service 中复制动态保存链路。

进入配置包治理和跨环境迁移时，使用计量单位的动态模块应声明 `MEASURE_UNIT` 依赖。推荐依赖身份为 `platform + categoryAlias`，对应共享单位库；历史 `applicationAlias + categoryAlias` 继续兼容。健康检查会把缺少单位分类依赖、缺少单位伴生字段、缺少标准值字段或上下文字段缺失作为迁移风险输出。

## 币种与汇率边界

币种与汇率用于给 CRM、ERP、MES 和低代码动态模块提供共同的金额基础口径。平台层只承诺币种事实、租户本位币、汇率类型、汇率日期和基础折算，不进入总账、汇兑损益、期末重估、税务发票、多法人合并抵消等财务专题深水区。

币种目录使用 ISO 4217 alpha-3 code 作为业务保存值，例如 `CNY`、`USD`、`EUR`。币种不是普通字典，平台会维护名称、符号、小数位、舍入方式和启停状态，用于金额展示、导入导出、基础折算和后续金额字段契约消费。租户态读取币种时，租户配置优先于平台全局配置；平台全局配置作为兜底事实。

租户本位币通过独立设置维护，不直接塞进租户核心模型。当前阶段只支持租户本位币；公司、法人、组织或账簿级本位币属于后续业务深化的 scope 扩展，不改变币种和汇率基础模型。

汇率类型用于表达不同业务口径，例如即期、月度、记账、报告或预算汇率。汇率按 `fromCurrencyCode + toCurrencyCode + rateTypeCode + effectiveDate` 维护，运行时按指定业务日期取不晚于该日期的最近启用汇率。租户汇率优先于平台全局汇率；后续如果进入 ERP 财务专题，可在此基础上扩展来源、审批、会计期间、重估和对账规则。

金额字段契约通过动态 `FieldDefinition.money` 表达，静态模型可用 `@MoneyField` 编译到同一契约。契约描述原币金额、币种字段、折算币种、本位币金额字段、汇率类型、汇率日期字段和可选汇率字段。模块字段配置保存后，平台会按需要自动创建或复用币种伴生字段和本位金额影子字段；固定币种不创建币种伴生字段，汇率影子字段只在显式绑定已有字段时使用。动态记录创建、更新及子表变更会按该契约归一本位金额与汇率，并接管默认币种、币种规范化和派生金额字段写入；静态保存链路暂不拦截，后续可在静态 service 门面侧按同一契约接入。金额字段能力不提供独立 prepare 入口，统一走模块字段配置保存。

配置包健康检查已经覆盖计量单位和金额字段的基础字段契约与依赖声明。导入导出列级联动仍属于后续深化能力。
