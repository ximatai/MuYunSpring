# 身份与权限专题概览

身份与权限专题把租户、组织、部门、用户、角色、动作授权、数据权限、菜单剪枝和当前用户上下文串成同一条后端治理链路，为静态模块和动态模块提供一致的身份来源、授权判断和数据范围约束。

本文只梳理平台能力和接入线索，不展开 Java 底层设计。实现细节以 `muyun-iam` 领域服务、`muyun-boot` Web 入口和相关 contract 测试为准。

## 能力定位

身份与权限不是独立于平台能力之外的业务模块，而是动作执行、动态 Web、静态 Web、菜单返回和审计上下文的共同前置能力。

核心定位：

1. 租户是平台数据隔离的身份根，`tenantId` 仍是基础字段和默认 Ability 作用域。
2. 当前用户上下文负责把登录用户、租户、组织和系统态操作者带入请求链路。
3. 动作权限约束「能不能执行某个模块动作」。
4. 数据权限约束「能在该动作下看到或操作哪些记录」，不替代租户基线隔离。
5. 菜单权限只做返回树剪枝，不改变菜单模型、菜单方案或菜单挂载关系。
6. 静态模块和动态模块都按 `moduleAlias + actionCode` 进入同一套权限口径。

## 主要对象

| 对象         | 标识                      | 说明                                                                                                                           |
| ------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 租户         | `iam.tenant`              | 平台身份根。租户 alias 当前等同于租户 ID；租户自身由系统态维护，支持启停和排序。                                               |
| 组织机构     | `iam.organization`        | 租户内机构树，表达公司、分支机构、事业部等组织主体；支持树、排序、启停，机构编码在租户内唯一。                                 |
| 部门         | `iam.department`          | 归属某个组织机构的部门树；支持树、排序、启停，部门编码在同一机构内唯一。                                                       |
| 职员         | `iam.employee`            | 租户内人员主数据，归属机构和部门，承载员工号、姓名、联系方式、启停状态和排序。                                                 |
| 职员账号     | 子资源                    | 职员与登录账号的一对一绑定关系，通过职员入口维护。                                                                             |
| 岗位分类     | `iam.position_category`   | 租户内岗位分类树，用于把岗位标准项按岗位族、序列或管理分组组织起来。分类只承担管理分组，不表达任岗或汇报关系。                 |
| 岗位         | `iam.position`            | 租户内岗位标准项，不强制绑定部门，可挂到岗位分类下，用于维护可复用岗位定义。                                                   |
| 职员任岗     | 子资源                    | 职员在某个机构、部门担任某个岗位的关系事实，通过职员入口维护。                                                                 |
| 用户         | `iam.user`                | 租户内登录账号，包含用户名、登录启停、密码状态和登录安全审计；用户名在租户内唯一。人员资料归职员维护。                         |
| 角色         | `iam.role`                | 租户内权限包。只保留账号角色和任职角色两条授权层级；角色组锁定为任职级角色包，数据授权角色锁定为任职级数据范围模板。           |
| 账号角色授权 | 授权事实                  | 使用 `AccountRoleGrant` 表达账号绑定账号角色，可携带管理作用域。                                                               |
| 任职角色授权 | 授权事实                  | 使用 `EmploymentRoleGrant` 表达具体任职绑定任职角色、角色组或数据授权角色。                                                    |
| 角色动作授权 | 授权事实                  | 角色到 `moduleAlias + actionCode` 的授权事实，包含数据权限策略和租户范围策略。                                                 |
| 当前用户     | `CurrentUser`             | 请求内身份快照，包含 `userId`、`username`、`tenantId`、`organizationId` 和 `system`。                                          |
| 业务主体     | `BusinessPrincipal`       | 权限聚合前的显式业务身份，可表达账号、职员或具体任岗。普通登录由当前用户推导；代办等场景由校验后的代办上下文提供。             |
| 职员代办     | `iam.employee_delegation` | 职员之间的业务代办关系事实，记录委托人、受托人、可选任岗、有效期和启停状态。当前先承载业务代办，不混入工作流审批接管执行链路。 |
| 代办上下文   | `ActingContext`           | 一次请求内的实际操作者、被代办业务主体、委托关系和可选模块动作范围。它不替代当前用户，也不会未经委托校验自动进入权限链路。     |

## 核心业务链路

### 登录与上下文

1. 用户调用登录入口提交 `tenantId + username + password`。
2. 登录服务在租户上下文内校验用户状态和密码，生成 Bearer token，并把 token hash、用户、租户、签发时间、空闲过期时间、绝对过期时间和最近访问时间写入 `iam_user_session`。
3. 后续请求由 Bearer token 解析当前用户；服务端只按 token hash 查询 session，不持久化明文 token。
4. `CurrentUserWebFilter` 将当前用户写入 `CurrentUserContext`；普通租户用户同步写入 `TenantContext`，系统用户进入系统态租户上下文。Servlet async redispatch 会重新绑定这些 scope 并延续同一 trace；需要在业务显式派发的短生命周期 worker 中执行时，调用方可捕获并使用 `WebRequestContext`，它只传播登录身份、租户与 trace，不传播动作授权或代办 scope。
5. session 使用滑动过期：有效访问会在节流窗口后刷新最近访问时间并延长空闲过期时间，但不会超过本次登录的绝对过期时间。
6. 同一用户允许多端登录，对应多条未撤销 session；登出、修改密码、禁用用户或用户失效时撤销对应 session。

### 租户应用开通

`TenantApplication` 表达租户是否可以使用某个应用。它是模块执行的产品可用性前置条件，不是菜单开关，也不替代角色动作授权或数据权限。

1. 普通租户用户执行模块动作时，平台先校验模块所属应用已对当前租户开通，再判断角色动作授权和数据权限；静态和动态模块复用同一动作授权链路。
2. 移除或全局停用应用会立即阻止该应用模块的页面、接口和动作访问，但不删除角色授权、菜单或配置事实；菜单可见性和角色授权目录同样只展示当前可用应用。重新启用并开通后可恢复使用。
3. 系统用户不受租户应用开通限制；`platform` 是系统态应用，不能分配给租户。
4. `iam` 是租户治理的必开基线应用。新建租户与启动期存量租户都会执行幂等补齐，不能把既有租户留在应用门禁之外而使其无法进入应用配置入口。
4. 新租户会自动开通 `iam`，且不能移除；租户停用才是整体暂停该租户访问的治理动作。

### 组织、部门、职员与用户

1. 租户由系统态维护，是用户、组织、部门、角色和菜单方案等租户内对象的上层边界。
2. 组织机构在租户下形成树，表达公司、分支机构、事业部等主体。
3. 部门归属组织机构，并在机构内形成部门树；部门不跨机构复用。
4. 职员归属一个主机构和一个主部门，用于承载清晰的人事身份主数据。
5. 岗位是租户内可复用标准项，不直接表达某个部门下的任职关系。
6. 职员任岗关系表达某个职员在某个机构、部门担任某个岗位；维护入口归入职员体系。
7. 用户账号归属租户，只表达登录主体和认证安全状态，不承载机构、部门、姓名、手机号、邮箱等人员档案。
8. 职员账号绑定表达登录账号对应的职员身份；当前职员和账号是可选一对一关系，不做一个账号多职员身份切换，也不做一个职员多账号。

### 角色与授权

角色授权设计见 [角色授权设计](ROLE_AUTHORIZATION_DESIGN.md)，对外稳定业务错误见[错误码目录](ERROR_CODE_DIRECTORY.md)。核心收口如下：

1. 角色按授权层级分为账号角色和任职角色。
2. 账号角色授予用户账号，用于平台管理员、租户管理员、机构管理员、运维账号或服务账号等登录身份级权限。
3. 任职角色授予职员任职，用于岗位职责、兼职、多部门任职和组织数据范围。
4. 不再提供职员级角色授权；职员本人相关能力通过业务规则或稳定归属字段表达。
5. 角色组锁定为任职级角色包，只能授予任职，只能包含任职级普通角色和最多一个数据授权角色。
6. 数据授权角色锁定为任职级数据范围模板，只为选择“继承数据授权”的动作提供范围，不直接授予业务动作资格。
7. `Role` 仍是唯一角色定义表，不新增账号角色表；账号和任职通过 `assignmentType` 区分。
8. 角色定义有治理归属和共享策略，通过 `ownerScopeType`、`ownerScopeId` 和 `sharePolicy` 表达平台、租户、机构私有或公开范围。
9. 账号角色授权和任职角色授权使用不同授权事实表，不再用通用 `RoleGrant(subjectType, subjectId)` 承载全部关系。
10. 角色定义归属只决定谁维护、谁可见、谁可拿来绑定；授权生效时的管理作用域、机构、部门和任职上下文仍由 `AccountRoleGrant` 或 `EmploymentRoleGrant` 提供。
11. 授权事实按 `moduleAlias + actionCode` 落表；配置动作和标准动作通过授权矩阵统一回显。
12. 动作继承会归并到最终权限动作，避免同一入口出现多套授权口径。

### 内置管理角色边界

平台超级管理员是系统账号身份，不归属普通租户，用于系统态维护租户、平台配置和全局治理对象。平台超级管理员可以继续由系统用户表达，也可以通过账号级系统角色授权表达，但不依赖职员或任职。

`tenant.admin` 是平台识别的租户管理员账号角色。授权事实仍落到 `AccountRoleGrant`，管理作用域必须为 `TENANT:tenantId`；角色用途由系统托管的 `Role.systemPurpose = TENANT_ADMIN` 表达，不把管理员标记写入账号。对当前租户已开通应用中的可授权动作，租户管理员在运行时获得当前租户全量动作和数据范围，不依赖逐条 `RoleAction`；应用未开通或被停用时仍先拒绝访问。租户管理员不获得系统态、跨租户、`iam.tenant` 或不可向租户开通的平台模块权限。

启动期会幂等修复每个租户的系统托管租户管理员角色，因此存量租户保留原有 `AccountRoleGrant` 即可进入该身份模型；历史 `RoleAction` 事实不会再决定租户管理员的运行时访问结果。

`organization.admin` 是机构管理员账号角色，用于给账号授予本机构及下级范围内的 IAM 治理能力。授权事实应落到 `AccountRoleGrant`，管理作用域为 `ORGANIZATION:organizationId`。当前授权覆盖组织、部门、职员和用户模块；机构管理员不默认获得角色管理、职员账号关系表、租户维护、平台元数据、动态模型或系统级配置模块权限。

新增租户或机构时，可以由开通动作默认创建管理员账号，并同步插入对应 `AccountRoleGrant`。账号表只表达登录账号事实，不写入管理员类型或作用域字段；管理员身份不应写死在程序分支中。

### 动作权限与数据权限

1. Web 入口和动作执行入口通过动作上下文声明当前模块、动作、动作级别和是否需要数据权限。
2. 动作授权先判断当前用户是否具备该模块动作。
3. 需要数据权限的动作继续解析数据范围策略。
4. 查询类动作将数据范围合入查询条件；记录类动作要求目标记录落在授权范围内。
5. 动态模块标准 CRUD、动态动作列表、记录动作可用性、descriptor 和 OpenAPI 都接入同一动作授权结果。

账号角色不配置组织、部门、本人、任职等数据范围。任职角色的动作开启数据权限时，必须选择具体范围或“继承数据授权”。授权工作台首次开启数据动作时默认写入明确的“继承数据授权”策略；它不是空值或运行时回退，用于从当前任职的生效数据授权角色解析范围，也不会与动作自身范围取并集或放宽已经显式配置的数据范围。关闭动作才表达无权限。

当前代码中已有的数据范围策略包括：

| 策略                      | 含义                                                                         |
| ------------------------- | ---------------------------------------------------------------------------- |
| `none`                    | 内部哨兵状态；表示动作未配置有效的数据范围，不作为授权工作台选项                 |
| `all`                     | 当前租户内的全部数据                                                         |
| `owner`                   | 本人负责                                                                     |
| `assignee`                | 负责人                                                                       |
| `member`                  | 相关人                                                                       |
| `organization`            | 本机构                                                                       |
| `organizationAndChildren` | 本机构及下级                                                                 |
| `department`              | 本部门                                                                       |
| `departmentAndChildren`   | 本部门及下级                                                                 |
| `inheritDataGrant`        | 继承数据授权。仅任职角色动作可用，用于从当前任职的生效数据授权角色解析范围。 |
| `referenceDependency`     | 按当前模块元数据声明的引用字段，继承目标模块 `view` 动作的数据范围；无有效解析时拒绝访问 |
| `custom`                  | 保留字段，当前授权入口拒绝开放                                               |

租户范围策略包括当前租户和全部租户。它只描述授权事实的租户适用范围，不取消平台基础租户隔离的默认语义。

数据范围字段有两种接入方式。普通业务记录、流程记录和动态记录优先使用平台标准权限字段，例如 `authUserId`、`authOrganizationId`、`authDepartmentId` 和 `authModuleAlias`。静态主数据如果已经有稳定业务归属字段，可以通过 `DataScopeFieldMappingAbility` 把标准权限语义投影到业务字段，例如组织使用 `id` 表达机构范围，部门使用 `organizationId` 和 `id`，职员使用 `organizationId` 和 `departmentId`。该映射只服务于数据权限裁剪，不作为通用字段别名系统。动态模型当前仍维持平台默认标准权限字段，后续如需开放动态字段投影，应通过元数据显式声明、字段类型校验和权限诊断能力单独推进。

相对数据范围需要结合授权上下文解释。账号角色不参与相对数据范围计算；任职角色按具体任职机构解释“本机构”“本机构及下级”，按具体任职部门解释“本部门”“本部门及下级”。

### 业务代办切入点

业务代办不改变登录身份。实际登录人仍由 `CurrentUser` 和审计上下文表达；被代办人进入权限链路前会先解析成显式 `BusinessPrincipal`。普通 `userId` 权限入口按账号角色和账号绑定职员后的任职角色聚合；显式业务主体入口只消费调用方给出的账号或任职，不从账号隐式扩展出全部人员身份。

`EmployeeDelegation` 作为职员体系内的关系事实维护，表达某个职员授权另一个职员在有效期内代办业务。委托关系可以绑定委托人任岗或受托人任岗，也可以按模块或具体动作收窄 scope；动作 scope 以 `moduleAlias + actionCode` 解释，不脱离模块单独生效。

代办执行前应先校验当前登录账号绑定到受托职员，再校验委托关系、有效期、任岗绑定和 scope，然后把校验后的 `BusinessPrincipal` 交给角色聚合与数据范围解析。`ActingContext` 只承载这次请求的操作者、被代办业务主体和委托关系，不允许绕过委托校验直接影响普通权限请求。

静态 Web 动作入口支持通过请求头声明被代办职员和可选任岗；受托职员不从请求读取，而是由当前登录账号绑定关系推导。声明代办时，入口先解析 `ActingContext`，命中当前模块和动作后，动作权限和数据权限都使用被代办业务主体判断；当前用户仍用于登录态、租户隔离和审计归属。

代办数据权限按被代办主体的角色授权上下文解释“本机构”“本部门”等相对范围；如果被代办主体没有对应授权，不回落到实际操作者的授权。数据授权角色和引用依赖范围在代办上下文中也必须按被代办主体解释，不借用实际操作者，避免放大数据可见性。

创建数据范围记录时，平台会为 `DataScopeCapable` 模型补齐默认业务归属。普通登录使用当前用户填充 `authUserId`、`authOrganizationId` 和 `authModuleAlias`；代办上下文命中当前模块和动作后，使用被代办业务主体填充可确定的账号、机构和部门归属。显式传入的归属字段不会被默认值覆盖；被代办主体没有账号 ID 时不会把实际操作者写成负责人。

标准生命周期会用当前登录用户填充 `createdBy` 和 `updatedBy`。代办场景下，审计字段仍记录实际操作者；被代办主体只进入权限、数据范围和业务归属，不写入创建人或更新人。

平台运行审计只做轻量动作留痕，不建设业务单据事件流水。动作事件和记录事件可记录代办委托 ID、被代办主体账号、职员、机构、部门和任岗 ID，用于排查实际操作者与业务主体关系；审计 payload 不承载表单字段快照、业务内容差异或业务状态流转明细。

### 菜单剪枝

菜单模型仍归平台菜单专题维护。权限专题只在返回当前用户菜单树时做可见性剪枝：

1. 后端根据当前用户推理菜单方案，前端不传 `menuSchemeAlias`。
2. 菜单节点挂载模块后，按模块 `menu` 动作判断是否可见。
3. 剪枝只影响本次返回结果，不修改菜单节点、菜单方案或模块挂载。
4. 菜单可见性同样要求所属应用已对当前租户开通，但菜单剪枝不是租户应用开通的唯一保护边界。

## 组织人员主数据

身份权限从账号权限延伸到组织人员主数据，但领域命名继续沿用当前平台语义，不为机构另造新名词。

### 组织与部门

`Organization` 继续表达机构语义，例如公司、分支机构、事业部等相对稳定的组织主体。机构可以形成树，用于表达集团、公司、分支机构之间的管理归属。

`Department` 表达部门模型。部门必须归属某个 `Organization`，并在机构内形成部门树。部门不跨机构复用；跨机构协作通过人员任职、兼职或后续人员组表达。

组织和部门拆开后，身份上下文和数据权限需要区分两类范围：

1. 机构范围：当前机构、机构及下级。
2. 部门范围：当前部门、部门及下级。

### 职员与用户

`Employee` 表达职员主数据。职员承载员工号、姓名、联系方式、主机构和主部门等人事身份，不等同于登录账号。员工号在同一机构内唯一，职员所在部门必须归属同一机构。

职员任岗关系表达职员的岗位事实。主岗必须匹配职员主机构和主部门；兼岗可以指向其他有效机构和部门。任职角色授权会参与权限和数据范围推导；工作流参与人解析和职员主部门同步不由任岗关系自动触发。

`UserAccount` 继续表达登录账号，只承载用户名、登录启停、密码状态、登录审计和账号级授权入口。账号与职员绑定作为职员子资源维护，用于从登录用户定位职员，并继续聚合该职员的任职角色授权和兼职上下文。当前账号与职员是可选一对一关系：账号可以不绑定职员，职员也可以暂不开通账号；账号与职员生命周期联动后续单独收口。

### 岗位与职务

`Position` 表示岗位标准项，例如销售经理岗、财务审核岗。岗位标准项不强制关联部门；某个部门下实际可任职岗位通过职员任岗等关系事实表达。

`JobTitle` 可作为轻量职务/职称模型，表达部门经理、总监、高级工程师等称谓或职责级别。暂不单独建设“职位”模型，避免和岗位、职务混用；如果后续出现岗位族、职级、招聘职位等明确场景，再独立扩展。

跨机构、跨部门兼职可以通过任岗事实和任职角色授权参与权限计算；流程参与人选择、跨机构审批放行和多账号身份切换仍按独立专题讨论。

## 边界说明

1. 本专题不把身份权限设计成独立低代码 DSL；动态模块和静态模块都回到平台动作、数据范围和菜单剪枝能力。
2. 数据权限不和 `tenantId` 基线隔离混淆；租户过滤仍是平台默认作用域。
3. 菜单权限不改变菜单配置事实，只裁剪当前用户可见树。
4. 平台动作审计只记录必要身份和权限判定上下文，不替代工作流、导入导出等专题流水。
5. 当前不展开完整管理端 UI、自定义数据权限表达式执行、动作前置依赖和跨模块同表记录归属。
6. 静态链路保持轻量：业务模块通过平台动作、数据范围能力和 Web 注解接入，不应手写一套权限流程。
