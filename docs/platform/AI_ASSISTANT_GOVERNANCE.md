# 智能助手能力融合专项治理

本文定义 MuYunSpring 面向终端用户的智能助手建设目标、分层边界、前后端接入方式和阶段验收口径。专项以用户可感知的工作台增强为首要交付，不把通用模型代理、任意 API 调用或概念完整的 Agent 框架作为先决条件。

模型连接、租户优先与平台兜底、凭据保护及文本调用边界见[模型连接配置](topics/configuration/AI_MODEL_INTEGRATION.md)。本文建立在该能力之上，不改变 `AiModelGateway` 作为业务侧模型访问门面的定位。

## 目标场景

专项从开始就面向三条完整业务链路设计和验收。

### 找到业务和数据

用户通过自然语言描述想访问的业务或数据，助手应能够：

1. 在当前用户可见的菜单中匹配业务入口。
2. 复用 Workbench 正式导航机制打开菜单和页签。
3. 等待目标页面建立可交互上下文。
4. 读取页面声明的查询项、字段类型和可用操作。
5. 将用户描述转换为合法查询条件并应用到页面。
6. 按需选择或打开用户有权访问的记录。

完成标准是浏览器进入正确页面并呈现目标数据，不以模型仅返回菜单名称或查询建议作为完成。

### 理解并填写业务单据

用户描述要填报的业务事实后，助手应能够：

1. 找到并打开对应业务页面。
2. 通过页面正式入口启动新建或编辑。
3. 读取当前表单的字段、类型、必填性、可编辑性、选项和引用定义。
4. 将自然语言映射为结构化字段补丁。
5. 通过页面字段变更管线填写草稿，继续触发公式、引用依赖清理、校验和脏状态管理。
6. 将填写后的真实表单交给用户检查和修改。

首期停在“草稿已填写、等待用户保存”。助手不得直接修改组件内部状态，也不得猜测引用记录 ID。

### 编排动态模块元数据

用户描述既有动态模块所需的数据结构后，助手最终应能够：

1. 定位目标模块和元数据关系，建立用户可见的本地候选。
2. 推导并配置字段类型、必填性、选项和引用关系。
3. 执行平台已有的模型校验和物理结构预检。
4. 展示字段、关系和数据库影响的结构化变更摘要。
5. 经用户明确确认后进入元数据领域已有的 change-set 生效链路。

该场景从第一阶段起就是架构约束，而不是与前两个场景无关的远期 Agent。动态配置应复用已经成立的配置治理能力，不能让模型直接修改生效配置或数据库结构。本专项以既有动态模块的元数据编排闭环为边界；动作编排、业务规则、页面与表单布局配置另行治理，不作为本次智能助手交付的阻塞项。

## 存量基础与待治理缺口

模型网关、Workbench 导航、标准页面会话和表单变更管线是本专项复用的存量基础。助手结构化回合、前端运行时、能力注册和 Surface 已按本文分层落地；当前建设重点是完成第三阶段真实场景验收，并继续收紧跨页面任务、交互取消和配置生效边界。

配置治理不能被视为已经具备统一的“模块草稿到发布”事务。页面修订已有专门发布服务；现有元数据模型 change-set 已能对既有关系和字段做客户端 proposal、预览、指纹校验、事务 apply 和一次运行态激活，但不覆盖新建模块、完整页面编排或模块级持久候选。元数据及字段的普通保存仍会触发 schema ensure 和运行态刷新；已有配置包版本指针与导入草稿也不等同于实际配置的统一发布或回滚。

三种状态必须保持清晰边界：浏览器未保存草稿、已持久化但未生效的配置候选、已经生效的配置。需要补齐的隔离、校验和生效能力由配置领域拥有，助手只接入其正式入口。不得以普通元数据保存模拟“无副作用草稿”，也不承诺跨模块修改天然具有原子发布或自动回滚能力。第三阶段继续按已确认的治理缺口、范围和失败处理边界推进。

## 建设原则

1. **用户交互优先。** 首期增强 Workbench、标准页面和配置工作区的现有交互，后端通用 API 工具调用不是优先目标。
2. **复用正式入口。** 助手打开菜单、应用查询、修改字段和触发动作时，必须调用用户手工操作所使用的正式机制。
3. **能力归原领域所有。** 助手只暴露和组合平台已有能力，不复制 CRUD、权限、页面状态或配置发布实现。
4. **动静一体。** 静态 Java 模块和动态元数据模块应向助手提供来源无关的页面、表单和动作语义，不建立两套助手运行时。
5. **前端状态不透明开放。** 页面主动投影适合助手使用的上下文和能力，不向助手暴露 Vue 状态树、组件引用或 DOM。
6. **Prompt 不产生权限。** Prompt、Skill 和能力描述只影响模型行为；真实执行继续遵守身份、租户、动作权限、数据范围、业务可用性和审计。
7. **按真实复用提炼。** 首期只建立完成目标场景所需的窄契约；第二种实现或稳定复用出现后，再提升为更通用机制。

## 宏观分层

```text
交互与交付层
  助手面板、流式反馈、确认和客户端效果
        ↓
前端 Assistant Runtime
  当前 Surface、能力目录、能力执行和回合衔接
        ↕
后端 Assistant 会话入口
  系统提示词、模型调用、结构化能力请求和运行限制
        ↓
AiModelGateway
  当前平台或租户的模型路由与供应商传输

前端 Assistant Runtime
        ↓
既有前端平台机制
  Workbench 导航、页面会话、查询、表单草稿和页面动作
        ↓
既有后端业务与治理链路
  权限、数据范围、CRUD、动作、校验、审计和发布
```

### 模型基础设施

`AiModelGateway` 继续负责按当前身份上下文解析模型连接并完成供应商调用。助手使用的结构化消息和工具调用协议已经由供应商无关契约承接；页面状态、业务权限和能力执行仍不进入模型网关。

### 后端助手会话

后端首期只提供固定用途的助手会话入口，职责包括：

- 持有平台系统提示词和通用行为约束。
- 调用 `AiModelGateway`。
- 接收结构化页面上下文和当前可用能力描述。
- 返回文本增量或结构化能力调用请求。
- 限制单回合消息大小、能力调用次数、超时和取消。
- 保持模型凭据不进入浏览器。

该入口不是接收任意提示词、任意工具或任意模型参数的公共代理。首期不要求后端先建设通用业务 API 工具目录。

### 前端 Assistant Runtime

前端运行时负责：

- 跟踪当前活动工作台页面。
- 取得当前页面主动贡献的上下文和能力。
- 将经过裁剪的上下文与能力描述提交给后端。
- 校验模型请求的能力是否仍在当前目录中。
- 调用现有前端机制执行菜单、查询、表单等交互。
- 将执行结果和更新后的页面上下文返回给下一回合。
- 在页面切换后重新绑定当前能力目录。

首期不引入独立工作流引擎。模型回合、当前页面 Surface 和有限的能力调用足以承载第一批跨页面任务。

## 第一阶段架构基线

### 职责与依赖方向

智能助手沿用当前模块边界，不新增 Gradle 子项目或前端包。第一阶段确定以下归属：

| 职责                                         | 所有者                          | 依赖边界                                      |
| -------------------------------------------- | ------------------------------- | --------------------------------------------- |
| 模型连接、路由和供应商传输                   | `muyun-platform` 的 AI 模型能力 | 不依赖助手、页面或 Web 类型                   |
| 助手回合编排、平台 Prompt 和运行限制         | `muyun-platform`                | 只通过模型门面访问模型，不直接调用 Controller |
| 助手 HTTP 与流式交付                         | `muyun-platform-web`            | 适配助手回合，不承载页面状态或业务执行        |
| 后端回合编排与模型协议类型                   | `muyun-platform`                | 不依赖 Servlet、前端页面和供应商 SDK 类型     |
| 浏览器端回合事件、上下文、能力调用和结果类型 | `web-contracts`                 | 只表达来源无关语义，不依赖 Vue 和 UI adapter  |
| 助手会话 client 与流式协议解析               | `web-core`                      | 不持有具体页面和业务模块状态                  |
| Surface 注册端口和浏览器端纯契约             | `web-core` 与 `web-contracts`   | 供页面运行器向上贡献，不依赖 Workbench        |
| 当前 Surface、能力合并、回合衔接和助手面板   | `platform-workbench`            | 组合活动页面贡献，通过 `vue-ui-antdv` 渲染    |
| 标准页面上下文和交互能力                     | `dynamic-page-runtime`          | 适配现有页面会话、查询和表单变更入口          |
| 动态配置候选、校验和生效                     | 配置与治理领域                  | 独立于助手补齐，助手只消费正式治理入口        |

后端依赖保持 `platform-web → platform assistant service → model gateway`；前端依赖保持“助手壳层 → Assistant Runtime → 当前 Surface → 所属运行器正式入口”。平台领域不得反向依赖 Web descriptor，页面运行器也不得把完整会话对象提升为助手公共契约。

现有 `AiModelGateway` 保留 `generate/stream` 文本契约兼容，同时在同一公共模型门面提供供应商无关的结构化回合与工具调用契约。助手编排只依赖这个归一化模型协议，不能直接持有供应商 SDK、连接配置或内部 `AiModelClient`，也不能把自由 JSON 文本当作可靠的能力调用协议。助手的页面上下文、能力目录和确认策略仍属于助手层，不进入模型基础设施；具体 Java 类型、流式事件和 provider adapter 行为已经由第二阶段契约测试锁定。

### 核心运行链

一次前端能力调用按以下链路完成：

1. Workbench 确定当前活动页面及其 Surface 实例。
2. Assistant Runtime 获取该实例主动投影的上下文和当前可用能力，并生成绑定页面实例、Surface 代次和任务上下文修订的调用令牌。
3. 助手 client 通过当前 Surface 注册的不透明请求入口发起回合；该入口复用页面已经建立的受控 HTTP client。系统用户在租户页面中选择的租户作用域继续由现有受控请求头和 Web 过滤链建立，Workbench 不读取或拼接租户 ID。
4. 后端从认证会话和 `TenantContext` 取得调用身份，运行时解析当前模型连接；租户、用户和模型配置不由模型参数指定。
5. 模型返回文本或结构化能力请求。后端只交付能力意图，不代替前端操作页面。
6. Assistant Runtime 校验能力编码、参数结构和调用令牌；页面、页签、记录、编辑草稿或租户已经变化时拒绝旧调用。
7. 当前 Surface 调用所属运行器的正式入口执行交互。执行前以及每次异步返回产生客户端效果前都重新校验令牌；页签切换、Surface 撤销或显式取消会中止关联的 `AbortSignal`，其他上下文修订会使调用失效并丢弃结果。该交互产生的业务请求继续经过原有权限、数据范围、校验和审计链。
8. 前端返回结构化执行结果；导航或页面重建后等待新 Surface 就绪，再开始下一回合。

Workbench 按稳定的页签实例标识持有 Surface 注册，不以“最后注册的组件”判断活动页面；这同时覆盖 `KeepAlive` 下非活动页面仍挂载的情况。Surface 代次随页面宿主卸载、租户作用域切换和业务会话重建而变化；调用令牌分别携带页面上下文修订与用户交互修订，用于区分后台刷新和用户主动改变记录、草稿或查询范围。这些字段及失效行为已经由第二阶段契约测试锁定。

### 上下文事实归属

| 事实                   | 权威来源                               | 助手使用方式                                                          |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------- |
| 当前用户和系统身份     | 后端认证上下文                         | 后端自行读取；前端提交值不作为授权依据                                |
| 当前租户执行作用域     | 页面受控 HTTP client 与 Web 身份过滤链 | Surface 只注册不透明请求入口；Workbench 和模型均不可读取或覆盖租户 ID |
| 可见菜单               | 已按身份剪枝的 Workbench 菜单树        | Workbench Surface 提供候选和正式打开入口                              |
| 当前页签和页面身份     | Workbench                              | 用于选择活动 Surface，不由模型构造任意 route                          |
| 页面字段、查询项和动作 | resolved 页面描述和页面会话            | 页面 Surface 裁剪后提供，不读取 DOM                                   |
| 记录和表单草稿         | 当前页面业务会话                       | 只投影任务必需字段，修改进入正式状态管线                              |
| 模型连接与凭据         | 后端模型配置和路由                     | 仅模型基础设施可见，绝不进入助手上下文                                |
| 平台 Prompt 和运行限制 | 后端助手服务                           | 客户端上下文和业务数据不能覆盖                                        |

助手按“用户目标—必要澄清—继续执行”理解连续回合。用户只需表达想完成的事情，无需预先拆分页面步骤；模型结合受限对话历史、最新页面事实和当前能力目录决定下一步。信息足够时直接调用能力，必要事实缺失或存在歧义时只提出一个简洁问题，用户回答后继续原目标。前端只携带受消息数、单条长度和总长度约束的当前面板历史，状态提示和工具结果不混入对话；每个执行步骤仍重新读取当前 Surface，历史不能覆盖新鲜页面事实或产生权限。

当前不持久化完整对话，也不在助手主循环中编码“新增职员”“填写日报”等业务流程。业务差异继续由 Surface 的上下文与能力表达，模型负责理解目标和组合能力。只有经过真实调用成本或偏航风险验证的少数场景，才可通过可插拔指导补充约束，并且不得改变通用调度主链。日志默认记录 trace、回合和能力执行事实，不默认持久化完整用户消息、模型内容或业务记录正文。

平台大量页面由稳定范式生成，模型不应在每个回合从零推导这些公共操作关系。后端按已知 Surface 类型和已声明的公共能力组合，附加受平台控制的精简操作知识：Workbench 说明可见菜单检索与正式导航，标准记录页说明浏览、查询、新建或编辑草稿、表单描述、批量字段修改和引用解析，元数据治理说明候选、目标解析和预检。该知识只解释平台范式，不包含职员、部门、日报等业务流程，也不改变 Surface 实际声明的能力、参数或权限；未知 Surface 不获得推测性指导。标准页或治理页组合了 Workbench 导航能力时，会同时获得导航范式知识。

| 存量机制                            | 结论                                                  | 接入边界                                                      |
| ----------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------- |
| `AiModelGateway` 与运行时模型路由   | 直接复用模型选择和供应商隔离                          | 使用供应商无关的结构化回合表达，不加入页面业务语义            |
| `StreamingHttpClient`               | 复用认证、取消和响应流                                | 使用助手事件解析，保持普通 `HttpClient` 接入兼容              |
| `WorkbenchNavigation`               | 作为导航唯一执行入口                                  | Workbench Surface 提供可见菜单查找和活动页上下文              |
| `ModulePageHostSession`             | 作为标准页面 Surface 生命周期所有者                   | 已负责在页面状态稳定后注册窄 Surface，并在停用或重建时撤销    |
| `ModulePageSessionView`             | 内部状态足以支持查询、选中和表单操作                  | 暴露面过宽，只由运行器内部 adapter 使用，不作为公共助手 API   |
| resolved 页面描述、查询项和表单字段 | 作为页面理解的权威来源                                | 只暴露面向助手的最小投影，并裁剪敏感字段                      |
| 页面字段变更、引用候选和计算公式    | 作为表单填写的正式执行链                              | 通过 Surface 窄方法接入，禁止直接赋值草稿对象                 |
| 页面动作、权限和数据范围            | 继续承担业务执行治理                                  | 能力发现不等于授权，真正执行时仍重新校验                      |
| 页面修订发布                        | 可复用已有页面候选与发布能力                          | 只覆盖页面修订，不代表整个动态模块统一发布                    |
| 元数据模型 change-set               | 复用既有模型预览、指纹防漂移、事务 apply 和运行态激活 | 当前面向既有关系与字段的客户端 proposal，不等于模块级持久候选 |
| 元数据及字段普通保存                | 不能作为隔离配置草稿                                  | 需由配置领域补候选、生效和失败收口边界                        |
| 配置包归档、指针与导入草稿          | 可复用快照、健康和迁移事实                            | 当前不写实际配置、不切运行态，不能冒充发布或回滚              |

### 配置领域前置治理

第三阶段的元数据编排交付依赖现有模型 change-set 候选边界。该边界应表达候选内容、基线版本、结构化校验、真实预览、差异摘要、确认后的生效操作和失败收口。它由元数据治理领域形成稳定门面，助手不拥有配置状态机。

第一阶段不在助手专题内设计新的配置存储模型，但明确后续实现必须先回答：

1. 元数据关系与字段候选如何沿用客户端 change-set，哪些写入会影响 schema 或运行态。
2. 预检如何基于候选和基线版本生成稳定指纹，并阻止过期候选生效。
3. 一次生效包含哪些元数据和物理结构事实，失败时如何事务回滚或明确报告失败。
4. 已有模型预检、事务 apply、schema ensure 和运行态激活分别承担什么。

该前置能力可以在第二阶段并行治理，但进入第三阶段动态配置实现前必须形成明确契约和测试证据。

最低治理范围已经确定：候选必须绑定稳定模块、关系身份和基线版本，复用现有 change-set 的预览、指纹、事务 apply 与运行态激活，并在实际写入前完成预检。元数据与 schema 的生效边界由现有配置领域契约负责，部分失败不得报告成功。动作、业务规则和页面配置不并入本次 change-set，也不要求本专项为它们设计统一发布模型。

### 目标场景架构映射

| 目标场景       | 上下文来源                                 | 正式执行入口                               | 回合结果                                     |
| -------------- | ------------------------------------------ | ------------------------------------------ | -------------------------------------------- |
| 找到业务和数据 | Workbench 可见菜单、活动页签与页面查询描述 | `WorkbenchNavigation`、页面查询和记录入口  | 新 Surface、查询状态和可见结果摘要           |
| 填报业务单据   | 页面表单描述、当前草稿和引用候选定义       | 新建或编辑入口、字段变更管线和引用候选解析 | 可见且未保存的表单草稿、校验状态和变更摘要   |
| 编排动态元数据 | 元数据工作区上下文与模型 change-set 候选   | 经治理的候选修改、校验、预览及生效入口     | 候选版本、真实预览、差异摘要和明确的生效结果 |

三类场景的差异留在各自 Surface 与领域入口中。助手回合只处理上下文发现、能力意图、结构化结果和下一 Surface，不按场景增加主流程分支。

### 第一阶段取舍

**当前确定：**

- 采用模型在后端、页面能力在前端执行的主链路。
- 前端以活动 Surface 为上下文和能力边界，跨页面后重新发现能力。
- 初始能力以代码贡献为主，执行权和权限校验留在原有机制。
- 三个最终场景使用同一回合与 Surface 机制。
- 不新增独立 Agent Gradle 模块、前端包或通用后端工具平台。

**第二阶段验证后再收口：**

- 结构化模型协议的具体 Java 类型、provider adapter 映射和流式事件字段。
- Surface 注册接口、代次字段和能力 schema 的最终命名。
- Prompt 与代码级 Skill 贡献的最小公共形态。
- 会话历史由前端携带到何种长度，何时需要服务端持久化。

**明确不由助手专题解决：**

- 元数据候选、生效、回滚和 schema 迁移的领域状态机。
- 业务 API、页面动作和权限体系中已经存在的业务规则。
- 任意网页或第三方应用的 DOM 自动化。

至此，智能助手第一阶段收口为上述职责、运行链、事实归属、存量映射和配置治理前置条件。第二阶段可以在这些边界内验证具体契约命名；配置领域的候选与失败恢复机制仍是第三阶段动态配置交付的前置工作，不以本阶段文档完成视为已经具备。若实现需要反转既定依赖或让助手持有新的业务事实源，应回到本阶段重新评估，而不是以局部适配绕过。

## 前端接入边界

### Assistant Surface

每个可由助手理解和操作的前端区域通过一个受控 Surface 提供能力：

```ts
interface AssistantSurface {
  describe(): AssistantSurfaceContext;
  capabilities(): AssistantCapability[];
}
```

Surface 通过 `web-core` 的注册端口按页签实例注册，并提供任务上下文修订、用户交互作用域、可选的执行前稳定入口和不透明的助手回合请求入口；生命周期代次由注册中心分配，页面无需自行制造全局唯一值。Workbench 只激活当前页签对应的注册项；页签切换和 Surface 撤销会取消已有调用，代次或用户交互作用域变化会使旧令牌失效。后台查询、加载和展示投影变化只修订任务上下文，不得伪装成用户交互变化；运行时在模型决策前通过 Surface 稳定入口等待这些过渡完成并读取新上下文。稳定入口不得等待缺失的用户输入，也不得自行产生页面效果。下列名称对应当前职责和实现边界，公共行为由第二阶段契约测试约束。

阶段性 Surface 包括：

| Surface                              | 所有者                 | 职责                                                   |
| ------------------------------------ | ---------------------- | ------------------------------------------------------ |
| `WorkbenchAssistantSurface`          | `platform-workbench`   | 可见菜单查找、正式菜单导航和当前页签上下文             |
| `ModulePageAssistantSurface`         | `dynamic-page-runtime` | 来源无关的页面、查询、选中记录和表单草稿能力           |
| `MetadataGovernanceAssistantSurface` | 元数据治理工作区       | 贡献字段候选、确定性目标解析和正式 change-set 预检入口 |

页面导航或页签切换后，新页面注册自己的 Surface。助手下一回合必须读取新 Surface，不沿用上一页面的能力和字段描述。

### Assistant Capability

前端能力是代码级、类型化的受控入口：

```ts
interface AssistantCapability<Input = unknown, Output = unknown> {
  code: string;
  description: string;
  inputSchema: unknown;
  available(context: AssistantSurfaceContext): boolean;
  execute(input: Input, context: AssistantExecutionContext): Promise<Output>;
}
```

能力注册只描述如何向助手暴露现有前端机制，不重新实现业务能力。`execute` 必须调用所属层的正式门面：

- 菜单导航调用 `WorkbenchNavigation`，不直接写 Router 或浏览器 history。
- 查询调用页面运行器的查询状态入口，不拼装私有 HTTP 请求。
- 表单回填调用字段变更管线，不直接修改 `editingRecord`。
- 页面动作调用已解析的页面动作入口，不让模型拼 URL。
- 动作结果复用现有数据变化事实和本地 reaction。

### 上下文投影

Surface 只提供完成当前任务所需的最小上下文：

- 页面身份、标题、模块和模式。
- 当前选中记录的必要标识和显示名称。
- 查询项及其类型和可选条件。
- 当前可见、可编辑的表单字段。
- 当前页面实际可用的动作。
- 编辑、脏状态、校验和加载状态。

凭据、密文、受保护字段的原始值、不可见字段、组件内部状态和无关记录不得进入助手上下文。记录内容和工具返回值都作为不可信业务数据处理，不能改变平台系统约束。当前记录读投影先在服务端完成字段保护，助手只能接触浏览器已获得的投影结果；后续若要连用户可见的脱敏文本也排除，必须由服务端解析描述符发布来源无关的助手暴露事实，不在前端按字段名或控件类型猜测。

## 能力、Prompt 与 Skill

| 概念          | 定位                                           |
| ------------- | ---------------------------------------------- |
| Capability    | 原子、结构化、可执行的前端或后端能力           |
| Context       | 当前页面主动提供的只读任务事实                 |
| Prompt        | 平台持有的行为约束和任务说明，不承载权限       |
| Skill         | 一组 Capability、Context 和任务指导的组合      |
| Client Effect | 导航、选择、草稿修改等由前端正式机制完成的效果 |

首期不建立可配置的 Skill 实体、Skill 市场或在线 Prompt 编排。先用代码组合完成真实场景；当“业务查找”“单据填报”“动态配置”等多个稳定组合出现后，再提炼轻量的 `AssistantSkillContribution`。

Skill 不得包含可绕过平台的脚本、任意 URL 或任意 Bean 名。它只组织已注册能力，且不改变能力执行时的权限判断。

稳定页面范式的操作知识由后端平台目录持有，并通过 Surface 类型与已声明能力组合选择；它是比 Skill 更基础的公共背景，不为某个业务目标编排步骤。页面仍只贡献当前事实和可执行能力，模型结合范式知识自行规划。这样可以减少重复描述和无效探测，同时避免把前端业务数据提升为系统 Prompt。

## 首批能力目录

### Workbench

```text
workbench.find-menu
workbench.open-menu
```

菜单候选来自当前用户已经获得的可见菜单树。模型不得构造未授权菜单或任意业务路径。

### 标准页面

```text
query.describe
query.apply-quick-search
record.start-create
record.start-edit
scope.select-tenant
scope.select-navigator
```

查询条件必须由页面已声明的查询项编译；字段、操作符和值继续经过页面现有校验和后端数据范围。作用域能力只在页面当前结构和权限允许时注册。到达用户要求的页面或记录即视为完成，只有用户明确要求创建或修改数据时才能进入对应草稿。

### 表单草稿

```text
form.describe
form.patch-draft
reference.resolve-and-patch
reference.search-options
reference.patch-draft
```

字段补丁逐字段进入正式变更管线。引用字段通过正式候选解析获得记录身份，不接受模型猜测的内部 ID。首期不向助手开放自动保存。

### 配置治理

元数据编排通过配置工作区 Surface 接入，按业务意图提供窄门面：

```text
configuration.describe-metadata-model
configuration.find-metadata-field-targets
configuration.add-metadata-field-draft
configuration.add-metadata-property-field-draft
configuration.update-metadata-field-draft
configuration.preview-metadata-draft
```

这些能力适配现有元数据编辑会话和 change-set，不成为第二套元数据实现。候选修改只进入用户可见、可继续编辑和取消的本地候选；预检返回差异和校验结果，但不向模型交付可复用的指纹。正式 apply 不作为模型能力注册，用户通过页面保存与确认入口决定是否生效，执行时重新预检并校验候选版本。动作、业务规则、页面和表单布局配置不进入本次能力目录。

## 助手回合协议

首期采用“模型在后端、用户交互能力在前端”的回合模式：

1. 前端提交用户消息、当前 Surface 上下文和当前可用能力描述。
2. 后端调用模型并返回文本或能力调用请求。
3. 前端确认能力仍可用，校验参数后调用正式前端机制。
4. 页面后台过渡结束后，前端重新生成上下文；用户交互作用域或活动 Surface 变化时，旧调用失效。
5. 前端将能力结果和新上下文提交到下一回合。
6. 模型继续处理，直至完成、失败、需要用户确认或达到运行限制。

运行时只自动吸收不改变用户交互作用域的后台变化。真实的记录切换、租户切换、表单编辑等冲突仍会暂停当前回合，但面板保留未完成的用户目标，使用户可以在确认页面后用“继续”或补充信息恢复对话，无需重新完整描述任务。用户显式取消的目标不进入后续历史。

阶段协议只需表达：

```text
text-delta
capability-call
capability-result
confirmation-required
completed
failed
```

首期可使用流式 HTTP 与连续回合请求，不因概念完整性提前引入 WebSocket、后台任务或持久化 Agent 工作流。

### 面向用户的交互内容模型

助手消息不能长期停留在“一个文本字符串加若干瞬时按钮”。用户澄清、下一步建议和执行确认都属于对话本身，应与提出它们的助手消息保持关联，并能表达已经回答、取消、替换或失效。当前回合响应支持文本及一个可选的受控选择交互，按文本、选择的顺序展示：

```text
text
selection
```

`text` 使用受限 Markdown 展示，不接受原始 HTML、脚本或任意远程资源。`selection` 只表达单选交互，至少包含稳定的交互标识、提示文本、输入策略、呈现方式和 2 至 8 个不透明选项。首期不以通用 UI Schema 表达表单、页面组件或客户端命令。

选择区分两种输入策略：

| 输入策略             | 普通文本输入 | 用途                                               |
| -------------------- | ------------ | -------------------------------------------------- |
| `free_text_allowed`  | 保持可用     | 给出常见下一步，用户可以点选，也可以继续自由描述   |
| `selection_required` | 暂时不可用   | 缺少一个必须明确的分支，回答前不能继续当前助手任务 |

“确认 / 取消”是 `selection_required` 的标准呈现方式，不建立另一套确认协议。取消只拒绝本次提议，不等于停止当前模型请求、结束会话或执行其他页面命令；确认也不授予权限。涉及持久化或高风险操作时，交互必须绑定具体能力、参数、对象范围和版本，真正执行前仍由所属业务入口重新校验权限、数据范围、版本和业务可用性。

交互卡片内嵌在提出问题的助手消息中。建议选择不阻塞输入框；必答选择在交互解决前禁用自由输入并说明原因。用户提交选择时生成结构化回答，同时保留可读标签供模型历史理解；发送期间禁止重复提交；失败且原页面上下文仍有效时允许显式重试。页面或上下文变化后，未回答的选择失效，用户重新描述目标；必答选择提供本地“放弃本次提议”入口，解除输入阻断。交互解决后原卡片继续显示最终状态，不弹出脱离上下文的全局确认框，也不保留仍可点击的旧按钮。

运行状态与消息内容保持分离。面板可以展示“正在理解”“正在执行页面操作”“正在组织回复”“正在取消”等短暂状态，但这些状态不进入模型历史。停止当前运行、拒绝确认和关闭对话是不同动作，不共享一个模糊的 `cancel` 语义。客户端拒绝不符合当前协议的交互并展示明确错误，恢复输入，不执行异常内容。未来扩展内容种类时再定义逐项降级契约。

当前助手会话仍是 Workbench 内的前端会话，不因引入选择交互提前建设服务端事件日志、多设备同步或持久化历史。首个增量由现有回合响应返回受控交互内容，面板在当前会话中维护其解决状态，并把结构化选择作为下一回合用户输入提交。只有跨页面重载、跨登录会话恢复或多客户端接力成为明确目标时，才把消息、交互状态、幂等提交和事件游标提升为服务端事实。

## 风险与确认

| 类型           | 示例                             | 首期策略                             |
| -------------- | -------------------------------- | ------------------------------------ |
| 只读上下文     | 描述页面、查找菜单、读取校验状态 | 可直接执行                           |
| 客户端可逆效果 | 打开菜单、应用查询、选择记录     | 执行后向用户展示结果                 |
| 未保存草稿     | 启动新建、填写表单或配置草稿     | 可执行，用户可见且可修改             |
| 普通持久化     | 保存记录、启停、普通业务动作     | 后续开放，执行前展示摘要并确认       |
| 高风险操作     | 删除、批量修改、权限配置         | 强确认并重新鉴权，首期不开放         |
| 元数据生效     | 应用元数据模型 change-set        | 校验、预览、差异确认后进入正式生效链 |

确认必须绑定具体能力、参数、对象范围和版本。确认后执行前仍要重新检查权限、版本、业务可用性和数据范围。

## 阶段任务与验收

建设按“架构治理 → 接入机制 → 能力与交互交付”三个阶段推进。第一阶段架构基线和第二阶段公共接入机制均已形成并通过契约验证，当前处于第三阶段的能力与交互交付。找业务与数据、填报单据、编排动态元数据是最终交付的三个组成部分，从开始就用于检验架构是否合理，但不各自成为建设阶段。

| 阶段     | 目标                       | 主要产出                                           | 完成判定                                               |
| -------- | -------------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| 第一阶段 | 明确架构骨架与存量边界     | 分层、职责、依赖方向、核心链路及必要治理项         | 三类目标场景都能映射到同一架构，关键缺口和取舍明确     |
| 第二阶段 | 建立轻量的能力接入机制     | 代码级注册、上下文贡献、调用与结果协议、运行时治理 | 代表性能力通过同一机制接入，新增能力无需修改助手主流程 |
| 第三阶段 | 丰富能力并完成用户交互交付 | 前端助手与三个目标场景的完整链路                   | 用户能查数据、填单据，并完成动态元数据编排与确认生效   |

### 第一阶段：架构治理与骨架确定

**阶段目标：** 明确智能助手在平台中的位置，以及模型访问、助手运行、前端交互和既有业务能力之间的职责与依赖。

**建设范围：**

- 复盘现有模型网关、Workbench、页面会话、表单、权限和配置治理的实际边界。
- 确定前后端分别拥有的上下文、执行能力和状态，明确跨端调用链。
- 明确哪些存量机制直接复用、哪些需要补窄门面、哪些存在职责错位并需要修正。
- 用查数据、填单据、动态配置三个场景推演架构，尤其检查动态配置是否被现有草稿和发布能力完整承接。
- 固化核心契约的职责和生命周期，不提前冻结所有接口名称、事件枚举或实现类。

**交付结果：** 可指导代码建设的架构方案、存量接入映射和必要治理项。本文中的接口与能力编码以实际接入形成的稳定契约为准；不因文档列出名称就新增框架或类。

**完成判定：**

1. 三个目标场景的上下文从哪里来、由谁执行、结果如何返回都有明确归属。
2. 前后端分工、依赖方向和身份权限边界清晰，模型网关保持原有职责。
3. 每项必要调整能说明根因、复用收益和范围，未把存量不存在的能力当作已经具备。
4. 第二阶段可以据此实现接入机制，无需重新决定宏观分层。

本阶段以架构治理结论为交付，不要求完成助手聊天界面或某一业务场景。

### 第二阶段：能力注册与运行机制建设

**阶段目标：** 将第一阶段的骨架落为轻量、可验证的代码机制，使现有前后端能力能够有序向助手开放。

**建设范围：**

- 建立代码级能力声明与注册，明确参数、结果、可用条件及执行入口。
- 建立工作台与页面的上下文贡献机制，以及页面切换、卸载、租户变化时的绑定和失效规则。
- 打通模型调用、结构化能力请求、前端执行、结果回传的完整运行链。
- 组织平台提示词、能力说明和场景指导；Skill 先保持代码组合，不建设在线编排平台。
- 补齐参数校验、敏感字段裁剪、运行限制、取消和错误处理等当前链路必需的治理。
- 选择少量代表性接入验证导航、表单变更和配置治理边界，检验注册机制是否真正复用现有入口。

**交付结果：** 可通过测试或最小调试入口运行的公共接入机制，以及供后续业务能力采用的接入范例。正式助手面板和完整业务能力在第三阶段交付。

**完成判定：**

1. 代表性能力能够注册、按上下文发现、执行并返回结构化结果。
2. 页面变化后的过期调用不会作用于另一页面、记录或租户；字段修改沿用已有联动管线。
3. 新增能力通过贡献声明和适配现有入口完成，无需在助手主流程中增加业务分支。
4. Prompt 和能力描述不能成为权限来源，后端业务访问继续执行既有授权与数据范围检查。
5. 关键契约已有测试支撑，能够进入第三阶段持续丰富能力。

**当前实现基线：**

- 模型公共门面保留已有文本生成与流式契约，并补充供应商无关的结构化回合、能力声明和能力调用协议。供应商适配层负责在平台能力编码与供应商工具名之间映射，助手运行时不依赖具体供应商协议。
- 后端助手回合入口固定系统指令并限制消息、能力、结果和载荷规模；模型适配层同时限制结构化响应体、能力调用数量和单次参数大小，公共响应契约拒绝重复调用标识。身份仍来自服务端当前用户上下文，页面上下文和能力目录只作为不可信输入参与模型推理。
- 前端面板在新用户消息前携带有界、角色明确的用户与助手历史；后端将其恢复为模型对话角色，并将最新用户消息、最新页面事实和本步能力结果单独组成当前消息。状态提示不进入历史，工具循环中的页面上下文仍逐步刷新，使澄清后的回答能够继续原目标而不会复用过期页面事实。
- `web-core` 提供按稳定页签实例注册的 Surface 端口、上下文快照、调用令牌、取消和过期调用治理。Surface 代次由注册中心单调生成；页面会话只贡献不含业务值的修订号，令牌不携带草稿正文，并且不能跨页面、记录、草稿或租户沿用。
- 能力产生客户端效果必须进入注册中心提供的受保护效果边界。该边界在效果发生前复验令牌，并记录效果后的预期令牌；非效果型异步调用和效果后的异步收尾都在完成后再次复验。合法效果会结束当前步骤，由调用方在下一步重新取得 Surface；效果后再次发生的用户编辑、页签变化或显式取消仍会丢弃过期结果。
- 动态标准页面通过正式页面会话接入，代表性能力覆盖页面描述、表单描述和有界批量草稿修改。批量修改先完整校验字段和值，再按声明顺序进入现有引用依赖清理和表单公式链，最终一次提交草稿状态，避免半批修改和无意义的多次重渲染；密码字段不向助手投影，文件和引用字段在正式候选解析能力接入前保持不可写。
- Workbench 以当前用户可见菜单树提供菜单查找与打开能力，只目录化能够通过正式导航入口解析的菜单。Workbench fallback Surface 保证首页和静态页仍能发现导航能力，页面 Surface 激活时在其上叠加页面能力。页面请求继续使用页面会话的作用域 HTTP 客户端，保留租户请求头和既有后端授权链。

上述基线用于证明公共机制能够承接导航和表单类能力，不等同于最终助手交付。元数据字段候选、目标解析和正式 change-set 预检已经接入；最终保存仍由用户在治理页面审阅确认，动作、业务规则和页面配置继续留给各自专项。

至此，第二阶段以结构化模型回合、服务端助手入口、前端 Surface 注册与运行治理、Workbench 导航范例和标准表单草稿范例完成收口。公共机制的边界已由后端、前端和组件生命周期测试锁定；后续业务能力应沿用该机制扩充，不在助手主流程中复制页面或业务逻辑。

### 第三阶段：能力丰富与交互交付

**阶段目标：** 在已验证的架构和接入机制上丰富平台能力，完成用户可直接使用的前端助手。

**建设范围：**

- 交付助手面板、流式反馈、执行结果、取消和必要确认交互。
- 通过既有注册机制接入 Workbench、标准页面、表单及配置工作区。
- 完成以下三个验收部分。它们可按依赖顺序实现，但共同组成这一阶段，不再拆成独立架构阶段。

| 验收部分       | 用户可见交付                                                   | 验收口径                                                     |
| -------------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| 找到业务和数据 | 根据描述打开业务页面、应用查询并展示记录                       | 真实浏览器中完成菜单匹配、导航、页面就绪、合法查询和结果呈现 |
| 填报业务单据   | 根据业务描述填写真实表单草稿，交由用户检查和保存               | 引用解析、公式、校验、字段保护和脏状态均沿用正式表单链路     |
| 编排动态元数据 | 根据描述为既有动态模块生成或修改字段候选，预检后由用户确认生效 | 一个代表性模型可从描述形成可见候选，经正式 change-set 生效   |

**交付结果：** 用户能通过同一个助手完成上述三类任务。元数据编排是核心验收部分，不能以配置建议、JSON 草案或不可审阅的后台修改替代完整候选与生效闭环。动作编排、业务规则、页面和表单布局配置留给后续专项。

**完成判定：**

1. 三类场景均完成真实浏览器验收，并覆盖适用的静态与动态页面接入。
2. 业务查询、表单修改和配置操作复用平台正式入口，没有助手专用业务状态或配置事实源。
3. 单据填写停在用户检查和保存边界；元数据生效绑定明确差异和版本，经用户确认后走正式 change-set 链。
4. 失败、取消和版本变化不会产生越权执行、错误页面修改或未经治理的部分生效。
5. 已接入能力可以继续通过同一机制扩充，无需重新建设助手运行时。

**当前交互增量：**

- 助手文本已经通过独立的受控 Markdown 边界展示标题、列表、引用、代码和表格；原始 HTML、危险链接和远程 Markdown 图片不会进入可执行 DOM。用户输入与运行状态继续按纯文本展示，避免把对话双方和系统反馈混成同一种内容来源。
- Workbench 已提供全局助手面板，支持消息提交、文本增量、分步结果反馈、显式取消和有界工具循环。结构化回合通过平台 SSE 逐段交付可见文本，并只在终态完整且结束原因匹配响应形态后交付经过校验的能力调用；供应商工具分片在模型适配层归一化，读取过程同时限制单事件、整回合及工具参数预算，前端不解析供应商协议。页面切换和显式取消会中断浏览器流及后端模型请求，不把半截响应当作完成回合；流式错误保持平台错误码、状态和追踪标识，只实现普通 JSON 请求的自定义 HTTP 客户端继续使用兼容入口。
- 面板携带有界对话历史支持宏观目标、必要澄清和继续执行；运行时不按菜单、职员、部门、单据或元数据场景枚举调度分支。模型始终结合当前 Surface 的事实和能力规划下一步，缺少必要选择时以普通助手文本提问，用户回答后沿原目标继续。
- 诊断沿既有日志与可选前端观察端口交付，不建立第二套业务流水。后端在当前请求 trace 下只记录回合传输方式、输入项数量、结束原因、能力调用数量、是否存在文本及异常类型；不记录用户消息、对话历史、页面上下文、模型正文、能力参数或结果。前端运行时可向受治理的适配器报告步骤、Surface 类型、能力编码、结果类别和重启原因；默认不持久化，也不包含页面业务值、输入参数、执行结果或供应商请求标识。观察端口失败不得影响助手执行。
- 能力执行结果与后续说明分别记录。运行时通过不同入口区分只读结果、受调用令牌保护的内部状态提交和实际页面效果；只有通过 `applyEffect` 提交的用户可见效果计入页面操作，引用候选的一次性选择缓存通过内部状态入口提交。后续请求失败时，只携带并提示已经生效的页面操作，不把只读调用、缓存重放、内部状态或局部执行误报为整个用户目标完成。用户取消和页面上下文失效仍沿用各自的明确反馈。
- 运行时在每一步重新读取当前 Surface。导航只等待助手触发的目标页签与路由完成挂载；等待超时、用户切换页签或记录、上下文再次修订都会取消任务。只有助手导航后的同页 fallback Surface 被正式页面 Surface 替换时，才允许重新发起被中断的模型决策。
- 同一用户消息内，参数一致且已经成功的能力调用不会再次产生副作用；运行时复用既有结构化结果并结束无进展循环。上一 Surface 的执行结果可以交给新 Surface 的模型回合，不要求属于新页面的能力目录。
- OpenAI 兼容供应商适配层统一补齐对象工具参数的空 `properties`，避免各页面能力为供应商协议差异增加特例。
- 标准页面只在真实编辑草稿存在时声明表单可写，浏览态不会向模型虚构写入能力。
- 标准列表通过来源无关的查询控制端口向页面 Surface 提供查询状态、快速搜索和当前可见结果。控制端口只调用列表已有的查询状态与加载入口，不拼装助手专用请求；静态模块和动态模块继续复用同一组件链路。
- 查询结果只投影当前页面已显示的列表列，隐藏记录字段不会进入模型上下文；字段值、数组规模和关键词长度均受限。查询成功、失败、回收站切换及空就绪状态都会修订查询上下文，过期能力结果不能作为当前页面结果继续使用。
- 标准页面通过正式会话入口开放“开始新增”和“开始编辑”。新增先只读解析默认值；编辑只接受正常列表当前页或当前正常详情中的记录，并重新校验该记录的更新动作可用性。只有准备完成且页面上下文仍有效时，才同步提交编辑会话。回收站不开放新增和编辑，助手也不会获得保存能力，用户必须在页面中审阅草稿并自行保存。
- 表单描述向模型提供经过逐字段和整批预算裁剪的当前标量值，并显式标记值投影是否截断，使模型能够在不读取 DOM 的前提下判断哪些字段仍需修改；批量补丁限制字段数量、拒绝重复字段，先验证整批输入再产生页面效果。模型供应商返回结构完整、结束原因明确为 `stop` 的空回合时，适配层保留原始结束事实；助手会话只在上一轮至少有一项成功能力结果时正常收尾，损坏响应、截断结束、首轮空回合和全失败结果仍明确提示失败。
- 单值引用字段只通过标准选择器的候选提供者向助手开放。助手可按业务名称执行“检索—唯一精确匹配—草稿回填”的原子能力；只有忽略大小写和首尾空白后名称一致、结果总数为一且候选可用时才会修改草稿。不能唯一确定时回到候选查询，查询结果隐藏内部 ID，只返回绑定当前页面上下文和本次检索的一次性选择键。正式回填在同一次草稿变更中应用候选 ID 与服务端授权的联动字段，并继续复用引用依赖清理和公式计算链。多值、树形和其他带作用域的引用选择仍保持关闭，待各自正式选择语义形成后再接入。
- 引用目标模块必须声明实际需要的查询字段和页面快速搜索字段，标准选择器、助手和普通列表共用该查询契约。租户模块已显式开放名称检索并继续排除工作台品牌等无关字段，避免为助手建立旁路查询。
- 元数据治理页已经接入独立的页面 Surface。助手可以读取当前模块、关系、受控字段摘要和本地草稿状态；字段摘要有数量上限，页面上下文只携带不含草稿正文的修订号。
- 当前关系没有打开字段编辑器或排序操作时，页面向助手开放普通业务字段的新增和修改，以及模块引用和字典字段的新增候选能力。可修改目录只包含当前关系中允许业务编辑且没有特殊属性绑定的字段；字段规格取自页面已加载的完整启用目录，模型上下文中的规格摘要可以裁剪，但能力参数枚举不能丢失合法规格。显式字段名与自动命名均遵守平台字段命名契约，动态记录协议保留名由前端提前拒绝并由 change-set 预检权威校验。
- 引用与字典候选先通过关系作用域的正式目标目录检索，再对返回的模块 alias 或字典应用/类别身份做精确复核；引用的目标元数据、键字段和展示字段由服务端目录解析，模型不能猜内部 ID。确定结果随后进入现有元数据 edit session，并通过受调用令牌保护的页面效果边界打开真实字段编辑器。候选对用户可见、可继续修改或取消；编辑器打开期间阻止切换元数据关系，避免不可见候选残留在 module-wide change-set 中。已有业务数据时，字段规格变更继续受页面现有的数据安全目录约束。
- 当前未保存候选存在真实变更时，页面才声明元数据预检能力。预检复用手工保存使用的 module-wide change-set preview 入口，并随请求传递取消信号；返回结构化字段、物理结构、排序影响和校验问题，但不向模型暴露发布入口或可复用的指纹令牌。字段 UPDATE 会明确列出类型、非空和索引变化；已有数据且无法证明满足新增必填或唯一约束时，公共预检直接拒绝，避免确认摘要与实际 DDL 漂移。用户并发修改候选后，旧预检结果通过页面调用令牌失效。
- 助手预检只针对它已提交到 edit session 且仍与可见编辑器一致的候选；用户在编辑器中继续修改后，旧候选的预检能力立即失效，正式保存会以当前可见表单重新形成 change-set。元数据治理的预检与手工保存共用同一个前端客户端边界，避免助手复制 endpoint、proposal 或指纹协议。字段影响摘要会明确引用目标或字典身份。当前已经形成“描述当前模型—确定性检索引用/字典目标—新增或修改字段候选—用户审阅修改—标准预检—页面确认生效”的完整边界。引用候选的真实页面验收已确认正式目标目录、权威影响摘要和取消不生效契约；动作、业务规则和页面配置留待各自专项治理。
- 已在真实浏览器验证当前页说明、菜单导航、进入标准新增表单，以及在同一未保存草稿中按语义填写配置名称、模型 ID 和租户引用；引用字段既可由用户输入确定名称后失焦自动补全，也可由助手通过同一标准候选源确定性回填，均不会自动保存。导航后能够等待新页面 Surface 并继续回合。以“我要新增一名职员，帮我做”表达宏观目标时，模型能够自主进入未保存新增表单；当前本地 LM Studio 模型在读取表单后的说明或澄清回合仍可能达到输出长度上限，因此连续澄清协议由契约测试锁定，真实模型质量作为独立风险保留。查询数据、进入编辑表单的弱模型稳定触发及配置候选发布仍待后续增量完成。

标准列表查询的控制端口、结果裁剪和快速搜索执行已经由组件与 Surface 契约测试覆盖。真实浏览器已确认页面查询能力能够进入模型能力目录；当前本地 LM Studio 模型仍可能选择只读能力或返回空结构化回合，因此“自然语言稳定触发查询”的端到端验收尚未完成。该风险属于模型工具调用质量与兼容性，不通过前端意图猜测或旁路查询补偿；后续以更稳定的结构化调用模型复验，同时保留弱模型作为降级与错误反馈测试对象。

新增和编辑入口采用“异步准备、同步提交”两段式边界：准备期间不改变页面；提交时复用调用令牌检查，防止用户并发操作被旧助手结果覆盖。真实浏览器已确认 LM Studio 能调用新增入口并打开未保存表单；进入编辑入口仍会出现空结构化回合，归入同一模型稳定性风险。

语义填报采用一个有序、原子的字段变更批次，而不是由模型逐字段制造多个独立页面回合。标量字段、枚举和日期时间继续复用标准编解码和表单联动；JSON 结构值、文件及尚未接入正式选择语义的字段不向助手开放写入。用户意图、日期表达和选项语义由模型结合对话理解；前端只验证能力结构、字段可写性、标准值类型、引用候选及调用上下文，不用字段名与原话子串匹配或自然语言词表证明修改意图。歧义通过澄清解决，所有修改保持为可审阅的未保存草稿；单值引用优先通过“业务名称确定性解析—标准草稿回填”完成，无法唯一精确匹配时再走“标准候选查询—不透明选择键—标准草稿回填”，模型始终不能直接提交内部 ID。真实浏览器已确认普通字段和租户引用均可由自然语言请求填入且不会自动保存。LM Studio 在能力执行后的总结回合仍可能返回空内容；页面会保留已完成的标准草稿变更并明确反馈模型响应问题，不由前端猜测用户意图来补偿。

当前已经完成第三阶段的交互骨架、导航、标准查询与表单草稿能力，以及本专项范围内的元数据字段编排能力，但不代表第三阶段已经完成。剩余工作集中在真实浏览器组合场景的稳定验收、弱模型工具调用质量验证和配置生效边界收口；后续能力继续沿同一 Surface、调用令牌和正式业务入口扩充，不在面板中增加页面类型分支。

结构化建议选择、必答选择和确认呈现已经接入统一回合协议。选择由助手层的保留交互能力产生，不伪装成页面 Capability；普通建议保留自由输入，必答选择在解决前阻止并行输入，回答以交互标识、选项标识和可读标签进入下一回合。确认使用平台固定的“确认 / 取消”选项，模型只提供具体提议，避免把内部选项标识和标准交互语义交给模型生成。运行状态从运行时事实推导为理解、执行页面操作、组织回复和取消，不写入对话历史。真实浏览器已经验证可选建议的点选续接、确认卡片的输入阻断与取消回合；该能力继续复用当前连续回合和前端会话，不以接入外部 Agent 协议、建设服务端 Conversation 或开放任意生成式 UI 为前提。

### 后续演进

真实场景验证后，再按需要建设：

- 普通业务动作的确认与执行。
- 在代码级组合出现稳定复用后进一步完善 Skill 贡献。
- 服务端业务能力工具。
- 跨面板或跨登录会话恢复，以及经过治理的服务端历史记录。
- 长任务的后台执行、进度和取消。
- 更细的成本、配额和模型使用治理。

## 当前不做

首期明确不建设：

- 接收任意 Prompt 和模型参数的通用代理。
- 任意后端 API、URL、Controller 或 Service 注册。
- DOM 自动化和组件内部状态访问。
- 可视化 Skill 市场或 Prompt 编排器。
- 长期用户画像和跨会话自动记忆。
- 自主多 Agent 协作。
- 在用户不可见的情况下自动保存、删除、授权或发布。
- 绕过配置草稿、校验、预览和发布链的元数据修改。
- 由助手编排动作、业务规则、页面或表单布局；这些能力另立治理专项。

## 验证要求

按阶段验证对应边界：第一阶段完成设计核对，第二阶段验证公共机制契约，第三阶段完成业务与浏览器验收。整体验证覆盖：

1. 当前 Surface 只暴露允许的上下文和能力。
2. 导航后旧 Surface 能力失效，新页面能力重新绑定。
3. 菜单查找只使用当前用户可见菜单。
4. 查询只接受页面声明的字段和操作符。
5. 表单补丁拒绝未知、只读和受保护字段，并保留现有联动与校验。
6. 引用值通过正式候选解析，不接受模型臆造 ID。
7. 能力调用参数必须通过结构校验。
8. 后端业务请求继续执行租户、权限和数据范围校验。
9. 元数据生效必须经过校验、预览、版本检查和明确确认。
10. 模型超时、非法调用、页面切换和用户取消能够安全收口。
11. 宏观目标缺少必要信息时能够澄清，并在用户回答后携带原目标继续执行；状态提示不会污染模型对话。

前端优先使用纯状态、组件和必要的浏览器测试验证能力目录、Surface 切换和真实交互；后端使用契约测试验证会话边界、模型调用和权限不被助手入口削弱。动态配置进入真实数据访问和发布链时，应补对应集成测试。

## 收口判断

前两个阶段按上述架构与机制完成判定收口；最终交付时应同时回答：

- 用户是否通过自然语言完成了目标，而不只是得到操作建议。
- 助手是否复用了用户手工操作的正式前端机制。
- 静态和动态页面是否消费同一套助手契约。
- 新增业务能力是否只需贡献上下文和能力，而无需修改助手主循环。
- 模型、Prompt 或 Skill 是否没有成为新的权限来源。
- 当前实现是否已完成动态元数据候选、预检和确认生效闭环，并能在未来独立接入动作、规则和页面配置能力。

三个目标场景共同通过验收，且持续扩充能力无需改变已收口的分层与接入主流程，才视为专项完成。

## 助手接入与运行治理契约

页面字段通过来源无关的 `assistantPolicy` 声明自动投影边界。静态 Web DSL 使用
`field.assistantPolicy(AssistantFieldPolicy...)`，动态已发布页面使用字段 `props.assistantPolicy`，
两者编译为同一个 resolved 字段描述：

| 策略 | 字段描述 | 当前值 | 修改草稿 |
| --- | --- | --- | --- |
| `HIDDEN` | 不提供 | 不提供 | 不允许 |
| `DESCRIBE` | 提供名称、类型与约束 | 不提供，含选项值 | 不允许 |
| `READ` | 提供 | 提供受限投影 | 不允许 |
| `READ_WRITE` | 提供 | 提供受限投影 | 仍受页面可写性约束 |

普通字段默认 `READ_WRITE` 以兼容既有页面；密码输入强制 `HIDDEN`，模型声明的存储或输出保护字段上限为
`DESCRIBE`。前端的表单、列表、树与引用候选入口消费该策略，引用路径值保守关闭；自定义 Surface 应同样裁剪输出。
策略约束平台自动组织的上下文，不是后端授权或内容防泄漏网关；用户主动输入的文本不由字段策略重新解释。

会话边界由认证身份与页面执行租户组成，不进入模型上下文。切换身份或执行租户时清空历史、输入和待选择卡片，
取消旧任务并丢弃迟到结果；助手主动切换租户同样结束旧任务。同一作用域的跨页导航保留任务，目标业务页面未就绪时
等待正式 Surface，不通过临时 Workbench 请求入口发送原任务数据。页面重建与身份切换分别由调用令牌和会话代次约束。

能力组合在注册、目录投影和执行时检查重复与保留编码，拒绝静默覆盖。领域参数仍由能力自己的 `parseInput` 验证，
执行继续调用正式页面入口；`applyEffect` 是页面效果提交边界，不以模型声明或提示词代替。

具备标准查询描述符的列表开放 `query.apply-standard`：使用声明字段、操作符与枚举值组成 AND 筛选，
并使用声明可排序字段排序；所有输入验证通过后才替换高级条件和排序，保留快速搜索及常驻条件。
当前不开放猜测引用 ID、JSON 条件或任意表达式。没有标准查询端口的列表不声明该能力。

`form.patch-draft` 返回由实际草稿前后状态形成的摘要，区分直接修改和联动变化，并列出仍需填写的必填项。
摘要只包含允许读取的有限字段值，始终标识尚未保存；面板直接显示该结果，不依赖后续模型总结成功。

模型调用通过统一网关限制每用户和实例总并发，普通及结构化、流式及非流式调用共用额度；取消和失败均释放额度。
具体配置见[模型连接配置](topics/configuration/AI_MODEL_INTEGRATION.md)。该限制是单实例并发保护，不承诺分布式配额或按时间窗口计费。
