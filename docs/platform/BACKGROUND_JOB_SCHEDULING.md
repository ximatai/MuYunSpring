# 后台作业与定时调度设计

本文固化平台标准后台作业机制的目标设计：按计划或手动触发的定时作业、一次性入队的排队作业，以及低代码侧配置的定时调用模块动作，共用同一套计划、运行记录、执行与治理能力。当前尚未实现，实现按本文收口；建设边界与专题事实的分工见 [后台任务与异步批次边界](BACKGROUND_JOB_AND_BATCH_BOUNDARY.md)。

## 定位

平台负责“什么时候执行、由哪个节点执行、以什么身份执行、执行得怎样”：计划、触发、集群互斥、租约、重试、进度、运行记录、失败提醒和运维入口。业务专题只负责“执行什么”：处理器读取并写入专题自己的业务事实，不在作业记录中保存业务内容。

作业机制不是业务流程编排，不替代工作流；不是外部写入的幂等与回执流水，也不替代运行审计。

## 核心取舍

| 议题         | 决定                                                                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 能力范围     | 定时作业、排队作业与动态配置作业三块全部纳入，共用计划与运行模型。                                                                             |
| 推进顺序     | 先建核心并迁移现有调度，再以通讯录同步作为首个业务接入，最后建设动态配置作业。                                                                 |
| 计划归属     | 专题创建的计划由专题页面维护业务配置，并标记为专题托管；作业管理页只做运维（查看运行、立即执行、紧急暂停），不修改专题托管计划的业务配置。   |
| 执行身份     | 模型支持系统身份、发起人身份与专用服务账号三种模式；动态配置作业首批实现前两种，专用服务账号预留。                                             |
| 租户可见性   | 租户管理员可查看并运维本租户的计划与运行，平台级作业对其不可见。                                                                               |
| 失败处理     | 作业类型声明重试策略：定时作业默认不重试、等待下一周期，排队作业默认重试 3 次；最终失败或连续失败达到阈值时，以业务提醒通知所在范围的管理员。 |
| 运行记录留存 | 默认保留 90 天，每个计划至少保留最近 20 条；作业类型可声明不同保留期；清理本身作为平台定时作业运行。                                           |
| 执行语义     | 至少一次。处理器必须幂等；受租约保护的写入只有在租约仍有效时才能提交。                                                                         |
| 调度实现     | 平台自建，基于数据库租约与现有 PostgreSQL 能力；不引入 Quartz 等外部调度框架，不建设独立 worker 集群。                                         |

### 命名

平台中“任务”已被工作流待办（`WorkflowTask`）、页面模块任务（`PlatformModuleTaskDefinition`）和启动任务（`PlatformBootstrapTask`）占用。本机制在代码中统一使用 `Job`，中文统称“后台作业”：作业类型、作业计划、作业运行。管理页可以使用“定时任务”作为面向用户的菜单称呼，但模型、接口与文档术语保持“作业”。

## 模块与扩展点

```text
muyun-platform（job 包）
  作业类型注册、作业计划、作业运行、调度扫描、执行通道与租约
  执行身份、受租约保护的事务、失败提醒、运行记录留存
  非 HTTP 的模块动作调用门面与内置作业类型“调用模块动作”（动态阶段）
muyun-platform-web
  作业计划与作业运行的标准管理模块
muyun-iam
  执行身份解析、失败提醒的管理员收件人解析
业务专题（例如 muyun-iam 的 federation 包）
  实现作业处理器，并通过平台门面维护本专题托管的计划
```

模块放置符合现有生产依赖白名单：`muyun-iam` 与 `muyun-platform-web` 均依赖 `muyun-platform`。`muyun-platform` 不知道谁是管理员，也不解析账号；执行身份解析与“租户管理员、平台管理员”收件人由 IAM 实现平台定义的扩展点。

作业处理器以 Spring Bean 注册，声明：

| 声明         | 说明                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| 类型编码     | 全局唯一、稳定，写入计划与运行记录，例如 `iam.directory-sync`。                                        |
| 名称         | 多语言资源键，用于管理页展示。                                                                         |
| 作用范围     | 平台级或租户级。租户级作业的计划与运行都带 `tenantId`。                                                |
| 默认计划     | 平台级作业可声明默认计划，启动时幂等登记；租户级计划由专题或管理员创建。                               |
| 执行通道     | 作业在哪个通道执行，例如默认通道、内容生成通道、通讯录同步通道。                                       |
| 时限与重试   | 租约时长、最长运行时长、最大尝试次数与退避策略。                                                       |
| 互斥键规则   | 由计划或入队参数得出互斥键，同一互斥键同一时刻最多一个运行在执行。                                     |
| 失败提醒     | 是否提醒、连续失败阈值；高频排队作业（如翻译生成）可以关闭单次失败提醒。                               |
| 人工重试     | 是否允许管理员对失败运行发起重试或立即执行。                                                           |
| 留存期       | 运行记录保留天数，未声明时使用平台默认值。                                                             |

处理器收到只读的运行上下文：运行标识、触发方式、参数、租户与执行身份，以及上报进度、检查取消请求和进入受租约保护事务的方法。处理器不直接改写运行状态，结果以返回值或异常交给平台判定；返回值可以携带处理器定义的稳定结果码与统计摘要。

## 领域模型

| 模型     | 职责                                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作业计划 | 一个作业类型的一条执行计划：作用范围与租户、业务对象键、计划表达式与时区、启停状态、托管方、执行身份、参数、下次触发时间与连续失败计数。                     |
| 作业运行 | 一次执行：作业类型、所属计划（排队作业为空）、计划触发时刻、触发方式、触发人、执行身份、互斥键与去重键、状态、尝试次数、租约、进度、结果码、统计、错误摘要与追踪编号。 |

作业运行同时是执行队列与运行历史：到点的计划、手动触发和排队作业入队，都生成一条待执行的运行记录，由各节点的执行通道认领执行。定时作业、排队作业与动态配置作业只有一条执行链路。

专题需要的业务状态与查询（例如翻译生成的槽位、序号与“已过期”“不可用”等专题结果）仍保存在专题表中，以运行标识关联作业运行；作业运行只承担领取、租约、尝试、可用时间与执行留痕，不承载专题状态机。

### 计划

1. 计划表达式支持 cron 与固定间隔两种形式；cron 精度到分钟，按计划声明的时区计算，未声明时使用平台默认时区。夏令时跳过的时刻不触发、重复的时刻只触发一次。
2. 同一作业类型、租户与业务对象键唯一；平台级计划的 `tenantId` 为空，唯一约束按“空值相同”处理。专题以业务对象键区分计划，例如“租户 + 身份源”。
3. 首次登记或修改计划表达式时，从当前时间重新计算下次触发时间，不追补修改前的触发。
4. 托管方为专题时，计划的业务配置只能经专题门面修改；作业管理页上相应字段只读。
5. 暂停的计划不再生成新运行；已生成但未认领的运行保留执行，已在执行的运行继续完成，均可单独请求取消。
6. 部署配置提供全局调度总开关，只停止按计划的自动触发；手动执行与排队作业不受影响。
7. 计划引用的作业类型在当前版本中已不存在时，计划标记为不可用：不生成运行、不重复提醒，在管理页提示清理。

### 运行状态

```text
待执行 → 执行中 → 成功 | 部分成功 | 失败 | 已取消
           ↓
         待重试 → 执行中
```

1. 认领在短事务内完成：对互斥键加事务级锁后，校验状态、互斥键上没有其他有效执行中的运行，再写入租约令牌与到期时间。租约过期后的接管复用原运行记录，并计为一次尝试；定时作业最大尝试次数为 1 时，节点宕机即判定失败，等待下一周期。
2. 互斥只在认领时生效：同一互斥键已有运行在执行时，后来的运行保持待执行，等待前一运行结束后再被认领。定时作业的同一计划上一轮未结束时，本轮触发不再生成新运行，记一次跳过。
3. 平台在执行期间自动续租，以便识别节点宕机；超过作业类型声明的最长运行时长仍未结束的运行，平台停止续租并判定超时，避免挂死的处理器永久占用互斥键。
4. 租约到期、认领与续租以数据库时间判断，不依赖各节点时钟一致。
5. 计划的同一触发时刻只生成一条运行；停机期间错过的多次触发合并为一次补跑，不逐次追补。
6. 排队作业可声明去重键，同一去重键存在未结束的运行时返回该运行，不重复入队。去重键必须包含输入版本（例如业务记录的修订号），数据变化后的新请求因此会形成新运行，不会被旧运行吞掉。
7. 入队加入调用方事务：调用方回滚则入队一并撤回，提交后由执行通道领取。
8. 取消为协作式：平台记录取消请求，处理器在安全点检查后停止；待执行的运行直接取消。
9. 节点优雅停机时停止认领，正在执行的运行在宽限期内未完成则释放租约，不计入尝试次数。

### 受租约保护的写入

平台不能撤销处理器已经提交的事务，因此“过期运行不能覆盖新结果”只对经平台入口提交的写入成立：

1. 平台提供受租约保护的事务入口：在同一事务内锁定运行记录、校验租约令牌与到期时间，再执行处理器的业务写入；租约已失效时整个事务回滚。
2. 处理器的业务写入必须经该入口提交，并按页、按批拆成短事务；通讯录同步的每一页写入、翻译生成的结果发布都属于此类。
3. 处理器在该入口之外的写入（例如调用外部系统）不受保护，必须自身幂等。
4. 执行语义为至少一次：重试、接管与补跑都可能重复执行同一输入，处理器负责幂等。

## 执行

1. 每个节点运行调度扫描，按计划的下次触发时间生成运行；生成与推进下次触发时间在同一事务内，多节点并发扫描不会重复生成。计划触发以分钟为粒度。
2. 执行通道是节点内的独立线程池，按通道配置工作线程数与领取间隔；慢作业（如模型调用、通讯录拉取）不占用平台维护作业的线程。排队作业的领取延迟以秒计，本节点入队提交后立即唤醒对应通道。
3. 节点只认领本节点已注册的作业类型与通道，滚动发布期间新旧版本节点可以共存。
4. 扫描间隔、通道线程数与领取间隔、租约时长与留存天数通过 `muyun.platform.job.*` 部署配置调整，非法配置启动即失败。
5. 节点本地的周期工作（例如只扫描本机实时连接的在线闲置检测）不纳入本机制，继续使用 Spring 定时注解；需要集群内只执行一次或需要运行记录的工作必须使用本机制。

## 执行身份

作业在请求线程之外执行，不继承任何请求的用户、租户或委托上下文。执行身份引用保存在计划上，并在生成运行时复制到运行记录；没有计划的排队作业在入队时确定执行身份。这部分收口 [技术债 TD-008](../TECHNICAL_DEBT.md) 中后台任务系统态授权与审计的部分。

| 模式         | 说明                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 系统身份     | 平台级作业进入现有系统上下文，以“后台作业 + 类型编码”作为必填的系统原因。租户级作业进入新增的“租户内系统执行主体”：同时携带租户、系统原因和以作业类型标识的合成操作者，审计操作者类型为“后台作业”。静态作业处理器默认使用该模式。 |
| 发起人身份   | 保存发起人的身份引用，不保存任何凭据；每次执行通过可信执行身份解析器（`TrustedExecutionIdentityResolver`）重新解析账号、租户与委托，账号停用、删除、需改密或授权失效时本次运行失败。计划的发起人是最后修改人，排队作业的发起人是入队人。 |
| 专用服务账号 | 预留。以租户内专用于后台执行的账号身份运行，权限按普通角色授权；需要先定义服务账号类型及其不可交互登录的约束。                                                                                                            |

1. 租户内系统执行主体是现有 `TenantContext` 的补充：现有系统上下文不带租户，租户上下文又不带系统原因，二者都不能表达“限定在某租户内、无用户的系统执行”。该主体在租户过滤上等同租户上下文，在审计上记录系统原因；动作授权链路如何判定见“动态配置作业”。
2. 发起人身份只允许租户账号且其租户必须等于计划或运行的租户。平台账号会被解析为系统用户并在动作授权中直接放行，因此平台账号发起的计划一律按系统身份处理，受系统身份的全部约束。
3. 管理员对失败运行的重试与立即执行不改变执行身份；作业类型声明是否允许他人人工重试，例如翻译生成保留原触发者，不允许为取得更多额度而轮换身份。
4. 运行记录与运行审计都记录执行身份模式、作业类型、计划与运行标识；手动触发另记录触发人。触发人只表示“谁让它现在执行”，不改变执行身份。运行审计通过追踪编号定位到作业运行，作业运行不复制授权判定细节。

## 动态配置作业

动态配置作业是平台内置的作业类型“调用模块动作”，与静态作业共用计划、运行与执行链路。

当前静态模块动作的授权只在 Web 层拦截器中执行，只有动态记录动作在运行态内部授权；作业运行在 `muyun-platform` 中，不能经过 Web 层。因此动态阶段先在 `muyun-platform` 建设非 HTTP 的模块动作调用门面：复用与 Web 入口一致的动作授权、数据范围、租户、校验、生命周期和运行审计，静态与动态模块的动作都经该门面执行，动静一体在此门面上成立。

1. 计划参数为目标模块、动作编码与静态动作参数。首批只支持无需选中记录、无需界面交互的模块级动作；静态动作需显式声明可被定时调用，动态动作在元数据上声明。记录级动作与依赖表单输入的动作不在首批范围。
2. 保存计划时校验目标动作存在、可被定时调用，并对发起人身份校验其当前有权执行该动作；每次执行时按当前元数据与权限重新校验，参数有大小上限，不得携带凭据。
3. 以系统身份执行的计划必须同时满足：
   - 只有平台管理员可以创建或修改；
   - 目标动作在平台管理员维护的系统身份定时调用白名单中；
   - 租户级计划以租户内系统执行主体执行，限定在本租户内。

   动作授权遇到作业系统主体时，只放行白名单中的动作，并记录独立的授权判定；系统身份不受普通数据范围约束，白名单是必需的风险闸门。
4. 以发起人身份执行的计划，由有权执行该动作的本租户用户创建；其他管理员修改计划会把执行身份替换为修改人，并在界面上明确提示。
5. 目标模块或动作被删除、停用或改为不可定时调用时，计划在下次执行时失败并提醒，不自动删除计划。

## 失败处理与提醒

1. 处理器抛出的异常按作业类型声明区分为可重试与不可重试；可重试失败按退避进入待重试，超过最大尝试次数后判定失败。
2. 定时作业默认不重试，失败后等待下一周期；排队作业默认最多尝试 3 次。
3. “已有执行者在运行”“达到本轮批次上限”这类处理器正常结果，按处理器返回的结果码记为成功或部分成功，不计入失败。
4. 运行最终失败，或计划连续失败达到阈值（默认 3 次）时，通过[实时业务提醒](BUSINESS_NOTIFICATION_BACKEND_INTEGRATION.md)通知所在范围的管理员：平台级作业通知平台管理员，租户级作业通知该租户管理员，发起人身份的作业同时通知发起人。作业类型可以关闭或聚合提醒。提醒只携带作业与运行标识，点击后进入运行详情，并按点击者权限重新校验。
5. 业务提醒只投递在线用户，因此计划列表持久展示最近运行状态与连续失败计数，离线管理员登录后仍能发现失败。
6. 错误摘要只保存错误类型、稳定错误码与必要诊断，不保存外部报文、凭据、业务全文或堆栈；运行详情不展示请求参数原文。

## 管理入口

作业计划与作业运行以平台标准静态模块交付，位于系统管理菜单下，按普通动作授权控制。

| 角色       | 可见范围                     | 可执行操作                                                                           |
| ---------- | ---------------------------- | ------------------------------------------------------------------------------------ |
| 平台管理员 | 全部平台级与租户级计划和运行 | 立即执行、暂停与恢复、取消运行、重试失败运行；修改非专题托管计划；维护系统身份白名单 |
| 租户管理员 | 本租户计划和运行             | 立即执行、暂停与恢复、取消运行、重试失败运行；修改本租户非专题托管的计划             |

运行详情展示触发方式、触发人、执行身份、状态、进度、结果码、统计、错误摘要与追踪编号；专题可提供跳转到本专题结果页的链接。

## 运行记录留存

1. 已结束的运行默认保留 90 天，每个计划至少保留最近 20 条；无计划的排队作业只按天数清理。作业类型可声明不同保留期，平台默认值通过部署配置调整。
2. 清理分批执行、有上限，作为平台级定时作业运行，自身的运行记录同样受留存约束。
3. 专题以运行标识关联的业务事实（如同步统计、翻译版本）按专题自身的留存策略处理，不随作业运行一并删除；专题要求随业务记录删除同步清理的运行，由专题在其删除事务内调用平台入口清理。

## 现有调度的迁移

| 现有调度         | 处理                                                                                                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 日志留存清理     | 迁为平台级定时作业，随日志留存服务条件装配，原调度开关语义保留。人工立即清理不经作业，因此存储层按日志类型的数据库锁继续保留；作业互斥只防止重复调度。 |
| 交换文件清理     | 迁为平台级定时作业。                                                                                                                                                                         |
| 工作流超期扫描   | 迁为平台级定时作业，获得集群内单次执行与运行记录；以测试确认进入系统上下文后的查询范围不变。                                                                                                 |
| 业务内容翻译生成 | 迁为排队作业，独立执行通道；专题生成表保留槽位、序号、请求与专题结果，以运行标识关联，领取、租约、尝试与可用时间由作业运行承担；保留 30 天留存、原触发者身份、不允许轮换身份与业务删除时同事务清理。 |
| 翻译生成记录清理 | 随翻译生成迁移，过期运行由作业运行留存按翻译作业类型声明的保留期处理。                                                                                                                       |
| 在线闲置检测     | 不迁移，属于节点本地周期工作。                                                                                                                                                               |

迁移不改变各专题对外行为：执行频率默认值、批次上限、跨实例互斥、留存期与失败后可恢复性保持不变，并以既有测试和新增 contract 测试锁住。翻译生成迁移风险最高，排在核心阶段最后，先以 contract 测试锁住现有行为再迁移。

## 实施阶段

| 阶段 | 内容                                                                                                                                       |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 核心 | 作业类型注册、计划、运行、调度扫描、执行通道、租约与重试、受租约保护的事务、执行身份与租户内系统执行主体、失败提醒、留存、管理模块；迁移现有调度。 |
| 接入 | 外部身份联邦的通讯录同步作为首个租户级、专题托管的业务作业接入，用真实业务检验抽象。                                                       |
| 动态 | 非 HTTP 的模块动作调用门面，内置“调用模块动作”作业类型，发起人身份与系统身份执行，系统身份白名单，低代码侧计划配置入口。                   |

## 不建设的能力

1. 外部调度框架、独立 worker 集群或跨应用的调度中心。
2. 作业之间的依赖编排、DAG 与分片执行；需要多步编排的业务归工作流或专题自身。
3. 秒级精度的计划调度与严格准点保证；计划以分钟为粒度，允许扫描间隔内的延迟。
4. 恰好一次的执行保证；平台保证至少一次与受租约保护的写入。
5. 在作业记录中保存业务全文、外部报文或凭据。
6. 任意脚本或表达式作为作业内容；动态配置作业只能调用已声明可定时调用的模块动作。

## 验收

以 contract 与 IT 覆盖以下边界：

1. 多节点并发扫描与认领时，同一计划触发时刻只生成并执行一次，同一互斥键不并发。
2. 节点在执行中宕机，租约到期后由其他节点接手并计入尝试；过期运行经受租约保护的事务提交时被拒绝。
3. 超过最长运行时长的运行判定超时并释放互斥键；优雅停机释放租约且不计尝试。
4. 停机期间错过的多次触发只补跑一次；暂停的计划不生成运行；上一轮未结束时本轮跳过。
5. 排队作业随调用方事务入队与撤回，按含输入版本的去重键幂等入队，可重试失败按退避重试，超过次数后失败并按类型声明提醒。
6. 作业执行不继承请求上下文；租户级作业不能读写其他租户数据；系统身份执行记录系统原因与作业操作者。
7. 发起人身份在账号停用、授权收回后执行失败；平台账号不能以发起人身份绕过白名单；人工重试不改变执行身份。
8. 系统身份计划只能由平台管理员维护，且目标动作必须在白名单中。
9. 租户管理员看不到平台级作业与其他租户的计划和运行。
10. 迁移后的日志留存、交换文件清理、工作流超期扫描与翻译生成保持原有行为。
11. 运行记录按类型保留期与保底条数清理，不删除专题业务事实。
