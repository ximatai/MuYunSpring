# 后台作业与定时调度设计

核心机制、交换文件清理、日志留存清理、工作流超期扫描、业务内容翻译迁移及动态配置作业已实现；通讯录同步尚未实现。

本文固化平台标准后台作业机制的目标设计：按计划或手动触发的定时作业、一次性入队的排队作业，以及低代码侧配置的定时调用模块动作，共用同一套计划、运行记录、执行与治理能力。当前实现核心机制、既有调度迁移及模块动作定时调用，后续专题接入仍按本文收口；建设边界与专题事实的分工见 [后台任务与异步批次边界](BACKGROUND_JOB_AND_BATCH_BOUNDARY.md)。

## 定位

平台负责“什么时候执行、由哪个节点执行、以什么身份执行、执行得怎样”：计划、触发、集群互斥、租约、重试、进度、运行记录、失败提醒和运维入口。业务专题只负责“执行什么”：处理器读取并写入专题自己的业务事实，不在作业记录中保存业务内容。

作业机制不是业务流程编排，不替代工作流；不是外部写入的幂等与回执流水，也不替代运行审计。

## 核心取舍

| 议题         | 决定                                                                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 能力范围     | 定时作业、排队作业与动态配置作业三块全部纳入，共用计划与运行模型。                                                                             |
| 推进顺序     | 先建核心并迁移现有调度，再以通讯录同步作为首个业务接入，最后建设动态配置作业。                                                                 |
| 计划归属     | 专题创建的计划由专题页面维护业务配置，并标记为专题托管；作业管理页只做运维（查看运行、立即执行、紧急暂停），不修改专题托管计划的业务配置。   |
| 执行身份     | 模型支持系统身份、发起人身份与专用服务账号三种模式；动态配置作业首批实现前两种，专用服务账号预留。                                             |
| 租户可见性   | 租户管理员可查看并运维本租户的计划与运行，平台级作业对其不可见。                                                                               |
| 失败处理     | 作业类型声明重试策略：定时作业默认不重试、等待下一周期，排队作业默认重试 3 次；最终失败或连续失败达到阈值时，以业务提醒通知所在范围的管理员。 |
| 运行记录留存 | 默认保留 90 天，每个计划至少保留最近 20 条；作业类型可声明不同保留期；清理本身作为平台定时作业运行。                                           |
| 执行语义     | 至少一次。处理器必须幂等；受租约保护的写入只有在租约仍有效时才能提交。                                                                         |
| 调度实现     | 平台自建，基于数据库租约与现有 PostgreSQL 能力；不引入 Quartz 等外部调度框架，不建设独立 worker 集群。                                         |

### 命名

平台中“任务”已被工作流待办（`WorkflowTask`）、页面模块任务（`PlatformModuleTaskDefinition`）和启动任务（`PlatformBootstrapTask`）占用。本机制在代码中统一使用 `Job`，中文统称“后台作业”：作业类型、作业计划、作业运行。管理页可以使用“定时任务”作为面向用户的菜单称呼，但模型、接口与文档术语保持“作业”。

## 模块与扩展点

```text
muyun-platform（job 包）
  作业类型注册、作业计划、作业运行、调度扫描、执行通道与租约
  执行身份、受租约保护的事务、失败提醒、运行记录留存
  非 HTTP 的模块动作调用门面与内置作业类型“调用模块动作”（动态阶段）
muyun-platform-web
  作业计划与作业运行的标准管理模块
muyun-iam
  执行身份解析、失败提醒的管理员收件人解析
业务专题（例如 muyun-iam 的 federation 包）
  实现作业处理器，并通过平台门面维护本专题托管的计划
```

模块放置符合现有生产依赖白名单：`muyun-iam` 与 `muyun-platform-web` 均依赖 `muyun-platform`。`muyun-platform` 不知道谁是管理员，也不解析账号；执行身份解析与“租户管理员、平台管理员”收件人由 IAM 实现平台定义的扩展点。

作业处理器以 Spring Bean 注册，声明：

| 声明         | 说明                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| 类型编码     | 全局唯一、稳定，写入计划与运行记录，例如 `iam.directory-sync`。                                        |
| 名称         | 多语言资源键，用于管理页展示。                                                                         |
| 作用范围     | 平台级或租户级。租户级作业的计划与运行都带 `tenantId`。                                                |
| 默认计划     | 平台级作业可声明默认计划，启动时幂等登记；租户级计划由专题或管理员创建。                               |
| 执行通道     | 作业在哪个通道执行，例如默认通道、内容生成通道、通讯录同步通道。                                       |
| 时限与重试   | 租约时长、最长运行时长、最大尝试次数与退避策略。                                                       |
| 互斥键规则   | 由计划或入队参数得出专题键；平台以“作业类型 + 作用范围与租户 + 专题键”构成有效互斥键，同一有效键同一时刻最多一个有效租约。跨类型或跨租户的互斥须显式声明。 |
| 失败提醒     | 是否提醒、连续失败阈值；高频排队作业（如翻译生成）可以关闭单次失败提醒。                               |
| 人工重试     | 是否允许管理员对失败运行发起重试或立即执行。                                                           |
| 留存期       | 运行记录保留天数，未声明时使用平台默认值。                                                             |

处理器收到只读的运行上下文：运行标识、触发方式、参数、租户与执行身份，以及上报进度、检查取消请求和进入受租约保护事务的方法。处理器不直接改写运行状态，结果以返回值或异常交给平台判定；返回值可以携带处理器定义的稳定结果码与统计摘要。

## 领域模型

| 模型     | 职责                                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作业计划 | 一个作业类型的一条执行计划：作用范围与租户、业务对象键、计划表达式与时区、启停状态、托管方、执行身份、参数、配置修订、下次触发时间与连续失败计数。配置修订只随计划表达式、参数与启停变化递增，调度扫描写入的运行时状态不推进它；管理员修改必须携带配置修订，缺失或过期均拒绝，专题托管计划由专题门面直接覆盖。                     |
| 作业运行 | 一次执行：作业类型、所属计划（排队作业为空）与生成时的计划配置修订、计划触发时刻、触发方式、触发人、冻结的执行输入（参数与目标）、执行身份、有效互斥键与去重键、状态、尝试次数、租约、进度、结果码、统计、错误摘要与追踪编号。 |

作业运行同时是执行队列与运行历史：到点的计划、手动触发和排队作业入队，都生成一条待执行的运行记录，由各节点的执行通道认领执行。定时作业、排队作业与动态配置作业只有一条执行链路。

运行在生成时冻结执行输入与执行身份：计划修改只影响此后生成的运行，重试与接管按原运行的输入执行；需要按修改后的计划执行时，生成新运行。处理器在执行时读取的专题业务配置不属于冻结输入，专题须自行声明其版本复核规则。

专题需要的业务状态与查询（例如翻译生成的槽位、序号与“已过期”“不可用”等专题结果）仍保存在专题表中，以运行标识关联作业运行；作业运行只承担领取、租约、尝试、可用时间与执行留痕，不承载专题状态机。

### 计划

1. 计划表达式支持 cron 与固定间隔两种形式；cron 精度到分钟，按计划声明的时区计算，未声明时使用平台默认时区。夏令时跳过的时刻不触发、重复的时刻只触发一次。固定间隔按上一次运行结束的时刻起算（fixed-delay），首次触发按声明的首次延迟计算，与现有 Spring 定时调度的语义一致；cron 按日历时刻触发。
2. 同一作业类型、租户与业务对象键唯一；平台级计划的 `tenantId` 为空，唯一约束按“空值相同”处理。实现使用包含类型、作用范围、租户与业务对象键的规范化 SHA-256 `planKey` 唯一索引，空租户拥有独立编码，不与任何真实租户混淆。专题以业务对象键区分计划，例如“租户 + 身份源”。
3. 首次登记或修改计划表达式时，从当前时间重新计算下次触发时间，不追补修改前的触发。
4. 托管方为专题时，计划的业务配置只能经专题门面修改；作业管理页上相应字段只读。
5. 暂停的计划不再生成新运行；已生成但未认领的运行保留执行，已在执行的运行继续完成，均可单独请求取消。
6. 部署配置提供全局调度总开关，只停止按计划的自动触发；手动执行与排队作业不受影响。
7. 启动登记时核对全部计划（含暂停计划）的类型可用性。计划引用的作业类型在当前版本中已不存在时，标记为不可用：不生成运行、不重复提醒，在管理页提示清理；能够执行该类型的节点扫描时恢复可用标记。缺失类型不在每轮扫描中反复置为不可用，避免滚动发布中新旧节点持续相互覆盖。

### 运行状态

```text
待执行 → 执行中 → 成功 | 部分成功 | 失败 | 已取消
           ↓
         待重试 → 执行中
```

1. 认领在短事务内完成：对互斥键加事务级锁后，校验状态、互斥键上没有其他有效执行中的运行，再写入租约令牌与到期时间。租约过期后的接管复用原运行记录，并计为一次尝试；定时作业最大尝试次数为 1 时，节点宕机即判定失败，等待下一周期。
2. 互斥只在认领时生效：同一互斥键已有运行在执行时，后来的运行保持待执行，等待前一运行结束后再被认领。定时作业的同一计划上一轮未结束时，本轮触发不再生成新运行，记一次跳过。
3. 平台在执行期间自动续租，以便识别节点宕机；最长运行时长按每次尝试的开始时刻计算，超过作业类型声明的最长运行时长仍未结束的运行，平台停止续租并判定超时，使其租约令牌失效，避免挂死的处理器永久占用互斥键。
4. 租约到期、认领与续租以数据库时间判断，不依赖各节点时钟一致。
5. 计划的同一触发时刻只生成一条运行；停机期间错过的多次触发合并为一次补跑，不逐次追补。
6. 排队作业可声明去重键，有效去重键与互斥键同样由“作业类型 + 作用范围与租户 + 专题键”构成；同一有效去重键存在未结束的运行时返回该运行，不重复入队，返回前仍校验调用方对该运行的归属。去重键必须包含输入版本（例如业务记录的修订号），数据变化后的新请求因此会形成新运行，不会被旧运行吞掉。
7. 入队加入调用方事务：调用方回滚则入队一并撤回，提交后由执行通道领取。
8. 取消为协作式：平台记录取消请求，处理器在安全点检查后停止；待执行的运行直接取消。
9. 节点优雅停机时停止认领并中断尚未进入处理器的领取等待，已进入处理器的运行在宽限期内未完成则尝试释放租约，释放成功不计入尝试次数。宽限期后释放操作最多等待 1 秒；数据库不可用或释放阻塞时放弃等待，由租约自然到期后按正常接管策略处理，避免关停逐个等待连接超时。
10. 租约令牌失效（超时、停机释放或被接管）只意味着旧执行者再也不能经受租约保护的事务提交结果，并不能保证它已经停止：被暂停的节点或尚在进行的外部调用可能与新执行者重叠。平台保证的是同一有效键在同一时刻只有一个有效租约，以及只有有效租约持有者的数据库提交受保护；旧执行者在下一次续租或受保护提交失败时停止。

### 受租约保护的写入

平台不能撤销处理器已经提交的事务，因此“过期运行不能覆盖新结果”只对经平台入口提交的写入成立：

1. 平台提供受租约保护的事务入口：在同一事务内锁定运行记录、校验租约令牌，再执行处理器的业务写入；租约已失效时整个事务回滚。运行记录被锁定期间，续租、超时判定与接管都要等待该事务结束，所以租约在事务内到期不会被他人接管；事务的语句与锁等待设有上限，超出时回滚并按可重试失败处理。
2. 锁顺序统一为“专题业务锁在前、运行记录锁在后”：受保护事务允许专题先取得自身的业务锁，再进入租约校验；平台在删除、清理运行记录时也遵循同一顺序。专题删除链路（如业务记录最终删除时同事务清理生成任务）因此不会与结果发布形成相反的加锁顺序。
3. 处理器的业务写入必须经该入口提交，并按页、按批拆成短事务；通讯录同步的每一页写入、翻译生成的结果发布都属于此类。
4. 处理器在该入口之外的写入（例如调用外部系统）不受保护，必须自身幂等。
5. 执行语义为至少一次：重试、接管、补跑以及租约失效后旧执行者的残余执行都可能重复处理同一输入，处理器负责幂等。

## 执行

1. 每个节点运行调度扫描，按计划的下次触发时间生成运行；生成与推进下次触发时间在同一事务内，多节点并发扫描不会重复生成。计划触发以分钟为粒度。
2. 执行通道是节点内的独立线程池，按通道配置工作线程数与领取间隔；慢作业（如模型调用、通讯录拉取）不占用平台维护作业的线程。排队作业的领取延迟以秒计，本节点入队提交后立即唤醒对应通道。
3. 节点只认领本节点已注册的作业类型与通道，滚动发布期间新旧版本节点可以共存。
4. 扫描间隔、通道线程数与领取间隔、租约时长与留存天数通过 `muyun.platform.job.*` 部署配置调整，非法配置启动即失败。
5. 节点本地的周期工作（例如只扫描本机实时连接的在线闲置检测）不纳入本机制，继续使用 Spring 定时注解；需要集群内只执行一次或需要运行记录的工作必须使用本机制。

## 执行身份

作业在请求线程之外执行，不继承任何请求的用户、租户或委托上下文。执行身份引用保存在计划上，并在生成运行时复制到运行记录；没有计划的排队作业在入队时确定执行身份。账号身份、业务执行范围与作业归属租户是三个独立事实：账号身份是谁在执行，业务执行范围是作业读写哪个租户的数据，作业归属租户决定管理可见性与有效键；三者分别记录，不互相推断。这部分收口 [技术债 TD-008](../TECHNICAL_DEBT.md) 中后台任务系统态授权与审计的部分。

| 模式         | 说明                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 系统身份     | 平台级作业进入现有系统上下文，以“后台作业 + 类型编码”作为必填的系统原因。租户级作业进入新增的“租户内系统执行主体”：同时携带租户、系统原因和以作业类型标识的合成操作者，审计操作者类型为“后台作业”。静态作业处理器默认使用该模式。 |
| 发起人身份   | 保存发起人的身份引用，不保存任何凭据；每次执行通过可信执行身份解析器（`TrustedExecutionIdentityResolver`）重新解析账号、租户与委托，账号停用、删除、需改密或授权失效时本次运行失败。计划的发起人是最后修改人，排队作业的发起人是入队人。 |
| 专用服务账号 | 预留。以租户内专用于后台执行的账号身份运行，权限按普通角色授权；需要先定义服务账号类型及其不可交互登录的约束。                                                                                                            |

1. 租户内系统执行主体是现有 `TenantContext` 的补充：现有系统上下文不带租户，租户上下文又不带系统原因，二者都不能表达“限定在某租户内、无用户的系统执行”。该主体在租户过滤上等同租户上下文，在审计上记录系统原因；动作授权链路如何判定见“动态配置作业”。
2. 动态配置作业的发起人身份只允许租户账号，且其租户必须等于计划的业务执行范围。平台账号会被解析为系统用户并在动作授权中直接放行，因此平台账号发起的动态计划一律按系统身份处理，受系统身份的全部约束。专题排队作业沿用专题已有的身份交接契约：例如翻译生成允许真实账号租户与业务执行范围不同，也允许平台账号作为原触发者，执行时经可信执行身份解析器与专题范围复核恢复。
3. 管理员对失败运行的人工重试生成一条新运行，保留原运行的冻结输入、计划修订与执行身份；原失败记录保留。自动重试和接管复用原运行。立即执行与人工重试不改变执行身份；作业类型声明是否允许他人人工重试，例如翻译生成保留原触发者，不允许为取得更多额度而轮换身份。
4. 运行记录与运行审计都记录执行身份模式、作业类型、计划与运行标识；手动触发另记录触发人。触发人只表示“谁让它现在执行”，不改变执行身份。运行审计通过追踪编号定位到作业运行，作业运行不复制授权判定细节。

## 动态配置作业

动态配置作业是平台内置的作业类型“调用模块动作”，与静态作业共用计划、运行与执行链路。

`ModuleActionInvoker` 是领域层非 HTTP 门面。每次调用读取当前模块、动作及有效授权政策，检查模块存在、启用且属于全局或当前执行租户。静态动作绑定授权后的 `ActionExecutionContext` 后调用领域贡献；动态动作委派 `DynamicRecordService.executeAction`，继续复用动态动作授权、数据范围、可用条件、执行前校验、事务、生命周期与运行审计。门面不替代领域服务自己的附加授权与不变量。

### 声明与参数

- 动态动作由 `PlatformModuleAction.schedulable` 显式声明，默认关闭，在现有模块动作管理入口维护。只支持 `LIST` 层级、`SERVICE` 执行器、不接受表单上下文的动作；记录、批量、`ANY`、对话与表单动作保存计划时拒绝。`formSupported` 表示可接受表单上下文，首批保守地整类排除。
- 静态领域 Spring Bean 实现 `ScheduledModuleAction`，显式贡献模块、动作编码、参数校验和执行方法；不扫描或反射调用 Controller。目录中的同编码动作必须存在、启用、声明 `LIST` 且不接受表单上下文。未贡献的静态动作不可调用。静态可用表达式依赖动态表单求值，首批不接受；领域可用性由贡献的 `validate` 及服务不变量负责。
- 静态贡献调用正常领域 Service，使用 `listForAction` / `selectForAction` 等动作感知查询读取受数据权限保护的数据；普通 `list/select` 不会因绑定了动作上下文而自动变成授权查询。写入保留原 Ability 与领域服务链路，不提供裸 DAO 调用捷径。
- 静态参数使用 JSON 对象，原文及编码后的参数各不超过 16 KiB，完整冻结输入（含身份引用）仍受作业 16 KiB 限制；递归拒绝密码、密钥、令牌、认证头等凭据字段。贡献的参数校验应声明业务允许的参数，不在参数中保存凭据或业务全文。参数作为动作 payload，不绑定记录、表单、查询结构或 HTTP 请求。

### 计划、身份与执行

专题模块为 `platform.scheduled_action_plan`，通过 `JobService.registerManaged` 在正常 CRUD 事务中维护底层计划；删除通过 `deleteManaged` 删除计划，保留已有运行。平台与租户类型分别为 `platform.module-action-platform`、`platform.module-action`，均使用 `default` 通道、最长五分钟、一次尝试及标准失败提醒。静态参数、身份引用与身份模式随运行生成冻结；人工重试保留原冻结输入，立即执行不替换执行身份。

1. 发起人模式 `INITIATOR` 在每次保存时用 `TrustedExecutionIdentityResolver.capture` 捕获最后修改人的账号创建时间、账号租户及可选委托引用，不保存凭据或权限快照；界面明确标明每次保存会替换执行人。只接受与业务执行范围相同的租户账号。执行时重新解析，账号删除、停用、重建、需改密、委托或权限失效均失败。恢复普通租户上下文、真实用户与原委托，运行审计同时保留作业关联与真实操作者。
2. 平台账号保存的计划统一转为 `SYSTEM`，包括请求指定发起人模式的情况；不能借平台账号的普通动作放行绕过白名单。`SERVICE_ACCOUNT` 只作为模型枚举预留，不接受保存或执行。
3. 系统模式只能由平台管理员创建、修改、删除或启停，且保存与执行时目标必须在持久白名单 `platform.system_action_whitelist` 内。白名单是独立标准管理模块，只有平台管理员可见、可维护。租户系统主体保留当前租户过滤；平台系统主体没有业务租户。
4. IAM 对作业系统主体先判白名单，再处理普通匿名、登录或账号授权分支，放行判定为 `JOB_SYSTEM_WHITELIST_GRANTED`，操作者类型为 `BACKGROUND_JOB`。数据范围只对通过白名单的动作返回本执行范围内 unrestricted，不生成跨租户 bypass。领域内部若还要求其他动作权限，这些动作仍须独立通过白名单，不以入口授权替代。
5. 租户管理员看到本租户专题计划，普通用户只看到本租户且当前有权执行目标动作的计划；保存发起人计划仍复核目标权限。系统计划只允许平台管理员维护。作业运维页不修改专题业务字段；暂停与恢复同步专题启停状态，不替换执行身份。
6. 模块或动作删除、停用、撤销可定时调用声明后，下次运行失败并按标准规则提醒，不删除计划。最终失败同时提醒范围管理员及冻结的发起人。运行与审计都记录执行身份模式，并以追踪编号关联。

## 失败处理与提醒

1. 处理器抛出的异常按作业类型声明区分为可重试与不可重试；可重试失败按退避进入待重试，超过最大尝试次数后判定失败。
2. 定时作业默认不重试，失败后等待下一周期；排队作业默认最多尝试 3 次。
3. “已有执行者在运行”“达到本轮批次上限”这类处理器正常结果，按处理器返回的结果码记为成功或部分成功，不计入失败。
4. 运行最终失败，或计划连续失败达到阈值（默认 3 次）时，通过[实时业务提醒](BUSINESS_NOTIFICATION_BACKEND_INTEGRATION.md)通知所在范围的管理员：平台级作业通知平台管理员，租户级作业通知该租户管理员，发起人身份的作业同时通知发起人。作业类型可以关闭或聚合提醒。提醒只携带作业与运行标识，点击后进入运行详情，并按点击者权限重新校验。
5. 业务提醒只投递在线用户，因此计划列表持久展示最近运行状态与连续失败计数，离线管理员登录后仍能发现失败。
6. 错误摘要只保存错误类型、稳定错误码与必要诊断，不保存外部报文、凭据、业务全文或堆栈；运行详情不展示请求参数原文。

## 管理入口

作业计划与作业运行以平台标准静态模块交付，位于系统管理菜单下，按普通动作授权控制。

| 角色       | 可见范围                     | 可执行操作                                                                           |
| ---------- | ---------------------------- | ------------------------------------------------------------------------------------ |
| 平台管理员 | 全部平台级与租户级计划和运行 | 立即执行、暂停与恢复、取消运行、重试失败运行；修改非专题托管计划；维护系统身份白名单 |
| 租户管理员 | 本租户计划和运行             | 立即执行、暂停与恢复、取消运行、重试失败运行；修改本租户非专题托管的计划             |

运行详情展示触发方式、触发人、执行身份、状态、进度、结果码、统计、错误摘要与追踪编号；专题可提供跳转到本专题结果页的链接。

## 运行记录留存

1. 已结束的运行默认保留 90 天，每个计划至少保留最近 20 条；无计划的排队作业只按天数清理。作业类型可声明不同保留期，平台默认值通过部署配置调整。
2. 清理分批执行、有上限，作为平台级定时作业运行，自身的运行记录同样受留存约束。
3. 专题以运行标识关联的业务事实（如同步统计、翻译版本）按专题自身的留存策略处理，不随作业运行一并删除；专题要求随业务记录删除同步清理的运行，由专题在其删除事务内调用平台入口清理。

## 当前接入与部署契约

`JobHandler` Spring Bean 声明类型策略，专题通过 `JobService.registerManaged` 登记计划，通过 `enqueue` 在调用方事务中入队。参数仅允许不超过 16 KiB 的身份、版本及目标引用，不得含凭据或业务全文；去重键须包含专题输入版本。核心默认执行 `SYSTEM` 外层身份，处理器必须显式声明支持其他身份模式；模块动作类型支持 `INITIATOR` 并恢复其可信身份，其他未支持模式明确失败。翻译处理器仍在系统外层上下文内沿用专题的原触发者可信恢复契约。

处理器通过 `JobContext.transaction(businessLocks, writes)` 先取专题业务锁，再锁运行并校验令牌、租约和取消请求；业务锁和写入处于同一事务。事务最长 30 秒，SQL 语句上限 20 秒、锁等待上限 10 秒，失败回滚后按可重试失败处理。处理器应按批进入该入口，不在持锁期间进行外部调用。租户内系统主体的 `TenantContext.isSystem()` 仍为 `false`，不会获得跨租户系统授权；审计记录 `BACKGROUND_JOB`、系统原因、作业类型、计划与运行标识，合成操作者为稳定的类型摘要。

配置前缀为 `muyun.platform.job`，默认开启自动调度以延续交换文件清理的既有行为：

| 配置 | 默认值 | 边界 |
| ---- | ------ | ---- |
| `scheduled-enabled` | `true` | 只停止自动触发，排队、人工运维、续租继续运行 |
| `scan-interval` | `1m` | 1 秒至 1 小时 |
| `lease-duration` | `1m` | 30 秒至 1 小时；类型声明可覆盖 |
| `shutdown-grace` | `30s` | 0 至 5 分钟 |
| `retention-days` | `90` | 1 至 36500 天；类型声明可覆盖 |
| `channels` | `default` 通道 | 通道总数必须为 1 至 32 |
| `channels.<name>.initial-delay` | `0` | 节点就绪后首次领取延迟，0 至 5 分钟；入队唤醒不能绕过 |
| `channels.<name>.delay-after-execution` | `false` | 为 `true` 时每次执行后也等待 `claim-interval`，入队唤醒不能缩短等待 |
| `channels.<name>.threads` | `default` 通道 2 | 每通道 1 至 64，总计不超过 256 |
| `channels.<name>.claim-interval` | `1s` | 100 毫秒至 1 分钟 |

上述通道属性均开放部署绑定，用于按通道控制资源、启动延迟与执行节奏；内容生成通道的专题装配约束见下文。通道必须显式配置，类型引用未配置通道时启动失败；节点只领取已注册类型与对应通道。默认计划在平台 schema 启动完成后登记，保留管理员修改过的计划和暂停状态。运行留存作业每日执行，每轮最多 10 批、每批 200 条，按类型保留期和每计划至少 20 条终态记录清理，不处理专题业务事实。

日志留存与工作流超期扫描复用 `default` 通道，属于数据库维护，无需额外通道配置。类型编码分别为 `platform.business-log-retention`、`platform.workflow-overtime`。日志留存的 `muyun.platform.business-log.retention.scan-delay`（24 小时）、`initial-delay`（一分钟）及工作流的 `muyun.workflow.overtime-scan-delay-ms`（300000）、`overtime-scan-initial-delay-ms`（60000）用于首次登记默认计划。已登记计划的间隔和首次延迟以持久计划为准，部署配置变化不覆盖计划；需要调整时由管理员在作业管理页维护。固定间隔至少一分钟，首次延迟不得为负，沿用平台计划校验。

日志留存的 `scheduled-enabled=false` 不注册处理器，已登记计划标记不可用且不再自动触发；重新启用后恢复可用性，并保留管理员暂停状态。平台全局调度开关同样控制两项作业。两类开关均不影响日志治理的人工立即清理入口。存储中立的日志清理仍使用独立存储适配器的幂等、分批删除与 advisory lock，不将整个清理包装成一个作业事务；其独立提交不具备作业事务回滚语义。工作流扫描按节点 ID 稳定游标每批最多 200 条，每批单独进入受租约与取消保护的短事务；节点更新与对应事件原子提交，后续批次失败不回滚已提交批次。保留原扫描范围、超期判定、版本检查和系统操作者事件；节点 `updatedBy` 保留原编辑者，作业身份记在运行记录中，不新增工作流提醒或逐节点运行审计。

日志留存正常完成记为成功；达到批次上限记为部分成功；存储锁被其他执行者持有记为成功跳过，结果码为 `SKIPPED_ALREADY_RUNNING`，均不增加连续失败。统计以日志类型为前缀记录删除数、批次数和各状态的策略计数；每类策略的结果仍写程序日志。工作流统计记录扫描、预警、超期和更新节点数。真正异常交由作业机制记录失败、按阈值提醒，定时作业不自动重试。

业务内容翻译自动建立独立 `content-generation` 通道。租户业务类型为 `platform.content-generation`，平台业务类型为 `platform.content-generation-platform`，两者按业务执行范围确定归属，共用五分钟租约与最长单次时长、最多三次尝试、15／30 秒退避、30 天运行留存；关闭失败提醒和管理员人工重试。账号租户、业务执行范围分别保存在专题请求中，外层系统主体不替代实际翻译操作人。队列参数只保存生成记录及槽位引用，去重键包含请求与序号，入队及运行关联随调用方事务提交或撤回。

原 `muyun.content.generation-workers`（默认 1，1–8）、`generation-delay-ms`（默认 1000，100–60000）分别映射到该通道的线程数和领取间隔；`generation-initial-delay-ms`（默认 60000，0–300000）控制每次节点就绪后首次领取延迟，入队唤醒不能绕过它。该通道在每次执行后仍等待领取间隔，保持原 fixed-delay 节奏。通道自动装配，不要求既有部署新增配置；也可显式配置 `muyun.platform.job.channels.content-generation.threads`、`claim-interval`，未显式设置旧参数时以新通道配置为准，新旧显式值冲突则启动失败，线程数仍限 1–8。首次延迟继续由原内容参数控制（覆盖该通道的 `initial-delay`），`delay-after-execution` 固定为 `true`。全局自动调度开关不停止翻译排队执行。

`JobHandler.lockBusiness` 在认领、续租、完成、取消、释放及留存删除的运行锁之前取得专题业务锁，`stateChanged` 在同一事务镜像运行变化到专题事实。回调只进行数据库操作，不调用外部服务；运行状态的事实源仍是平台，专题不自行领取或维护租约。

`platform.content-generation-retention` 使用 `default` 通道，每小时 fixed-delay、首次延迟一分钟，每轮清理最多 200 条超过 30 天的终态专题记录。运行记录独立清理；状态与问题码以专题表为准，运行已被清理时尝试次数返回 0、重试时间为空，不影响终态查询。原文、译文与证据独立留存。业务最终删除先持有专题业务锁，再通过 `JobService.purgeUnfinished` 清理关联未结束运行；专题记录与这些运行同事务删除或回滚。旧专题线程池、领取和租约字段已移除。

管理模块为 `platform.job_plan`、`platform.job_run`，挂载在现有“平台管理 → 运行运维”菜单中。管理页只修改非专题托管计划的时间配置；专题计划通过专题门面创建和修改。IAM 中平台账号为平台管理员，租户管理员依据显式账号授予的租户管理员角色判定；无 IAM 适配时管理拒绝访问，失败提醒只记录日志。

## 不建设的能力

1. 外部调度框架、独立 worker 集群或跨应用的调度中心。
2. 作业之间的依赖编排、DAG 与分片执行；需要多步编排的业务归工作流或专题自身。
3. 秒级精度的计划调度与严格准点保证；计划以分钟为粒度，允许扫描间隔内的延迟。
4. 恰好一次的执行保证与旧执行者立即停止的保证；平台保证至少一次、单一有效租约与受租约保护的写入。
5. 在作业记录中保存业务全文、外部报文或凭据。
6. 任意脚本或表达式作为作业内容；动态配置作业只能调用已声明可定时调用的模块动作。

## 验收

以 contract 与 IT 覆盖以下边界：

1. 多节点并发扫描与认领时，同一计划触发时刻只生成一条运行；同一有效键在同一时刻只有一个有效租约；不同租户的相同专题键互不串行，幂等入队不会返回其他租户的运行。
2. 节点在执行中宕机，租约到期后由其他节点接手并计入尝试；过期运行经受租约保护的事务提交时被拒绝。
3. 超过最长运行时长的运行判定超时并释放互斥键，旧执行者此后的受保护提交被拒绝；优雅停机释放租约且不计尝试；受保护事务持有运行记录期间，续租与接管等待其结束。
4. 停机期间错过的多次触发只补跑一次；暂停的计划不生成运行；上一轮未结束时本轮跳过；固定间隔按上一次运行结束起算。
5. 计划修改后，已生成的运行与其重试仍按原冻结输入执行。
6. 排队作业随调用方事务入队与撤回，按含输入版本的去重键幂等入队，可重试失败按退避重试，超过次数后失败并按类型声明提醒。
7. 作业执行不继承请求上下文；租户级作业不能读写其他租户数据；系统身份执行记录系统原因与作业操作者。
8. 身份验收：发起人身份在账号停用、授权收回后执行失败；平台账号不能以发起人身份绕过白名单；人工重试不改变执行身份。
9. 动态配置验收：系统身份计划只能由平台管理员维护，且目标动作必须在白名单中。
10. 租户管理员看不到平台级作业与其他租户的计划和运行。
11. 迁移后的日志留存、交换文件清理、工作流超期扫描与翻译生成保持原有行为；翻译结果发布与业务记录最终删除并发时不死锁，账号租户与业务执行范围不同的翻译仍可执行。
12. 运行记录按类型保留期与保底条数清理，不删除专题业务事实。
